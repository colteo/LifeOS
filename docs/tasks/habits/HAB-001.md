# HAB-001 — Habit Tracker v1

Status: DESIGN — blueprint for review (GitHub issue #41). Nothing here is implemented. No code,
migration, API, package, Firebase, Render, Neon or cron-job.org change is part of this document.

This is the umbrella document of the issue #41 epic. Companion specifications:

- [HYD-001](../nutrition/HYD-001.md) — Hydration v1 (the only source of water data).
- [REM-001](../automation/REM-001.md) — generic and conditional reminders on the existing automation
  engine.

Builds on ADR-001 (onion), ADR-005 (PostgreSQL), ADR-006 (user-owned data, explicit `UserId`,
composite ownership keys), NUT-001 (local diary dates), NUT-003 (neutral copy, hub/IA rules),
NAV-001 (dock and More), AUTO-001/002/003A and ADR-012 (via REM-001 only).

Decision labels: **[Given]** = decided by the product owner (issue #41 / task brief); **[Proposal]** =
recommended default chosen in this blueprint, to be confirmed in review. Every [Proposal] can be
implemented as written; alternatives are recorded where the choice is not obvious.

## 1. Problem

LifeOS tracks money, training, meals and journal entries, but not the small recurring behaviours a
user wants to build ("read 20 pages", "stretch", "no phone after 23:00", "drink my water"). The
questions to answer:

> "What do I still have to do today?" · "Am I keeping it up?"

## 2. Given decisions

| # | Decision |
|---|---|
| G-1 | **[Given]** Habits v1: creation, frequencies, check-in, history, goals, streak and adherence. |
| G-2 | **[Given]** Every module is potentially available to every user; activation/preferences per user. |
| G-3 | **[Given]** Hydration is the single source of water consumed; Habits **derives** goal satisfaction from it and never stores water amounts. |
| G-4 | **[Given]** Reminders reuse AUTO-001 / ADR-012; no second scheduler or queue (REM-001). |
| G-5 | **[Given]** Deterministic domain state, .NET-owned writes, per-user isolation, UTC instants, no LLM. |
| G-6 | **[Given]** Cycle Tracker is completely separate and not designed here. |

## 3. Proposed product decisions (summary)

| # | Decision |
|---|---|
| P-1 | **[Proposal]** A habit is a **yes/no daily behaviour**. Check-in = "Done" for a local date. Quantitative habits (pages, minutes) are deferred; the one quantitative habit in v1 is **Hydration**, whose quantity lives in Hydration. |
| P-2 | **[Proposal]** Three frequencies: **Daily**, **Specific weekdays** (e.g. Mon/Wed/Fri), **N times per week** (1–7, ISO week Mon–Sun). |
| P-3 | **[Proposal]** Day statuses: stored **Done** / **Excused**; derived **Missed**, **Pending** (today, not yet done), **Not scheduled**, **Inactive** (archived/before start). Undo = delete the stored status. |
| P-4 | **[Proposal]** Days are **local calendar dates** sent by the client (NUT-001 model). No time of day, no UTC conversion, so time zone changes and DST cannot move a check-in. |
| P-5 | **[Proposal]** Backdating is allowed for any date from the habit's start up to local today; future dates are rejected. The UI offers today and the last 6 days directly; older days via History. |
| P-6 | **[Proposal]** Frequency changes are **versioned from local today** (`habit_schedule_versions`); past days keep the frequency they had. |
| P-7 | **[Proposal]** **Archive** instead of pause/delete for "inactive": an archived habit stops being scheduled, keeps its history and can be restored. Archive and restore are schedule versions (`Inactive`), so history math stays uniform. Delete is a separate destructive action with confirmation. |
| P-8 | **[Proposal]** **Streak** = consecutive *scheduled units* met (days for Daily/Weekdays, weeks for N-per-week). Excused and inactive units are neutral (neither break nor extend). Today/this week is pending and never breaks a streak. |
| P-9 | **[Proposal]** **Adherence** = met / expected over a window (default last 30 days), excused excluded from both. Shown with the raw counts ("21 of 26 days · 81%"). |
| P-10 | **[Proposal]** A **Hydration habit** ("Reach my water target") is derived: done on D ⇔ Hydration says D's target is met. No Done rows are ever stored for it; Excused is allowed. At most one active Hydration habit per user. |
| P-11 | **[Proposal]** No module activation flag. Habits appears in More for every user; the Home "Habits today" card appears only when the user has at least one active habit. |
| P-12 | **[Proposal]** Copy is neutral and non-judgemental ("Missed", never "Failed"; no shaming, no gamification badges in v1). |

### 5.1 Invariants

1. Name 1–80 characters after trimming; description ≤ 500; note ≤ 280.
2. `StartsOn` is within `[today − 365, today + 365]` at creation (today = caller's local date).
3. The schedule has ≥ 1 version; the first starts at `StartsOn`; versions are strictly increasing in
   `EffectiveFrom`; consecutive identical versions are merged.
4. A version's fields match its frequency (Weekdays ⇒ non-empty set; TimesPerWeek ⇒ 1..7; others ⇒
   none).
5. `ChangeFrequency(f, today)`: if a version starts today it is replaced, otherwise a new version
   starts today. Never changes a past version. Archived habits cannot change frequency.
6. `Archive(today)` appends `Inactive` from today (or replaces today's version) and sets Archived;
   `Restore(today, frequency)` appends the given frequency from today (default: the last non-Inactive
   frequency) and sets Active.
7. A check-in date is `≥ StartsOn` and `≤ today`, and its version is not `Inactive`.
8. **Done is rejected for a Hydration habit** (`HabitCompletionSourceIsDerived`). Excused is allowed.
9. Excused is rejected on a date that is `NotScheduled` for a day-based frequency (meaningless).
   For TimesPerWeek every active day can be excused (it reduces that week's target, §6.3).
10. Done on a non-scheduled day of a Weekdays habit is allowed and shown as a bonus; it does not
    count in streak or adherence.
11. One check-in per `(habit, date)`; saving again replaces status/note (idempotent upsert).
12. At most one **active** Hydration habit per user.

## 6. Status, streak and adherence semantics

### 6.1 Day status (for one date D)

```text
version = schedule.VersionOn(D)              -- none (before StartsOn) → Inactive
if version.Frequency == Inactive             → Inactive
source = Manual ? checkIn(D) : (checkIn(D) is Excused ? Excused : hydrationDay(D).IsTargetMet ? Done : null)
if source == Done                            → Done
if source == Excused                         → Excused
if !IsScheduled(version, D)                  → NotScheduled     (Weekdays: D's weekday ∉ set)
if D == today                                → Pending
if version.Frequency == TimesPerWeek         → NotScheduled     (a week-goal day without check-in is neutral; the week is judged)
else                                         → Missed
```

Hydration habit: if the date has **no Hydration target** (`TargetMl == null`), the day is
`NotScheduled` (nothing to meet), never Missed.

### 6.2 Streak — alternatives

| | A. Consecutive calendar days with Done | **B. Consecutive scheduled units met (recommended)** | C. No streak, adherence only |
|---|---|---|---|
| Mon/Wed/Fri habit | breaks every Tuesday | Mon→Wed→Fri = 3 | — |
| 3×/week habit | meaningless | counted in weeks | — |
| Sick day | breaks | Excused is neutral | — |
| Motivation value | high but punishing | high, fair | low |

**Recommendation B.** Rules:

- Day-based (Daily, Weekdays): walk back over scheduled days from `asOf`. Today Done → +1; today
  Pending → skip. Earlier: Done → +1, Excused/NotScheduled/Inactive → skip, Missed → stop.
- Week-based (TimesPerWeek): walk back over ISO weeks. Current week met → +1, otherwise pending
  (skip). Earlier: met → +1; effective target 0 (fully excused/inactive) → skip; not met → stop.
- A change between a day-based and a week-based frequency **ends the walk** (streak counts only
  since that change); Daily ↔ Weekdays continues. Avoids mixing units.
- Best streak = maximum run over the whole history with the same rules (no "pending" in the past).

### 6.3 Weekly goal (TimesPerWeek = N)

- Week = ISO Monday–Sunday in local dates (same as Weekly Review and NUT-003).
- `available` = days of the week that are active (not Inactive, ≥ StartsOn) and not Excused.
- `target = min(N, available)`; `done` = Done check-ins in the week (any day).
- Week met ⇔ `done ≥ target` and `target > 0`. The first partial week after `StartsOn` is handled by
  the same rule (a habit starting Saturday with N=3 has target 2 that week).
- "This week 2 / 3" uses `target` for the current week; extras show "4 / 3".

### 6.4 Adherence

- Window default: the last 30 days ending `asOf` (selectable 7 / 30 / 90 in the detail view).
- Day-based: `Met` = Done on scheduled days; `Expected` = scheduled days − Excused − Pending(today).
  Bonus Done on non-scheduled days is excluded.
- Week-based: weeks fully inside the window plus the current week only if already met;
  `Met = Σ min(done, target)`, `Expected = Σ target`.
- `Percent = round(100 × Met / Expected)` (half away from zero); `Expected = 0` → no percentage,
  "Not enough data yet".

### 6.5 Hydration habit derivation

```text
HabitProgressCalculator(habit with Source=Hydration, checkIns (Excused only), hydrationDays):
  hydrationDays = IHydrationDayReader.GetDaysAsync(user, from, to)    -- HYD-001 §7.1
  Done(D) ⇔ hydrationDays[D].IsTargetMet
```

Nothing about water is persisted in Habits. Editing or deleting a past intake re-derives the habit's
past days on the next read (HYD-001 §10). The detail view says: "Done when your water target is
reached. Based on Nutrition → Water."

### 6.6 Time zones, day boundaries, DST

- Every date is a **local calendar date chosen by the client** (the day being viewed). The server
  stores dates, not instants, for check-ins, so DST transitions and zone changes cannot move them.
- "Today" for validation is computed from the request's `utcOffsetMinutes` (Finance/NUT-001
  convention): `localToday = (utcNow + offset).Date`, offset within ±14 h. Future dates → 400.
- Travelling east/west makes "today" jump with the device, exactly like the Food diary. A check-in made
  at 23:30 in Rome stays on that date after flying to New York.
- 23-hour and 25-hour DST days are ordinary dates: one status per date.
- Reminders (REM-001) resolve "today" with the user's IANA zone (`users.time_zone_id`), which follows the
  same device (PD-2); the two can differ only during the seconds between a zone change and its sync.

### 6.7 Edge cases

| Case | Behaviour |
|---|---|
| Backdated Done on a Missed day | becomes Done; streak/adherence recomputed (may join two streaks) |
| Undo today | back to Pending; streak unchanged until the day ends |
| Habit created with StartsOn in the past | earlier days are Missed unless backfilled; UI hint "Check in past days from History" |
| StartsOn in the future | listed under "Upcoming", not in Today; check-ins rejected until then |
| Frequency changed Daily → Mon/Wed/Fri today | past Daily days keep Missed/Done; from today only M/W/F scheduled |
| Archived for two weeks, restored | the two weeks are Inactive; streak continues across them (neutral) |
| Delete | check-ins and REM-001 reminders of the habit cascade; no other module affected |
| Weekdays habit, Done on a non-scheduled day | stored, shown as bonus, ignored by stats |
| TimesPerWeek, 7 Excused days | target 0 → week skipped |
| Hydration habit, target removed | days without target are NotScheduled; streak neither breaks nor grows |
| Hydration habit when Hydration target never set | creation rejected (409 `hydration_target_required`) |
| Two devices check in the same day concurrently | upsert on `(habit_id, date)`: last write wins, one row |
| Clock skew: client sends tomorrow's date | 400 future date |
| Over 100 active habits | 409 `habit_limit_reached` (abuse guard; [Proposal] limit 100) |

### 7.2 Pseudocode — Today list

```text
GetHabitsForDay(user, date, offset):
  require date ≤ localToday(offset)
  habits   = repo.GetAllAsync(user) where Active or StartsOn > date (upcoming)
  weekFrom = IsoWeekStart(date); from = min(weekFrom, date − 60)        -- enough for current streak in most cases
  checkIns = repo.GetCheckInsAsync(user, ids, from, date)
  hydro    = any Hydration habit ? IHydrationDayReader.GetDaysAsync(user, from, date) : none
  for each habit: progress = Calculator.Evaluate(habit, checkIns[h], hydro, asOf: date, window: 30)
                  if progress.CurrentStreak reached `from` → extend once with full history (rare)
  return grouped list
```

Streaks longer than the loaded window are computed by one extra, still bounded, history query for
that habit; personal habit histories are a few thousand rows at most.

## 8. API contracts

Routes under `/api/habits`, authenticated, user-scoped; another user's habit = 404. Strings for
enums. Field-keyed ProblemDetails for validation; 409 for business conflicts with a stable `code`.

| Route | Result |
|---|---|
| `GET /api/habits?date=yyyy-MM-dd` | 200 `HabitsForDayResponse` |
| `GET /api/habits/{id}?date=&window=30` | 200 `HabitDetailResponse`; 404 |
| `GET /api/habits/{id}/history?from=&to=` | 200 `HabitHistoryResponse`; 400 (> 366 days) ; 404 |
| `POST /api/habits` | 201 `HabitDetailResponse`; 400; 409 `habit_limit_reached` / `hydration_habit_exists` / `hydration_target_required` |
| `PUT /api/habits/{id}` | 200; 400; 404; 409 `habit_archived` (frequency change) |
| `POST /api/habits/{id}/archive` | 200; 404 |
| `POST /api/habits/{id}/restore` | 200; 404; 409 `hydration_habit_exists` |
| `DELETE /api/habits/{id}` | 204; 404 |
| `PUT /api/habits/{id}/check-ins/{date}` | 200 `HabitDayResponse`; 400 (future, before start, excused on non-scheduled); 404; 409 `habit_inactive_on_date` / `habit_completion_derived` |
| `DELETE /api/habits/{id}/check-ins/{date}?utcOffsetMinutes=` | 200 `HabitDayResponse` (idempotent); 404 |

Writes that depend on "today" carry `utcOffsetMinutes` (body for PUT/POST, query for DELETE).

### 10.1 Accessibility

- Each toggle is a `<button aria-pressed>` with an accessible name "Mark Read 20 pages done for
  today" / "Read 20 pages, done today, open options".
- Status is shown by icon **and** text (✓ Done, – Excused, ✕ Missed, ○ To do); calendar cells have
  `aria-label="Mon 13 Oct, Missed"`.
- Touch targets ≥ 48dp; streak flame icon is decorative (`aria-hidden`), the number is text.
- Results of a toggle are announced (`aria-live="polite"`: "Read 20 pages done. Streak 4 days.").
- Respect reduced motion (no confetti/animation in v1).

## 15. Rollout, risks, cost, privacy

- **Rollout:** each PR is deployable alone; migrations are additive (new tables only). Production
  migration per release follows the runbook S4 review. No feature flag is needed for Habits.
- **Neon/Render:** Habits adds no scheduled work. Read cost per Today view: 3 small indexed queries.
- **Privacy:** habit names/notes are user free text — never logged, never in push copy (REM-001
  uses fixed copy), never sent to AI in v1. Synthetic data in tests and docs.
- **Risk — stats rules are subtle:** mitigated by a pure calculator with a table-driven test suite
  (B1) before any UI.
- **Risk — history reads grow:** bounded windows + one extended read for long streaks; a cached
  `current_streak` column is explicitly *not* proposed (derived data that can drift).
