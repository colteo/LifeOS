## 1. Problem

AUTO-003A ships two *fixed* Finance reminders (09:00 local, item-driven). Users also need:

1. **Their own reminders**: "Call the dentist" on 20 Oct at 10:00; "Take vitamins" every day at
   08:30; "Water the plants" Mon/Thu at 19:00.
2. **Module-aware nudges** that fire only when still relevant: "a habit is still open today",
   "today's water target isn't reached yet".

Both must run on the existing engine (no second scheduler or queue), respect quiet hours and privacy
rules, survive late ticks and FCM failures, and never notify twice for one occurrence.

| # | Decision | Why |
|---|---|---|

| D-2 | **[Proposal]** Schedules: `Once(date, time)`, `Daily(time)`, `Weekly(weekdays, time)`; times are **local wall-clock in the user's current IANA zone** (follows the device, PD-2), whole minutes. | D-4 | **[Proposal]** Two handlers on the existing engine: `Reminder` (Custom, lateness **6 h**) and `ConditionalReminder` (nudges, lateness **2 h**). | `IAutomationHandler.MaxLateness` is per handler; nudges about "today" go stale faster. |

## 5. Domain model and invariants

Namespace `LifeOS.Domain.Reminders`.

```text
Reminder                                    (aggregate root)
- Id, UserId
- Kind            Custom | HabitIncomplete | HydrationGoal
- Title           string? 1..80 trimmed     (Custom ⇔ required; conditional ⇒ null)
- Note            string? ≤ 500             (Custom only)
- HabitId         Guid?                     (HabitIncomplete ⇔ required)
- Schedule        ReminderSchedule
- Status          Active | Paused | Completed
- NextDueLocal    DateTime? (Kind=Unspecified, whole minutes)   Active ⇔ non-null (except snooze-only)
- SnoozeUntilUtc  DateTimeOffset?
- LastTriggeredAtUtc DateTimeOffset?, LastOutcome Notified | Suppressed | Missed | Disabled ?
- CreatedAtUtc, UpdatedAtUtc

ReminderSchedule                            (value object)
- Kind            Once | Daily | Weekly
- Date            DateOnly?   (Once)
- Weekdays        WeekdaySet? (Weekly, non-empty)
- Time            TimeOnly    (whole minutes)
  FirstAfter(localNow)      → DateTime?   first occurrence strictly after localNow (minute precision)
  LatestAtOrBefore(localNow)→ DateTime?   most recent occurrence ≤ localNow
  Includes(localDateTime)   → bool
```

Invariants:

1. Kind/field shape as above; conditional kinds reject `Once`.
2. `Time` and `NextDueLocal` have whole minutes; `Weekdays` non-empty.
3. `Create/Update(…, localNow)`: `Once` must be strictly after `localNow`; `NextDueLocal =
   Schedule.FirstAfter(localNow)`; `SnoozeUntilUtc` cleared on schedule change.
4. `Pause()` keeps fields, Status Paused. `Resume(localNow)` recomputes `NextDueLocal` from now (no
   catch-up). Completed reminders cannot be resumed (edit creates a new `Once` date instead).
5. `Snooze(nowUtc, minutes ∈ {15, 60, 180})` allowed for Active and Completed; replaces a pending
   snooze; rejected for Paused.
6. `Advance(occurrenceLocal, outcome, nowUtc)`: if `NextDueLocal == occurrenceLocal` then
   `NextDueLocal = Schedule.FirstAfter(occurrenceLocal)`; a `Once` reminder with no further occurrence
   becomes Completed (`NextDueLocal = null`). Always sets `LastTriggeredAtUtc`/`LastOutcome`. If the user
   edited the reminder meanwhile (`NextDueLocal` differs) only the `Last*` fields change.
7. `AdvanceSnooze(snoozeUtc, outcome, nowUtc)`: clears `SnoozeUntilUtc` only if it equals `snoozeUtc`.

## 6. Scheduling on the existing engine

### 6.1 Why `next_due_local` (alternatives)

| | A. Zone buckets with a fixed time (AUTO-003A) | B. `next_due_at_utc` (AUTO-001 §16 sketch) | **C. `next_due_local` + zone join (recommended)** |
|---|---|---|---|
| Per-user times | no (one time for everybody) | yes | yes |
| Zone change (PD-2) | automatic | stale until recomputed; Users would have to call Reminders, or every tick re-scans | automatic: the wall-clock value does not depend on the zone |
| Query | per zone | `WHERE next_due_at_utc <= now` | `JOIN unnest(@zones, @localNows) z ON u.time_zone_id = z.zone WHERE r.next_due_local <= z.local_now` |
| DST | `ToUtc` | must be right at write time | SQL is a superset prefilter; exact `DueAtUtc` via `LocalSchedule.ToUtc` in .NET |

C keeps the AUTO-001 principle ("the tick knows nothing; LifeOS decides by its own clock") and the
module boundary (Users/core never call Reminders). `next_due_local` is a schedule value, not an
instant, like `diary_time` (NUT-001) — the UTC rule for instants is respected (`snooze_until_utc`,
`last_triggered_at_utc`, executions and deliveries are UTC).

### 6.2 Discovery (`FindDueAsync`)

```text
FindDueAsync(nowUtc, limit)                              -- one handler per kind group (D-4)
  zones     = repo.GetUserTimeZoneIdsAsync()             -- DISTINCT users.time_zone_id (≤ ~400)
  localNows = for each valid IANA zone: ConvertTime(nowUtc, zone) truncated to the minute
  rows      = repo.FindCandidatesAsync(kinds, zones, localNows, nowUtc, limit × 2)
              -- SQL (ids-only, oldest first):
              --   status <> 'Paused' AND kind = ANY(@kinds) AND type preference enabled
              --   AND ( (status = 'Active' AND next_due_local <= z.local_now)
              --      OR snooze_until_utc <= @now )
  for each row:
    zone = row.TimeZoneId
    if row.SnoozeUntilUtc <= now:  yield key "<id>:s:<snooze utc>", scheduled = SnoozeUntilUtc
    if row.NextDueLocal <= localNow(zone):
       occ = Schedule.LatestAtOrBefore(localNow) (≥ NextDueLocal)        -- skip intermediate misses
       due = LocalSchedule.ToUtc(zone, occ)                              -- AUTO-001 §6 gap/overlap rules
       if due > now: continue                                            -- inside a spring-forward gap
       if now ≥ due + MaxLateness: stale.Add(row, occ)                   -- maintenance below
       else yield key "<id>:<occ local>", scheduled = due
  existing = executions with these keys (one query) → terminal ones go to stale; Running/FailedRetryable skipped
  repo.AdvanceStaleAsync(stale)                          -- bounded, conditional UPDATE (see 6.4)
  return first `limit` occurrences
```

The core then claims each occurrence with `INSERT … ON CONFLICT DO NOTHING` exactly as for Weekly
Review and Finance reminders. Concurrent ticks: one INSERT wins.

### 6.3 Execution (`ExecuteAsync`)

```text
parse key → (reminderId, occurrenceLocal | snoozeUtc)       invalid → PermanentFailure("InvalidOccurrenceKey")
zone = occurrence.TimeZoneId                                 invalid → PermanentFailure("InvalidTimeZone")
r = repo.GetAsync(user, reminderId)                          missing → NotApplicable()
if r.Status == Paused or (schedule occurrence and !r.Schedule.Includes(occurrenceLocal))
                                                             → NotApplicable()   -- edited/paused since discovery
type = NotificationTypeFor(r.Kind)
if !preferences.IsEnabled(type)                              → Succeeded(null, advance(Disabled))
switch r.Kind:                                             -- conditional cases = ReminderConditionEvaluator,
  Custom          → notify                                  -- reused unchanged by the send-time check (§6.6)
  HabitIncomplete → s = IHabitDayStatusReader.GetStatusAsync(user, r.HabitId, occurrenceDate)
                    notify ⇔ s is { IsActive: true, Status: Pending }
                             and (s.WeekTarget is null or s.WeekDone < s.WeekTarget)
                    -- Pending = scheduled today and neither Done nor Excused (HAB-001 §6.1); a
                    -- N-times-per-week habit already met this week is not nudged.
  HydrationGoal   → d = IHydrationDayReader.GetDaysAsync(user, occurrenceDate, occurrenceDate)[0]
                    notify ⇔ d.TargetMl != null and !d.IsTargetMet
return notify
  ? Succeeded(notification: new(type, ResourceTypeFor(r), ResourceIdFor(r)), saveArtifact: advance(Notified))
  : Succeeded(notification: null,                                         saveArtifact: advance(Suppressed))
```

`occurrenceDate` is the local date of the occurrence (for a snooze: the local date of
`snoozeUtc` in the occurrence zone), so a 23:50 nudge executed at 00:10 still evaluates its own day.

`advance(outcome)` = `ct => { await repo.AdvanceAsync(user, id, occurrence, outcome, now, ct); return true; }`
— uses the scoped DbContext inside the completion transaction (AUTO-001 WP3A `IUnitOfWork`).

### 6.4 Schedule maintenance during discovery

A candidate whose resolved occurrence is **expired** or **already terminal** would be rediscovered on
every tick. `AdvanceStaleAsync` moves it forward with one conditional statement per row:

```sql
UPDATE reminders
SET next_due_local = @next, status = @status, last_outcome = 'Missed', updated_at_utc = @now
WHERE id = @id AND next_due_local = @expected          -- a concurrent edit or completion wins
```

This is the only write in discovery; it touches only Reminders rows, is idempotent and bounded by
the same `limit`. (Alternative rejected: leaving stale rows and filtering in SQL — the key is computed
in .NET, so SQL cannot exclude them.)

### 6.6 Delivery-time relevance check (conditional reminders)

**Requirement.** A HabitIncomplete or HydrationGoal push must not reach a device if, at the moment
of sending, the habit is already Done, Excused or not scheduled, or the water target is already
met. The execution-time check (§6.3) is not enough on its own:
- the delivery is sent by Phase A of the same or a later tick;
- it can be retried for up to 3 h (10/30/60 min backoff);
- it can be deferred by quiet hours.

**Why this is an architectural change.** `NotificationDispatcher` is core (AUTO-001 §14) and must
not reference Reminders, Habits or Hydration. Today it sends every claimed delivery whose device is
active and that falls outside quiet hours. A module-aware gate therefore needs an
inversion-of-control seam, following the same pattern as `IAutomationHandler`.

**Alternatives.**

| | Option | Verdict |
|---|---|---|
| A | Cancel pending deliveries from Hydration/Habits writes ("goal met → cancel nudges") | Rejected: Hydration and Habits would have to know Reminders (a forbidden direction), and every write path (edit, delete, backdate) would need it |
| B | Only shorten the delivery expiry | Rejected: it narrows the stale window but does not remove it; quiet-hours deferral and retries still apply |
| **C** | **Core port consulted by the dispatcher right before `SendAsync`, implemented by Reminders** | **Chosen [Proposal]**: core stays module-agnostic; the check runs on every attempt; no new job or table |

**Design (C).**

```csharp
// LifeOS.Application/Notifications — core, references no module.
public interface INotificationRelevanceCheck
{
    // The notification types this check owns (HabitReminder, HydrationReminder).
    IReadOnlySet<NotificationType> Types { get; }

    // Read-only. False ⇒ the delivery is not sent. Exceptions are treated as transient failures.
    Task<bool> IsStillRelevantAsync(NotificationRelevanceContext context, CancellationToken ct);
}

public sealed record NotificationRelevanceContext(
    Guid UserId, NotificationType Type, string? ResourceType, Guid? ResourceId,
    string? SourceOccurrenceKey, DateTimeOffset NowUtc);
```

```text
NotificationDispatcher.ProcessAsync(item)            -- order of checks
  1. device still active?                 no  → Failed DeviceInactive          (unchanged)
  2. quiet hours?                         yes → Deferred / Expired             (unchanged)
  3. relevance check registered for item.Type?                                 (new)
       ctx.SourceOccurrenceKey = item.SourceOccurrenceKey  -- from the claim statement
       false → CompleteFailedAsync(NotRelevant)   -- terminal; nothing sent
       throw → transient path (CompleteRetryAsync / Failed per NotificationDeliveryPolicy)
  4. SendAsync                                                                 (unchanged)
```

- **Placement and frequency.** The check runs **after** quiet hours, so a deferred nudge is
  evaluated again when it is finally sent. It runs **once per device attempt**: at most 50 per
  tick, each costing 1–2 small indexed reads.
- **Reminders implementation.** `ReminderRelevanceCheck` (Application/Reminders):
  1. parses `SourceOccurrenceKey` with `ReminderOccurrenceKey`;
  2. loads the reminder; if it is missing or Paused, the delivery is not relevant;
  3. calls the **same** `ReminderConditionEvaluator` as `ExecuteAsync`, for the **occurrence date**
     rather than "today", so a nudge retried after midnight is judged on its own day.
- **Other types.** Without a registered check (Custom, Finance, Weekly Review, Test), behaviour is
  unchanged.
- **Core store change.** `NotificationDeliveryWorkItem` gains `SourceOccurrenceKey` (nullable). It
  is read in the existing claim statement through a `LEFT JOIN automation_executions` on
  `source_execution_id`, so Phase A adds no query for other types.
- **New error code.** `NotificationErrorCode` gains `NotRelevant`, a stable code. R5's migration
  widens `ck_notification_deliveries_last_error_code` to accept it.
- **Reminder outcome.** The reminder's `last_outcome` stays `Notified`, because the execution did
  produce the logical notification; the delivery row records the per-device outcome. Updating the
  reminder from the dispatcher was rejected because the check must stay read-only.
- **Residual window.** A goal met **during** the FCM call (a few seconds) can still produce a push.
  This is accepted.

This extends the AUTO-001 dispatcher additively; it adds no scheduler or queue. No new ADR is
proposed, because it applies the existing rule that modules plug into core through ports. R5 must
update AUTO-001 §11 to list the new dispatcher step.

## 11. Scheduler, Neon/Render cost (operations; not executed)

- **Current Production, as reported by the product owner:** the cron-job.org tick job runs
  **every 10 minutes, every day**, which is equivalent to `*/10 * * * *`. The owner showed this from
  the cron-job.org configuration. It has **not** been verified here, either from execution history or
  from `automation_executions` / `notification_deliveries` data. The runbook (Part F) and AUTO-001
  §18 still describe the original Stage 1 job (`*/10 * * * 0,1` UTC). Aligning those operational
  documents is outside this blueprint; the owner should do it once the configuration is verified.
- **Operational release gate (required before R4 reaches users in Production):**
  1. **Scheduler:** cron-job.org execution history shows 200 responses every 10 minutes on every
     day of the week, including at least one weekday and one night. The tick response or
     `automation_executions` confirms that Phase C runs.
  2. **Cost:** Neon compute hours and Render instance hours, measured over at least one full week
     at this cadence, stay within the plan allowances (**VERIFY** current Free limits). If not,
     choose one of the variants below before R4.
  3. **Delivery:** on a real phone, a Custom reminder at a weekday time arrives within ~20 min, and
     a quiet-hours deferral is released at the end of the quiet period. After R5, a HabitIncomplete
     nudge is suppressed when the habit is completed before the send (§6.6).
  4. Until the gate passes, the Reminders UI (R4) stays out of Production releases.
- **Correctness requirement** (cadence-independent engine): at least one tick in every
  `[due, due + lateness)` window (6 h Custom, 2 h nudges) and around quiet-hours ends.
  **Promptness** = tick interval: a 10-minute cadence means a reminder arrives 0–10 min (+ Phase A of
  the next tick, i.e. up to ~20 min) after its time. Precise-to-the-minute alarms are not a goal.
- **Cost driver:** every tick touches PostgreSQL and wakes Neon. With a 10-minute cadence all day, Neon
  compute would stay active for a large share of the day (it suspends only after an idle period —
  **VERIFY** the current Neon Free suspend delay and monthly compute allowance before choosing).
  Render: the tick wakes `lifeos-api` outside keepalive hours (07:00–22:50 Rome) — **VERIFY** the
  current Free instance-hour allowance.

| Cadence variant | Promptness | Wakes/day | Notes |
|---|---|---|---|
| `*/10 * * * *` UTC (**reported current**) | ≤ 10 min | 144 | simplest; highest Neon cost |
| **2a (first fallback if cost is too high):** `*/10` 06:00–23:59 Europe/Rome + hourly 00:00–05:00 | ≤ 10 min by day, ≤ 60 min at night | ~114 | night reminders are mostly inside default quiet hours anyway; lateness (≥ 2 h) still holds |
| `*/15` all day | ≤ 15 min | 96 | ~⅓ fewer wakes |
| `*/20` 07–23 + hourly night | ≤ 20 min | ~55 | cheapest acceptable for habits/water |

Any change of cadence is a cron-job.org change only; the endpoint and code stay identical. This
blueprint changes no schedule. **Release sequencing:**
- R1–R3 can reach Production safely: they have no UI, and their handlers are registered only when
  the tick key is configured, as in AUTO-003A.
- R4 (the Reminders UI) is released to Production only after the operational gate above has passed.
- R5 additionally requires the delivery-time check (§6.6) to be covered by tests and observed once
  on a phone.

Per-tick load: discovery is one zones query + one candidate query (index `ix_reminders_due`) + one
executions lookup per handler; ≤ 25 executions per tick shared with all handlers (AUTO-001 caps).

## 12. Failure, deduplication and late-tick behaviour

| Scenario | Behaviour |
|---|---|
| Two ticks at once | unique `(user, type, occurrence_key)`: one claim wins |
| Tick 3 h late, Custom (6 h lateness) | fires once, late; `next_due_local` advances |
| Tick 3 h late, nudge (2 h) | not fired; maintenance marks `Missed`, advances to next day |
| Outage of 3 days, daily reminder | fires once for today's occurrence (if within lateness); the 2 missed days are skipped, not replayed |
| Execution crash after claim | lease expires → retry (3 attempts) → completion advances; FailedFinal → maintenance advances |
| Condition read fails (DB hiccup) | exception → `Unhandled` retryable (10/30 min) inside lateness |
| FCM transient | per-device retry 10 min / 30 min / 1 h / 3 h within delivery expiry (24 h or 3 h) |
| Token invalid | that device Inactive; others unaffected (AUTO-001) |
| No active device | execution Succeeded with zero deliveries; reminder still advances (`Notified` — the logical notification was produced) |
| Quiet hours | delivery deferred without using an attempt; nudges expire if the quiet period outlasts 3 h |
| Goal met / habit done between enqueue and send (nudge) | relevance check before the send attempt (§6.6) ⇒ `Failed` / `NotRelevant`, no push, on every device |
| Goal met while a nudge is deferred by quiet hours or waiting for an FCM retry | re-checked at the next attempt ⇒ `NotRelevant` |
| Relevance check throws (DB hiccup) | transient path: retried with the normal delivery backoff inside the 3 h expiry; never sent unchecked |
| Goal met during the FCM call itself | push may still arrive (seconds-long residual window; accepted) |
| Reminder edited while its occurrence is Running | the in-flight occurrence completes (may notify); `Advance` keeps the user's new `next_due_local` |
| Reminder deleted after enqueue | Custom: delivery still sent; tap opens "Reminder not found" (normal not-found page). Nudge: relevance check finds no reminder ⇒ `NotRelevant` |
| Reminder paused after enqueue | Custom: still sent. Nudge: `NotRelevant` |
| Habit deleted | its HabitIncomplete reminders cascade (FK) |
| Habit archived | nudge evaluates `IsActive = false` → Suppressed every day; list shows "Paused — habit archived" |
| Same habit nudge and HydrationGoal both about water | two different reminders, two pushes possible; editor hints when both exist |
| User changes zone Rome → New York at 10:00 Rome | next `08:30` resolves in New York (wall-clock); `occurrence_key` uses the local date-time, so no duplicate key; at most one extra/one skipped occurrence on the travel day (documented) |
| DST spring-forward, reminder 02:30 | due at 03:30 CEST (gap rule); one occurrence |
| DST fall-back, reminder 02:30 | first 02:30 (CEST); key by local date-time ⇒ one occurrence |

discovery (D-3) is later reused by other modules (e.g. a Todo module), record it as an ADR-012
amendment at that time.

## 15. Privacy and security

- Push: fixed copy, data `{type, id}` only (opaque UUID); no title, note, habit name or amount ever
  reaches Google.
- Logs: reminder/execution/delivery ids, types, outcomes. Never titles or notes.
- Titles/notes are user free text: synthetic in tests, never sent to AI in v1.
- Ownership: `UserId` from the token only; habit references checked in Application and by composite FK.
- Abuse: ≤ 50 open reminders per user; snooze values fixed; per-tick caps of AUTO-001.
