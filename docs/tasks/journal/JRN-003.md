## Scope

The App screen that asks the existing Journal Memory endpoints ([AI-004](../ai/AI-004.md),
promoted by [AI-006.1](../ai/AI-006.1.md)) one question about the user's own journal. App only:
page, API client, flow helper, DI registration, App timeout, tests and this document.

Not changed: Domain, Application, Infrastructure, API endpoints, `LifeOS.Contracts` (the existing
`LifeOS.Contracts.Memory` DTOs are used as they are), SQL/migrations, `lifeos-ai`, prompts, models,
retrieval, eval datasets/scorers/gates, Journal CRUD, deployment. No new package or design system.

## Route and navigation

| Route | Page | Header Back |
| --- | --- | --- |
| `/journal/ask` | `Pages/Journal/AskJournal.razor` (title "Ask Journal") | `/journal` |

The timeline (`/journal`) shows **Ask Journal** next to **New entry**. Hierarchy:
More → Journal → Ask Journal. The dock and header are unchanged (`/journal…` keeps More active).

## User flow

1. Type a question (labelled "Your question", `length / 500` counter; blank or over 500 characters
   is rejected client-side, never truncated; the API stays authoritative).
2. **Ask** (disabled while busy) runs `JournalAskFlow` (`Services/Journal/JournalAskFlow.cs`):
   1. `GET api/journal/memory/status`;
   2. while `pendingEntries > 0`: "Preparing your journal..." with "N entries left to prepare.",
      `POST api/journal/memory/sync` with `{"limit": 3}`;
   3. when nothing is pending: "Searching your journal...", `POST api/journal/memory/ask`
      with `{"question": "<trimmed>"}`.
3. The result is shown; the question stays in the field for a follow-up or a retry.

One question at a time: no chat bubbles, history, threads, saved questions/answers, provider/model
selector or prompt editing.

## Index before ask

There is no background worker; Ask drives the existing explicit, bounded sync.

- **Batch:** `JournalAskFlow.SyncBatchSize = 3` per request (not 10), so each request stays well
  inside the App timeout (3 entries × about 53 s worst case per embedding request).
- **Progress rule:** a sync must index or stale-discard at least one entry **and** lower
  `pendingRemaining` below the previous pending count. Otherwise preparing stops.
- **Stops (retryable error, Ask is not called)** on: an API error (400/502/503/transport), a sync
  without progress (nothing claimed, all failed, pending not decreasing), or cancellation (leaving
  the page cancels the in-flight request; the flow ends quietly).
- **No infinite loop:** the pending count must strictly decrease each round.
- A sync with some `failed` entries but real progress continues; failed entries keep their 6-minute
  lease, so the next sync makes no progress and preparing stops with
  "Your journal could not be fully prepared right now. Try again in a few minutes."
- Ask is never sent against a knowingly incomplete index from this UI.

**Empty journal** (`indexedEntries = 0`, `pendingEntries = 0`): no special UI; the question is sent and
the backend's `insufficient_evidence` is shown (retrieval finds nothing, so no answer model call).

Create / edit / delete need nothing new: the backend already queues create/update and removes deleted
content. The next Ask prepares new or edited entries; deleted entries are neither searchable nor
citable. Journal saves do not call sync.

## App timeout

`ApiTimeouts.JournalMemory = 300 s` (finite), used only by `JournalMemoryApiClient`'s dedicated
authorized `HttpClient`. Ask = API wake (about 60 s) + query embedding + answer (each up to 120 s
in Production, AI-006.1 §6). `ApiTimeouts.Default` (90 s) and `ApiTimeouts.NutritionAi` (210 s) are
unchanged.

## API client

`Services/Journal/JournalMemoryApiClient.cs`, registered in `MauiProgram` as
`new JournalMemoryApiClient(CreateAuthorizedHttpClient(services, ApiTimeouts.JournalMemory))`: the
existing pipeline (`AuthorizationMessageHandler`: bearer token, single-flight refresh on 401,
session end). `JournalApiClient` is unchanged. The search endpoint is not used.

| Method | Call |
| --- | --- |
| `GetStatusAsync()` | `GET api/journal/memory/status` |
| `SyncAsync(limit)` | `POST api/journal/memory/sync` (`SyncJournalMemoryRequest`) |
| `AskAsync(question)` | `POST api/journal/memory/ask` (`AskJournalMemoryRequest`) |

Failures become `ApiResult` errors: 400 → the validation messages; 502/503 → the API's readable
ProblemDetails message; a bare status without ProblemDetails (e.g. a proxy 502) → "Ask Journal is
unavailable right now. Your journal is safe; try again later." (never a raw status code); network
errors / timeouts → the shared "Could not reach the LifeOS API…". Caller cancellation propagates.

## Results

- **answered:** "Answer" card with the text as returned (`white-space: pre-wrap`, wrapped).
- **insufficient_evidence:** "I couldn't find enough in your journal to answer that." Nothing else;
  the UI never builds an answer of its own.
- **Sources** (only when the API returned citations): each citation in API order, with its date/time
  (the timeline's `JournalDisplay.ListDateTime`, device local time), its title when present and its
  excerpt; the whole row links to `journal/{entryId}`. Score, vector/lexical rank, chunk ordinal,
  retrieval version and provider ids are never shown.
- **error:** the readable message with **Retry**, which reruns the whole flow (status → sync → ask)
  with the same question.
- An unknown answer status is an error, never an answer.

## Privacy

Question, answer, citations and excerpts live only in the page's `JournalAskFlow` instance (a new one
per page visit, not a DI singleton). They are not persisted (no Preferences/SecureStorage/storage/
files), not logged and not sent to analytics. The page does not name OpenAI (or any provider) and
does not suggest that data stays on the device. ADR-013 and the AI-006.1 §7.1 privacy acceptance
remain authoritative.

## Known limitation (unchanged)

AI-006 accepted one conservative over-refusal (`allergy-drops`): Ask Journal may answer
`insufficient_evidence` for medical instructions present in the journal. The UI shows it like any
other insufficient-evidence result: no special case, no retry, no prompt change.

## Post-deploy phone smoke

Run **after** this branch is merged, deployed and the app installed (not part of this task). Use
only the synthetic entry below.

**A. First entry**
1. Journal → New entry: title `Test Ask Journal`, content
   `Oggi ho lasciato le chiavi rosse nel cassetto della scrivania.` Save.
2. Journal → Ask Journal. Ask `Dove ho lasciato le chiavi rosse?`
3. Expect "Preparing your journal..." then "Searching your journal...".
4. Expect an answer mentioning the desk drawer (cassetto della scrivania) and a Source for
   "Test Ask Journal".
5. Tap the Source → the original entry opens.

**B. Insufficient evidence**
1. Ask `Qual è il numero di telefono di Marco?` (not in the journal).
2. Expect "I couldn't find enough in your journal to answer that.", no phone number, no Sources.

**C. Update**
1. Edit the synthetic entry's content to `Oggi ho lasciato le chiavi rosse nello zaino.` Save.
2. Ask `Dove ho lasciato le chiavi rosse?` again.
3. Expect preparing, then the backpack (zaino), not the desk drawer.

**D. Delete**
1. Delete the synthetic entry.
2. Ask `Dove ho lasciato le chiavi rosse?` again.
3. Expect insufficient evidence; the deleted entry is not a Source.

**E. Status / database after the smoke**
- `GET api/journal/memory/status`: `pendingEntries = 0`, `indexIncomplete = false`.
- Production SQL: index identity rows only `openai` / `text-embedding-3-small`.

**F. Logs** (`lifeos-api`, `lifeos-ai`): no journal text, question, generated answer, citation
excerpt, user id or API key.
