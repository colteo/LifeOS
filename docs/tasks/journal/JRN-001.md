# JRN-001 — Personal Journal Core

Status: IMPLEMENTED (backend only)

## Problem

LifeOS has no place for free-form personal writing. JRN-001 adds the backend
foundation of a private personal journal: a user-owned timeline of text
entries with an authenticated CRUD API. It is useful on its own and deliberately
contains no AI.

Scope: Domain, Application, Infrastructure (EF Core + migration), Contracts,
API, tests. **No App/UI** (JRN-002).

## Product semantics

`JournalEntry` (`LifeOS.Domain.Journal`):

| Field | Meaning |
| --- | --- |
| `Id` | GUID v7, generated by the Domain. |
| `UserId` | Owner. Always the authenticated user; never read from a request. |
| `OccurredAtUtc` | The instant the entry is **about** (the event or thought). Chosen by the user; may differ from `CreatedAtUtc` (back-dated or forward-dated entries are allowed). |
| `Title` | Optional. |
| `Content` | Required free text. |
| `CreatedAtUtc` | When the entry was written (Application clock, `TimeProvider`). Never changes. |
| `UpdatedAtUtc` | Set on create and on every successful update. |

Rules:

- **Content** is required; null, empty or whitespace-only is rejected. Outer
  whitespace is trimmed; internal text and line breaks are kept. At most
  **20 000** characters after trimming.
- **Title** is optional: null or blank means "no title" (stored as `NULL`).
  Outer whitespace is trimmed. At most **200** characters after trimming.
- **No silent truncation:** over-long text is rejected (400), never cut.
- **OccurredAtUtc** is required by the API. Any offset is accepted and stored
  as UTC. Like every journal timestamp it is truncated to whole microseconds
  (the precision PostgreSQL stores, same rule as `OpeningBalance.NormalizeAsOf`)
  so a value returned by a write equals the value read back. It must lie in
  `[0001-01-02, 9999-12-31)` UTC: Npgsql maps the `DateTimeOffset` endpoints to
  PostgreSQL ±infinity, which are not instants. No future-date restriction.
- **Update** replaces `OccurredAtUtc`, `Title` and `Content` (full replacement:
  an omitted/blank title removes it) and stamps `UpdatedAtUtc`. Owner and
  `CreatedAtUtc` never change. An invalid update changes nothing.
- **Delete is a hard delete.** No soft delete, no archive, no undo.
- Out of scope: tags, mood, attachments, categories, AI fields, embeddings,
  chunks, vector columns, semantic search.

## Schema

Migration `20261007160915_AddJournalEntries` (one new table, nothing else
changed):

```text
journal_entries
  id               uuid                      PK
  user_id          uuid NOT NULL             FK -> users(id) ON DELETE CASCADE
  occurred_at_utc  timestamptz NOT NULL
  title            varchar(200) NULL
  content          text NOT NULL
  created_at_utc   timestamptz NOT NULL
  updated_at_utc   timestamptz NOT NULL

PK_journal_entries                 (id)
ix_journal_entries_user_timeline   (user_id, occurred_at_utc DESC, created_at_utc DESC, id DESC)
FK_journal_entries_users_user_id   ON DELETE CASCADE
ck_journal_entries_content         length(btrim(content)) > 0 AND char_length(content) <= 20000
ck_journal_entries_title           title IS NULL OR length(btrim(title)) > 0
ck_journal_entries_occurred_at     occurred_at_utc >= '0001-01-02+00' AND occurred_at_utc < '9999-12-31+00'
```

- The timeline index matches the list order exactly, so a user's newest-first
  page (and every keyset continuation) is an index range scan with no sort.
- **User deletion** cascades to the user's journal (user-owned leaf data, same
  rule as weekly reviews, devices and sessions under ADR-006). No account-deletion
  feature exists yet; this only defines the FK semantics.
- Check constraints are a database backstop for the Domain rules.
- No vector/embedding/chunk columns.

The migration has **not** been applied to any remote database.

## API

All routes require authentication (`RequireAuthorization`; also listed in
`EndpointAuthorizationHttpTests`). The user id comes only from the access token;
request contracts have no user id (an extra `userId` JSON property is ignored).

| Method | Route | Success | Errors |
| --- | --- | --- | --- |
| `GET` | `/api/journal?limit=&cursor=` | 200 `JournalEntryPageResponse` | 400 `limit` / `cursor` |
| `GET` | `/api/journal/{id}` | 200 `JournalEntryResponse` | 404 |
| `POST` | `/api/journal` | 201 `JournalEntryResponse` + `Location` | 400 `occurredAtUtc` / `title` / `content` |
| `PUT` | `/api/journal/{id}` | 200 `JournalEntryResponse` | 400 (as POST), 404 |
| `DELETE` | `/api/journal/{id}` | 204 | 404 |

Contracts (`LifeOS.Contracts.Journal`):

```text
CreateJournalEntryRequest(DateTimeOffset? OccurredAtUtc, string? Title, string? Content)
UpdateJournalEntryRequest(DateTimeOffset? OccurredAtUtc, string? Title, string? Content)
JournalEntryResponse(Guid Id, DateTimeOffset OccurredAtUtc, string? Title, string Content,
                     DateTimeOffset CreatedAtUtc, DateTimeOffset UpdatedAtUtc)
JournalEntryPageResponse(IReadOnlyList<JournalEntryResponse> Items, string? NextCursor)
```

Validation failures are `ValidationProblem` (400) keyed by the request field.

### Ownership

Every repository query filters by `user_id`. Another user's entry is
indistinguishable from a missing one: `GET`, `PUT` and `DELETE` return the same
404 problem ("Journal entry not found.") and nothing is changed.

## Pagination

Keyset (cursor) pagination, following the existing LifeOS convention
(Gym workout history, weekly reviews):

- `limit`: 1–50, default 20; outside the range → 400 `limit`.
- Order: `occurred_at_utc DESC, created_at_utc DESC, id DESC` (total and
  deterministic: `id` is unique).
- The handler fetches `limit + 1` rows to know whether another page exists.
  `NextCursor` is the last item's `(OccurredAtUtc, CreatedAtUtc, Id)` triple,
  `null` on the last page.
- Cursor text is opaque to clients: `"<occurredAt UTC ticks>_<createdAt UTC ticks>_<id:N>"`.
  A malformed cursor → 400 `cursor` ("Start again from the first page.").
- The next page is rows strictly after the cursor in timeline order. Entries
  added or edited while paging never make later pages repeat or skip rows that
  were not themselves moved.

## Tests

- Unit (`LifeOS.UnitTests.Journal`): Domain rules (create, optional title,
  required content, limits without truncation, UTC/µs normalization, timestamp
  range, update, invalid update atomicity) and handlers (create, get, update,
  hard delete, ownership, timeline order and tie-breaks, page walking, page
  size bounds, stability while paging).
- PostgreSQL (`JournalPersistenceTests`): migration/schema (columns, index
  definition, FK cascade, checks, no pending model changes), check constraints,
  round trip, ownership, update/delete, keyset paging with PostgreSQL's own
  ordering, timeline index use without sort, user cascade.
- HTTP (`JournalHttpTests`): authentication on every route, CRUD, ordering,
  validation fields, ignored `userId`, cross-user 404 identical to missing,
  pagination with `limit`/`cursor` and invalid values.
- Architecture (`JournalModuleArchitectureTests`): the Journal namespaces of every
  layer depend on no other business module and not on `System.Net.Http`.
