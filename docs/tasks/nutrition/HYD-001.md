## 1. Problem

LifeOS records meals (NUT-001) and nutrition targets (NUT-003) but not water. The question to answer:

> "How much water have I drunk today, and am I at my target?"

The answer must be quick to record (one tap for the common case), correct across days and time
zones, editable afterwards, and reusable by Habits and Reminders **without anyone else storing water
amounts**.

## 2. Given decisions

| # | Decision |
|---|---|
| G-1 | **[Given]** Hydration is the **single source of truth** for water consumed, in **millilitres**. |
| G-2 | **[Given]** Habits and Reminders reuse the Hydration data **without duplicating it** ("never triple-store one intake"). |
| G-3 | **[Given]** Every module is potentially available to every user; activation and preferences are per user. |
| G-4 | **[Given]** Deterministic, .NET-owned writes, per-user isolation, UTC persistence of instants. No LLM in v1. |
| G-5 | **[Given]** Hydration lives under Nutrition (`docs/tasks/nutrition/`). |
| G-6 | **[Given]** No Cycle Tracker, no medical predictions, no new infrastructure. |

## 3. Proposed product decisions

| # | Decision | Default / reason |
|---|---|---|
| P-1 | **[Proposal]** One **intake event** per drink: amount (ml, integer) + local diary date + local time + UTC instant. Totals are always computed (`SUM`), never stored. | Same shape as `meal_entries` (NUT-001), so day semantics are identical across Nutrition. No counter column that could drift. |
| P-2 | **[Proposal]** Amount: integer **1–4000 ml** per intake. No daily cap. | 4000 ml covers any real container (a 1.5 l bottle, a 3 l jug) and still catches a typo like `25000`. A daily cap would reject legitimate hot-day totals. |
| P-3 | **[Proposal]** Storage unit is **ml only**. Display: `250 ml` below 1000, `1.25 l` from 1000. No fl oz in v1. | Metric user base; a second unit is display-only and can be added without migration (open question Q-1). |
| P-4 | **[Proposal]** **Daily target = open-ended versions effective from a date** (`hydration_target_versions`). Setting/changing/removing a target takes effect **from local today**; past days keep the target they had. | See §6 alternatives. A water goal is a stable everyday setting, not a bounded plan; past adherence must not change because today's target changed. |
| P-5 | **[Proposal]** Target bounds **250–10000 ml**; "no target" is an explicit version (`target_ml = NULL`). | Explicit removal keeps history readable ("no target from 3 Nov"). |
| P-6 | **[Proposal]** **Three quick-add amounts** per user, default **150 / 250 / 500 ml**, editable. Plus "Custom amount". | One tap for a glass/cup/bottle. Three fits the Home card and the diary at 360dp. |
| P-7 | **[Proposal]** **Undo** after quick add = `DELETE` of the intake just created (snackbar, 6 s). No soft delete. | Mistaken taps are the main error; a real delete keeps the model simple. |
| P-8 | **[Proposal]** Edit = amount and time only; an intake never moves to another diary day (as NUT-001 meals). Delete with inline confirmation (not for Undo). | Moving across days is rare and complicates audit; delete + re-add covers it. |
| P-9 | **[Proposal]** Over target is fine and neutral: `2750 / 2000 ml · 138%`. No warnings, no colours that judge, no health advice. | NUT-003 neutral-copy principle; no medical claims. |
| P-10 | **[Proposal]** Auditability = `created_at_utc` / `updated_at_utc` per intake, append-mostly table, no revision log in v1. | Personal data minimisation; edits are user corrections, not a compliance trail. Revision log listed as deferred. |
| P-11 | **[Proposal]** No module activation flag. Hydration is visible to everyone in Nutrition; the Home card appears only when the user has a current target **or** an intake today. | Activation is derived from the user's own data: zero clutter for non-users, zero setup for users (G-3). |
| P-12 | **[Proposal]** Hydration exposes **one read port** to other modules (`IHydrationDayReader`), and nothing else. Hydration references no Habits or Reminders type. | G-2 by construction: consumers read totals/targets through a port; they cannot write or cache water data. |

### 4.1 Screens (MAUI Blazor Hybrid)

Information architecture follows NUT-003: **operational, per-day actions on the Food diary; cross-day
configuration on Targets.**

```text
More → Nutrition (hub)
        ├── Food diary   /nutrition          ← adds a "Water" section for the selected day
        └── Targets      /nutrition/targets  ← adds a "Water" section: daily target, quick-add amounts
Home   → Hydration card (only when target or intake today)
Dock   → unchanged (Home | Transactions | + | Nutrition | More)
"+"    → quick-add panel gains "Water" → /nutrition?add=water  (PR H4, optional)
```

**Food diary → Water section** (below Target, above Meals):

```text
Water                                         Remind me
1250 / 2000 ml                                    63%
[██████████████░░░░░░░░]
[ + 150 ml ] [ + 250 ml ] [ + 500 ml ] [ Custom ]

08:10   250 ml                                       ⋮
10:45   500 ml                                       ⋮
13:20   500 ml                                       ⋮
Last 7 days                                         >
```

- No target → `1250 ml today` and no bar/percentage.
- Empty day → "No water logged today." / "No water logged on this day." with the quick-add row.
- Quick-add on a past day: time defaults to 12:00 (NUT-001 convention), with the amount; the
  buttons log immediately and the row can be edited.
- ⋮ → Edit (amount, time) / Delete (inline confirmation). One open panel at a time (NUT-001).
- "Remind me" appears only when push is available and opens the REM-001 editor pre-filled
  (`kind = HydrationGoal`). Hidden when a HydrationGoal reminder exists → shows "Reminder 17:00".
- "Last 7 days" expands inline: seven rows `Mon 13 · 1800 / 2000 ml`, then `Met 4 of 6 days with a
  target · avg 1720 ml`.

**Targets → Water section**:

```text
Water
Daily target            [ 2000 ] ml          (or "No daily target")
Applies from today. Past days keep their target.
Quick add               [ 150 ] [ 250 ] [ 500 ] ml
                                        [ Save water settings ]
```

**Home → Hydration card**: `Water · 1250 / 2000 ml` + bar + the three quick-add buttons + Undo
snackbar. Tapping the title opens `/nutrition` (today).

### 4.2 Accessibility

- Quick-add buttons have accessible names "Add 250 millilitres of water"; touch targets ≥ 48dp.
- The progress bar is `role="progressbar"` with `aria-valuenow`/`aria-valuemax` (ml) and a text
  equivalent; progress is never conveyed by colour alone.
- Total updates are announced through an `aria-live="polite"` region ("Water today 1500 of 2000
  millilitres").
- Undo snackbar is focusable and stays ≥ 6 s; it pauses while focused.
- Works with system font scaling up to 200% (rows wrap, no truncated numbers).

## 5. Domain model and invariants

Namespace `LifeOS.Domain.Nutrition.Hydration`.

```text
HydrationIntake                         (entity)
- Id                Guid v7 (Domain)
- UserId            Guid, required
- AmountMl          int, 1..4000
- DiaryDate         DateOnly            local calendar day — authoritative for grouping
- DiaryTime         TimeOnly            whole minutes — authoritative for display/order
- OccurredAtUtc     DateTimeOffset      = (DiaryDate + DiaryTime) − utcOffset, |offset| ≤ 14 h
- CreatedAtUtc, UpdatedAtUtc            supplied by Application (TimeProvider)

  Create(userId, amountMl, date, time, utcOffsetMinutes, nowUtc)
  Update(amountMl, time, nowUtc)        keeps DiaryDate and the original offset (NUT-001 rule)

HydrationTargetVersion                  (entity, PK user + effective date)
- UserId, EffectiveFrom DateOnly
- TargetMl          int? (250..10000; null = no target from this date)
- CreatedAtUtc

HydrationTargetSchedule                 (pure domain service over a user's versions)
- TargetOn(date) → int?                 latest version with EffectiveFrom ≤ date; none → null

HydrationSettings                       (optional row; Default(userId) when absent)
- UserId, QuickAddMl[3] (each 1..4000), UpdatedAtUtc

HydrationDay                            (value object, computed, never persisted)
- Date, TotalMl (≥ 0), TargetMl?, IsTargetMet (TargetMl != null && TotalMl ≥ TargetMl),
  ProgressPercent? (floor(TotalMl × 100 / TargetMl), may exceed 100)
```

Invariants (Domain unit tests):

1. `AmountMl` is an integer in `[1, 4000]`. Zero and negatives are rejected (a "zero intake" is
   never stored; a day with no intakes has `TotalMl = 0`).
2. `DiaryTime` has whole minutes; `|offset| ≤ 14 h` (same check as `meal_entries`).
3. `Update` never changes `DiaryDate`; changing the time recomputes `OccurredAtUtc` with the
   original offset.
4. A target value is in `[250, 10000]` or explicitly null.
5. At most one target version per `(user, effective date)`; saving again on the same date replaces it.
6. `TargetOn(date)` for a date before the first version is null (no target), never the first value.
7. `IsTargetMet` is false when there is no target, regardless of the total. Over-target is still
   "met".
8. Quick-add amounts: exactly three, each in `[1, 4000]`; duplicates allowed.

## 6. Target model — alternatives and recommendation

| | A. Reuse NUT-003 plans (add `water_ml` metric) | **B. Open-ended versions (recommended)** | C. Single value, retroactive |
|---|---|---|---|
| Shape | bounded periods + weekday rules + overrides | `(effective_from, target_ml?)` rows | one column on settings |
| Typical use "2 l every day" | must create a period with an end date; gaps → no target | one row, forever | one value |
| Past days after a change | keep (period-based) | keep | **rewritten** (adherence and habit streaks change) |
| Weekday variations | yes | no (deferred, Q-3) | no |
| Ownership | water target would live in NUT-003 tables, outside Hydration | Hydration owns its target | Hydration |
| Complexity | high (overlap trigger, overrides) for a single number | low | lowest |

**Recommendation B.** It is the smallest model that keeps history stable, which HAB-001 needs (a
hydration habit's past days must not flip when today's target changes). NUT-003 plans stay
calorie/macro-only. Weekday-specific water targets are a deferred improvement that B can grow into
(an optional weekday column) without migration of existing rows.

Rule for edits: the API derives `effectiveFrom = local today` from `utcOffsetMinutes`; the client
cannot choose a past date (no retroactive rewrite) or a future date (v1 simplicity; Q-4).

## 7. Application use cases

Namespace `LifeOS.Application.Nutrition.Hydration`. Plain handler classes (no mediator), explicit
`UserId` on every call (ADR-006), `TimeProvider` for "now".

| Use case | Behaviour |
|---|---|
| `AddHydrationIntakeHandler` | validate, `HydrationIntake.Create`, persist, return the intake + the updated `HydrationDay` |
| `UpdateHydrationIntakeHandler` | own intake only (else NotFound); `Update`; return intake + day |
| `DeleteHydrationIntakeHandler` | own intake only; delete; return the updated day (used by Undo) |
| `GetHydrationDayHandler` | intakes of one date (time DESC, id DESC) + `HydrationDay` |
| `GetHydrationDaysHandler` | `HydrationDay` per date in `[from, to]` (≤ 92 days), zeros for empty days, plus the summary (days with target, days met, average total) |
| `GetHydrationSettingsHandler` | current target (today), quick-add amounts (defaults when no row) |
| `SetHydrationTargetHandler` | upsert version `(user, today)`; `targetMl = null` removes the target from today |
| `SetHydrationQuickAddHandler` | upsert settings row |

### 7.1 Ports

```csharp
// Hydration's own persistence (user-scoped; Infrastructure implements with EF Core).
public interface IHydrationRepository
{
    Task AddAsync(HydrationIntake intake, CancellationToken ct);
    Task<HydrationIntake?> GetAsync(Guid userId, Guid intakeId, CancellationToken ct);
    Task SaveAsync(HydrationIntake intake, CancellationToken ct);
    Task<bool> DeleteAsync(Guid userId, Guid intakeId, CancellationToken ct);
    Task<IReadOnlyList<HydrationIntake>> GetForDateAsync(Guid userId, DateOnly date, CancellationToken ct);
    Task<IReadOnlyDictionary<DateOnly, int>> GetDailyTotalsAsync(Guid userId, DateOnly from, DateOnly to, CancellationToken ct);
    Task<IReadOnlyList<HydrationTargetVersion>> GetTargetVersionsAsync(Guid userId, DateOnly upTo, CancellationToken ct);
    Task UpsertTargetVersionAsync(HydrationTargetVersion version, CancellationToken ct);
    Task<HydrationSettings> GetSettingsAsync(Guid userId, CancellationToken ct);   // Default when absent
    Task UpsertSettingsAsync(HydrationSettings settings, CancellationToken ct);
}

// The ONLY surface other modules (Habits, Reminders) may use. Read-only, computed, no caching.
public interface IHydrationDayReader
{
    // One HydrationDay per date in [from, to], inclusive; empty dates have TotalMl = 0.
    Task<IReadOnlyList<HydrationDay>> GetDaysAsync(Guid userId, DateOnly from, DateOnly to, CancellationToken ct);
}
```

`IHydrationDayReader` is implemented in Application by a small class over `IHydrationRepository`
(`GetDailyTotalsAsync` + `GetTargetVersionsAsync` + `HydrationTargetSchedule`), so the derivation
rule ("met" = total ≥ that date's target) exists exactly once.

### 7.2 Pseudocode — day computation

```text
GetDaysAsync(user, from, to):
  totals   = repo.GetDailyTotalsAsync(user, from, to)            -- one GROUP BY diary_date
  versions = repo.GetTargetVersionsAsync(user, upTo: to)          -- tiny: one row per change
  schedule = HydrationTargetSchedule(versions)
  return [ HydrationDay(d, totals.GetValueOrDefault(d, 0), schedule.TargetOn(d)) for d in from..to ]
```

## 8. API contracts

All routes authenticated, user-scoped, another user's intake = 404 (ADR-006). Dates `yyyy-MM-dd`,
times `HH:mm`. Enum-like values are strings. Contracts in `LifeOS.Contracts.Nutrition.Hydration`.

| Route | Result |
|---|---|
| `GET /api/nutrition/hydration/days/{date}` | 200 `HydrationDayResponse` (with intakes); 400 bad date |
| `GET /api/nutrition/hydration/days?from=&to=` | 200 `HydrationRangeResponse`; 400 (missing, from > to, > 92 days) |
| `POST /api/nutrition/hydration/intakes` | 201 `HydrationIntakeMutationResponse`; 400 |
| `PUT /api/nutrition/hydration/intakes/{id}` | 200 `HydrationIntakeMutationResponse`; 400; 404 |
| `DELETE /api/nutrition/hydration/intakes/{id}` | 200 `HydrationDaySummaryResponse` (updated day); 404 |
| `GET /api/nutrition/hydration/settings?date=` | 200 `HydrationSettingsResponse` (target on `date`, quick-add) |
| `PUT /api/nutrition/hydration/target` | 200 `HydrationSettingsResponse`; 400 |
| `PUT /api/nutrition/hydration/quick-add` | 200 `HydrationSettingsResponse`; 400 |

`DELETE` returns 200 with the day (not 204) so Undo can refresh the total without a second request.

`averageTotalMl` = integer mean over **all** days of the range (empty days count as 0), so the number
does not depend on whether the user logged at all. Rounded half away from zero.

```http
PUT /api/nutrition/hydration/target
{ "targetMl": 2500, "utcOffsetMinutes": 120 }          // or { "targetMl": null, ... }
PUT /api/nutrition/hydration/quick-add
{ "amountsMl": [200, 330, 750] }
```

Validation failures are field-keyed ProblemDetails (`amountMl`, `date`, `time`, `utcOffsetMinutes`,
`targetMl`, `amountsMl[1]`) as in NUT-003.

**Future dates:** `POST` rejects `date` later than the caller's local today
(`(utcNow + utcOffsetMinutes).Date`) with 400 "Water can't be logged for a future day." Past dates
are unrestricted (backdating is a correction, P-8).

## 9. Persistence and migration (proposal only)

Migration `AddHydration` (one migration, generated with EF tooling after the latest migration on
`main` at implementation time; no change to existing tables):

```text
hydration_intakes
- id               uuid         PK (UUID v7, Domain)
- user_id          uuid         → users(id) ON DELETE RESTRICT        (Nutrition convention)
- amount_ml        integer      ck_hydration_intakes_amount  1..4000
- diary_date       date         ck_hydration_intakes_diary_date (finite)
- diary_time       time         ck_hydration_intakes_diary_time (whole minutes)
- occurred_at_utc  timestamptz  ck_hydration_intakes_utc_offset (within ±14 h of date + time)
- created_at_utc   timestamptz
- updated_at_utc   timestamptz
- ix_hydration_intakes_user_diary (user_id, diary_date, diary_time DESC, id DESC)

hydration_target_versions
- user_id          uuid         → users(id) ON DELETE RESTRICT
- effective_from   date
- target_ml        integer NULL ck_hydration_target_versions_target (NULL or 250..10000)
- created_at_utc   timestamptz
- PK (user_id, effective_from)

hydration_settings                          (optional row; no row ⇒ defaults 150/250/500)
- user_id          uuid PK      → users(id) ON DELETE RESTRICT
- quick_add_1_ml, quick_add_2_ml, quick_add_3_ml  integer  ck 1..4000
- updated_at_utc   timestamptz
```

- No `total` column anywhere; no water column in any Habits or Reminders table (G-2).
- Daily totals: `SELECT diary_date, SUM(amount_ml) … GROUP BY diary_date`, index-only range scan on
  `ix_hydration_intakes_user_diary`.
- Down drops the three tables only. Idempotent script verified as non-superuser (runbook rule: no
  extensions).
- Splitting into two migrations (intakes in H1, targets/settings in H2) is acceptable if the PRs
  ship separately; each Down then drops only its own tables.

## 10. Integration with Habits and Reminders

```text
           ┌──────────────────────────── writes ───────────────────────────┐
  App ─────┤ POST/PUT/DELETE /api/nutrition/hydration/...                  │
           └─────────────────────────────┬─────────────────────────────────┘
                                         ▼
                         Hydration (Application/Nutrition/Hydration)
                         hydration_intakes · hydration_target_versions
                                         │  IHydrationDayReader (read-only)
                     ┌───────────────────┴───────────────────┐
                     ▼                                       ▼
        Habits: Hydration-sourced habit          Reminders: HydrationGoal condition
        "done on D" ⇔ day(D).IsTargetMet         "notify" ⇔ day(D).TargetMl != null && !day(D).IsTargetMet
        (nothing stored)                         D = occurrence date; checked at execution AND
                                                 again right before each send (REM-001 §6.6)
                                                 (nothing stored)
```

- Hydration never references Habits or Reminders (architecture test).
- An intake logged after a HydrationGoal nudge has been queued, but before it is sent, prevents the
  push: Reminders reads the new total through `IHydrationDayReader` right before sending. Hydration
  itself does nothing for this.
- A hydration edit/delete on a past day changes the derived habit status of that day immediately,
  because nothing is cached. This is intended: Hydration is the truth.

### 11.1 Edge cases

| Case | Expected |
|---|---|
| Two quick taps | two intakes (buttons disabled while a request is in flight; Undo removes the last) |
| Network timeout after server commit | user may see an error and retry → duplicate; visible in the list, deletable. Idempotency key deferred (§15) |
| Device zone changes mid-day | intakes keep their diary date; "today" follows the device (NUT-001) |
| Logging at 00:05 for the previous evening | navigate to yesterday first (diary semantics); quick add on Home always logs today |
| Target removed today, met yesterday | yesterday still met; today shows total only |
| Very large day (40 × 250 ml) | 10 000 ml, 500%; no warning, no cap |
| Intake deleted on a day a habit counted as done | that habit day becomes Missed/Pending on next read (HAB-001 §6.5) |

## 13. Risks and cost

- **Neon/Render:** Hydration adds no scheduled work and no tick load. Requests only on user action.
- **Privacy:** water intake is personal health-adjacent data: synthetic data only in tests/fixtures;
  never in logs or push copy (REM-001 copy contains no amounts).
- **Retroactive habit changes** after editing past intakes are intended (§10) — documented in the
  HAB-001 UI copy.
