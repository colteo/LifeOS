# NUT-001 — Text meal journal foundation

Status: IMPLEMENTED

> The dock statements below predate [NAV-001](../app/NAV-001.md): the Food diary
> now has its own **Nutrition** dock item, and More is active only on the
> Nutrition hub and Targets.

## Problem

LifeOS has no Nutrition capability. The first question to answer is simply:

> "What did I eat today?"

NUT-001 adds a daily, chronological, free-text meal journal. It is useful on
its own, with no AI and no nutrition calculations.

## Product decisions

- **One `MealEntry` is the whole meal.** Its description is free text and may
  name several foods naturally ("200 g grilled chicken, basmati rice, zucchini
  and one tablespoon of olive oil"). Nothing is parsed or split.
- **Description:** required; outer whitespace trimmed; internal text and line
  breaks preserved; at most **2000** characters (after trimming).
- **Meal type is optional** organizational metadata: `Breakfast`, `Lunch`,
  `Dinner`, `Snack`, `Other`, or none (unclassified). It never decides order and
  the journal is never grouped into Breakfast/Lunch/Dinner sections.
- **Order:** newest first within a diary day — `time DESC, id DESC`
  (deterministic tie-breaker). Enforced by the Application use case and the
  repository query (index-backed), not only by the UI.
- **Time:** required, whole minutes (as entered in the app).
- **No nutrition data:** no calories, macros, fibre, micronutrients, targets,
  servings or estimates. No empty nutrition dashboards.
- **No AI:** no model calls, no parsing, no classification (NUT-002).
- **No food database:** no Food/Ingredient/Recipe/Serving/Portion entities and
  no reuse of previously typed meals.

## Time / diary-date semantics

A meal belongs to the calendar day on which the user recorded it. If the device
time zone later changes, a historical meal must not move to another diary day.

### Chosen representation

| Column | Type | Meaning |
| --- | --- | --- |
| `diary_date` | `date` | The local calendar day the meal belongs to. **Authoritative for grouping.** |
| `diary_time` | `time` | The local wall-clock time the user recorded (e.g. 13:10). **Authoritative for display and ordering.** |
| `occurred_at_utc` | `timestamptz` | The real instant, in UTC (AGENTS.md: persist instants in UTC). |

On create the app sends the diary date, the local time and the device's UTC
offset (minutes) for that wall-clock time. The Domain derives
`occurred_at_utc = (diary_date + diary_time) − offset`. The offset itself is not
stored: it is always `(diary_date + diary_time) − occurred_at_utc`, and a check
constraint keeps it within ±14 hours.

Why this is the smallest clean model:

- The diary is queried and ordered by **stored local values**, never by
  converting UTC with the *current* device zone, so a later time-zone change
  cannot move a meal between days or reorder it. `GET` takes only a date.
- The real instant is still stored in UTC for future features (NUT-002,
  analytics) and is consistent with the repository-wide rule.
- No time-zone framework, no IANA zone storage.

On **edit**, the meal stays on its diary day (NUT-001 does not move meals
between days) and keeps the UTC offset it was recorded with; changing the time
recomputes `occurred_at_utc` with that original offset. So editing a meal later
from another time zone does not change what instant the meal refers to beyond
the explicit time change.

This is local to the Nutrition module and needs no ADR.

## Data model

```text
meal_entries
- id               uuid         PK (UUID v7, Domain)
- user_id          uuid         → users(id) ON DELETE RESTRICT
- description      text         1..2000 chars, not blank (ck_meal_entries_description)
- meal_type        varchar(16)  NULL | Breakfast | Lunch | Dinner | Snack | Other (ck_meal_entries_meal_type)
- diary_date       date         finite (ck_meal_entries_diary_date)
- diary_time       time         whole minutes (ck_meal_entries_diary_time)
- occurred_at_utc  timestamptz  within ±14 h of diary_date + diary_time (ck_meal_entries_utc_offset)
- created_at_utc   timestamptz
- updated_at_utc   timestamptz
- ix_meal_entries_user_diary: (user_id, diary_date, diary_time DESC, id DESC)
```

## API

All endpoints require authentication and are scoped to the caller. Another
user's meal is indistinguishable from a missing one (404).

| Route | Result |
| --- | --- |
| `GET /api/nutrition/meals?date=2026-10-03` | 200 `MealResponse[]`, newest first; 400 when `date` is missing or not `yyyy-MM-dd` |
| `POST /api/nutrition/meals` `{description, mealType?, date, time, utcOffsetMinutes}` | 201 `MealResponse`; 400 |
| `PUT /api/nutrition/meals/{id}` `{description, mealType?, time}` | 200 `MealResponse`; 400; 404 |
| `DELETE /api/nutrition/meals/{id}` | 204; 404 |

`mealType` is a case-insensitive name or null/empty (none). Numbers and unknown
names are 400. `MealResponse` is
`{id, description, mealType?, date, time, occurredAtUtc, createdAtUtc, updatedAtUtc}`.

## App

- **More → Modules:** Finance, Gym, **Nutrition** ("Meal journal",
  fork-and-knife icon). Not in the dock, not on Home.
- **Dock:** still `Transactions | + | More`; More is active on `/nutrition`
  and `/nutrition/*`.
- **`/nutrition`:** `Nutrition … < Back` (to More); a day navigator
  (`<  Today  >`, other days as "2 October 2026"; the next arrow stops at
  today); **Meals** section title with **+ Add meal** on the same row.
- **Add meal** opens inline: "What did you eat?" (multi-line), Meal type
  (Optional), Time (today: current local time; other days: 12:00), Add meal /
  Cancel. The diary date is the day being viewed.
- **Meal row:** "13:10 · Lunch" (or just "13:10"), then the full description,
  wrapped, with line breaks kept; ⋮ opens Edit / Delete inline below the row.
  One panel or form is open at a time. Delete asks for confirmation inline.
- **States:** loading, "No meals logged today." / "No meals logged on this
  day.", readable errors with Retry. Changing day closes any open form.
