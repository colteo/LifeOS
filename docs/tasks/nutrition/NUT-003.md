# NUT-003 — Manual nutrition targets

Status: IMPLEMENTED — offline validation passed; phone acceptance pending

Builds on NUT-001 (text meal journal) and NUT-002 (on-demand AI nutrition estimation).

## Principle

The user decides optional **daily targets** by hand: calories (kcal), protein, carbohydrates
and fat (g). Any combination is valid: calories only, protein only, calories + protein, all four,
or none.

This is **not** diet coaching, a recommendation, a meal plan or a calorie prescription. NUT-003
never calls AI, never infers a target (from meals, body data or training), and never judges a day.
The day's totals are compared with its target as plain numbers (`1840 / 2200 kcal`).

## Time rule: effective from today, never retroactive

A target applies **from the day it is saved forward**, until the next change.

```text
1 Oct   set   2200 kcal / 160 P / 240 C / 70 F
18 Oct  set   2400 kcal / 170 P / 260 C / 75 F
25 Oct  Remove targets

1–17 Oct   first target
18–24 Oct  second target
25 Oct →   no targets
```

Past days always keep the target that was effective on them. Targets are never copied onto days and
never recalculated. There is no way to set a target for a past or future day: the client never sends
an effective date (a stray `effectiveFrom` in the body is ignored).

### Which day is "today"

The same rule as the NUT-002 lazy close (`NutritionDays.TryGetLocalToday`):

```text
today = date( server UTC clock  shifted by  the device's current utcOffsetMinutes )
```

The client sends its current offset (`DateTimeOffset.Now.Offset`, minutes east of UTC, ±840); the
server derives the day from its own `TimeProvider`. The server's UTC date is never used as the
user's day: at 22:30 UTC on 3 October a UTC+2 device saves a target effective 4 October.

## Data model

History/event style; nothing is stored on the user row.

```text
nutrition_targets
- id              uuid          PK (UUID v7, Domain)
- user_id         uuid          → users(id) ON DELETE RESTRICT
- effective_from  date          ck_nutrition_targets_effective_from (no ±infinity)
- calories_kcal   numeric(6,1)  NULL, or > 0 and ≤ 10000
- protein_grams   numeric(5,1)  NULL, or > 0 and ≤ 1000
- carbs_grams     numeric(5,1)  NULL, or > 0 and ≤ 1000
- fat_grams       numeric(5,1)  NULL, or > 0 and ≤ 1000   (ck_nutrition_targets_values)
- source          varchar(32)   'Manual'                   (ck_nutrition_targets_source)
- created_at_utc  timestamptz
- updated_at_utc  timestamptz
UNIQUE (user_id, effective_from)  ux_nutrition_targets_user_effective_from
```

Migration `20261004134218_AddNutritionTargets` (EF tooling, after `AddMealNutritionSnapshots`): one
new table; `meal_entries` and `meal_nutrition_snapshots` are unchanged. Down drops only
`nutrition_targets`.

The unique index is also the lookup index: the effective target for a date is

```sql
SELECT … FROM nutrition_targets
WHERE user_id = @user AND effective_from <= @date
ORDER BY effective_from DESC LIMIT 1
```

### The "no targets" state

Remove targets writes a state whose four metrics are **all null**. That row is the explicit "no
targets from this day" marker; earlier rows stay and keep applying to their days. Lookup: no row on
or before the date → no target; latest row is all-null → no target. No row is ever deleted.

All-null is reserved for this explicit action: Set targets with every field empty is rejected (form,
API and Domain), and the user is pointed to **Remove targets** instead.

### Values

- `null` = that metric is not targeted.
- A present value must be **more than 0** (zero is rejected, not "no target") and at most
  10000 kcal / 1000 g per macro (daily amounts; same bounds in spirit as `MealNutritionSnapshot`).
- One decimal place, rounded half away from zero in the Domain (`NutritionTargetValues`), so 0.04
  rounds to 0.0 and is rejected. The UI shows whole numbers.
- At least one metric is required for an active target.

### Source (future-proofing only)

`NutritionTargetSource` is stored by name (`varchar(32)`), today with one value: `Manual`. Later
origins (e.g. `AiProposed`, `ProfessionalProvided`, `Imported`) can be added as enum values plus a
widened check constraint, without changing existing rows. Nothing in NUT-003 produces any other
source.

## Same-day edits

At most **one state per user per effective date**, enforced by the unique index. Saving again on
the same day (Set or Remove) replaces today's state in place: same id and creation time, new values
and `updated_at_utc`. Earlier days are untouched. Remove when no target is active today writes
nothing.

### Concurrency

Every save is one `INSERT … ON CONFLICT (user_id, effective_from) DO UPDATE`. Concurrent Set/Set
or Set/Remove requests for the same user and day leave exactly one state (the last committed write)
and never a duplicate history row. The UI is not relied on.

## Application

| Use case | Behaviour |
| --- | --- |
| `GetNutritionTargetHandler(user, date)` | target effective on any diary day |
| `GetCurrentNutritionTargetHandler(user, offset)` | target effective on the local today |
| `SetNutritionTargetHandler(user, values, offset)` | Manual state effective today (insert or same-day replace) |
| `RemoveNutritionTargetHandler(user, offset)` | "no targets" state effective today, only if a target is active |
| `GetDailyNutritionSummaryHandler` / `AnalyzeDayHandler` | the day's summary now carries the target effective on that date |

`DailyNutritionSummary` gains `Target` (`NutritionTargetValues?`). What remains (target − consumed)
is presentation only and is never stored. Target presence changes nothing about AI: Analyze day,
lazy close and Estimate behave exactly as in NUT-002.

## API

All routes are authenticated and user-scoped (the user id comes only from the token). Contracts, not
EF entities.

| Route | Result |
| --- | --- |
| `GET /api/nutrition/targets/current?utcOffsetMinutes=120` | 200 `{date, target}`; 400 |
| `GET /api/nutrition/targets?date=yyyy-MM-dd` | 200 `{date, target}`; 400 |
| `PUT /api/nutrition/targets` `{caloriesKcal?, proteinGrams?, carbsGrams?, fatGrams?, utcOffsetMinutes}` | 200 `{date, target}`; 400 |
| `DELETE /api/nutrition/targets/current?utcOffsetMinutes=120` | 200 `{date, target: null}`; 400 |

`target` is `{effectiveFrom, caloriesKcal?, proteinGrams?, carbsGrams?, fatGrams?, source}` or null.
400 (ProblemDetails, field-keyed) for zero, negative, too high, all empty (`target`), a missing or
out-of-range offset, or a malformed date. `DELETE` ends the target from today; history is kept.

`GET /api/nutrition/summary` and `POST /api/nutrition/analyze` summaries gain an optional
`target: {caloriesKcal?, proteinGrams?, carbsGrams?, fatGrams?}` (null without a target); existing
fields are unchanged.

## UI

### Nutrition page

The journal stays primary. A compact **Daily targets** section follows the Meals card; it always
shows the **current** target:

```text
Daily targets                      Set targets
No targets

Daily targets                      Edit
2200 kcal
160 P · 240 C · 70 F
Effective from 4 October
Remove targets
```

Set targets / Edit open the same inline form (header action style):

```text
Calories  [ 2200 ] kcal
Protein   [ 160  ] g
Carbs     [ 240  ] g
Fat       [ 70   ] g
Changes apply from today.
[ Save ] [ Cancel ]
```

Every field is optional; all empty is rejected ("Enter at least one target. To have no targets, use
Remove targets."); zero/negative is rejected in the form, bounds by the API. Remove targets asks
"Remove daily targets from today? Earlier days keep their targets." (Remove / Cancel).

### Daily nutrition

When the **selected day** has a target (resolved by the API for that date, so a past day shows its
historical target), the totals become comparisons; untargeted metrics show only the consumed value:

```text
3 meals · 2 analyzed
1480 / 2200 kcal
Protein   104 / 160 g
Carbs     151 g
Fat        49 / 70 g
```

The completeness line stays above the totals, so partial totals remain obvious. No progress bars,
no "over/under", no success or failure wording. Without a target the NUT-002 display is unchanged.

### Home

The Nutrition card keeps its NUT-002 shape. With a target for today, the totals read
`1840 / 2200 kcal` and `138 / 160 P · 191 / 240 C · 61 / 70 F` (untargeted macros: value only).
Without a target the lines are exactly the NUT-002 ones. Completeness and the Analyze today / Analyze
remaining / Open nutrition action are unchanged and never depend on the target. Budget and Training
are unaffected.

## Boundaries

- No AI: no call to lifeos-ai or Groq, no prompt or NUT-002 change, no recommendations or inference.
  `src/python/lifeos-ai` is untouched. Machine-checked by
  `Targets_Should_Not_Depend_On_Ai_Estimation`.
- No health profile (weight, height, sex, age, activity, body fat, BMR/TDEE, goals, cut/bulk).
- No Gym integration; Nutrition still depends on neither Finance nor Gym.
- Nutrition-specific: no generic Goal entity or Goals module.

## Phone acceptance checklist

1. Nutrition with no target → "No targets".
2. Set only calories → accepted.
3. Set only protein → accepted.
4. Set all four → accepted.
5. Save all blank → rejected, suggests Remove targets.
6. Edit the same day → current state updates; no duplicate visible behaviour.
7. Daily summary shows consumed / target.
8. Untargeted metrics show consumed only.
9. A partially analyzed day remains visibly partial.
10. Home shows the target comparisons compactly.
11. Remove targets → confirmation.
12. After remove → today has no target.
13. Yesterday → the previous target still applies if it was effective then.
14. Change the target on a later day → older days keep the old target.
15. Meal Estimate / Re-estimate unchanged.
16. Analyze day unchanged.
17. Restart the app → target state persists.
18. Finance / Gym smoke test.
