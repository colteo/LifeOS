# NUT-003 — Nutrition target planning

Status: IMPLEMENTED — offline validation passed; phone acceptance pending

Builds on NUT-001 (text meal journal) and NUT-002 (on-demand AI nutrition estimation).

> **Supersedes** the first NUT-003 design ("one manual target effective from today onward",
> migration `20261004134218_AddNutritionTargets`). That model was rejected before merge and never
> reached Production; its code and migration were removed (see [Migration](#migration)).

## Principle

The user plans optional daily nutrition targets as **bounded periods** with a **weekly pattern** and
**per-date exceptions**. Targets are calories (kcal), protein, carbohydrates and fat (g); every metric
is optional.

This is not diet coaching, a recommendation, a meal plan or a calorie prescription. NUT-003 never
calls AI, never infers a target, and never reads Gym data: "training days" are simply the weekdays the
user customises. The day's totals are compared with its target as plain numbers (`1840 / 2200 kcal`),
with no judgement.

## Model

### Target values

`NutritionTargetValues` (Domain) is one target: any combination of kcal / protein / carbs / fat.

- `null` = that metric is not targeted.
- A present value is **> 0**, at most **10000 kcal** or **1000 g** per macro, kept to **one decimal**
  (rounded half away from zero, so 0.04 rounds to 0.0 and is rejected).
- At least one metric is required. "No target" is always an explicit mode, never an empty target.

### Plans (periods)

```text
NutritionTargetPlan
- Id, UserId
- StartsOn, EndsOn          both required, inclusive, EndsOn >= StartsOn (a one-day period is valid)
- DefaultTarget?            optional
- Rules[7]                  exactly one per weekday, Monday..Sunday
- CreatedAtUtc, UpdatedAtUtc
```

- No open-ended plans. Multiple future plans may be created at any time.
- **Gaps are allowed** (7 Oct – 3 Nov, then 10 Nov – 1 Dec: 4–9 Nov have no target) and are never
  filled automatically.
- **Plans of one user never overlap** (inclusive ranges; adjacent periods such as 3 Nov / 4 Nov are
  fine). See [Overlap guarantee](#overlap-guarantee).

### Weekly pattern

Each weekday has one mode:

| Mode | Meaning | Values |
| --- | --- | --- |
| `Default` | the plan's default target | none stored |
| `Custom` | the weekday's own target | at least one metric |
| `NoTarget` | no target that weekday | none stored |

**The default target may be absent**, so a plan can consist only of custom/no-target weekdays. A
weekday set to `Default` in a plan without a default is invalid ("Monday uses the default target, but
the period has none.").

Example (7 Oct – 3 Nov): default 2200 kcal / 160 P / 240 C / 70 F; Monday, Wednesday, Friday Custom
2500 kcal; Sunday Custom 2800 kcal or NoTarget; other days Default.

**Persistence decision:** all seven rule rows are always stored (`nutrition_target_plan_day_rules`,
primary key `(plan_id, weekday)`). The pattern is explicit in the data, a check constraint can enforce
each row's mode/value consistency, and resolution needs no "missing row means Default" convention.

### Daily overrides

```text
NutritionTargetOverride
- Id, UserId, PlanId, Date
- Mode: Custom | NoTarget   (no "Default": removing the override is the way back)
- values (Custom only)
- CreatedAtUtc, UpdatedAtUtc
```

- At most one override per user and date (`UNIQUE (user_id, date)`); saving again replaces it.
- An override exists **only inside a plan**: it references the plan covering its date, and setting
  one on a date no plan covers is rejected ("No target period covers this date. Create a period
  first."). An override never creates a standalone target.
- Removing an override returns the date to its weekday rule.

### Resolution order (deterministic, Domain)

For a diary date (`NutritionTargetResolution.Resolve`):

1. Find the plan covering the date. None → **no target**.
2. A daily override exists → `Custom`: its target; `NoTarget`: no target.
3. Otherwise the weekday rule → `Default`: the plan default; `Custom`: the weekday target;
   `NoTarget`: no target.

### Past plans, editing and deletion

- Past plans stay stored and keep resolving their dates. Nothing is snapshotted per day: if the user
  explicitly **edits** a past plan, its dates resolve with the edited rules (deliberate configuration,
  not a side effect). Editing one plan never changes another.
- **Delete** is uniform for past, current and upcoming plans and always asks for confirmation. Deleting
  a plan deletes its weekly rules and its overrides (FK `ON DELETE CASCADE`); its dates then have no
  target. Meals and meal nutrition are never touched (no FK from them).
- **Editing a plan's dates** deletes, in the same transaction, its overrides that fall outside the new
  period, so an override can never outlive its plan's coverage.

## Overlap guarantee

Checked twice, never resolved automatically (no shortening, moving, merging or replacing):

1. **Application** — before saving, `SaveNutritionTargetPlanHandler` looks for an overlapping plan of
   the user (excluding the plan being edited) and returns `Overlap` with a readable message:
   "This period overlaps 7 Oct – 3 Nov 2026." (API: **409** ProblemDetails, no SQL wording.)
2. **Database** — trigger `trg_nutrition_target_plans_no_overlap` (`BEFORE INSERT OR UPDATE OF
   user_id, starts_on, ends_on`) runs `nutrition_target_plans_prevent_overlap()`, which
   - takes `pg_advisory_xact_lock(hashtextextended('nutrition_target_plans:' || user_id, 0))`, so all
     plan writes of one user are serialized until commit/rollback (a hash collision between users can
     only add waiting, never allow an overlap);
   - then looks for an overlapping plan of the same user. In READ COMMITTED every query of this
     volatile function takes a fresh snapshot, so after acquiring the lock it sees any overlapping plan
     committed by a concurrent transaction;
   - raises SQLSTATE **23P01** (`exclusion_violation`) with constraint name
     `ex_nutrition_target_plans_no_overlap`, which the repository maps back to `Overlap` (409);
   - refuses writes under any other isolation level (`invalid_transaction_state`) rather than weaken
     the guarantee. LifeOS uses the default READ COMMITTED.

**Exact guarantee:** two overlapping plans of the same user can never both be committed, whether
written concurrently, by the application or by direct SQL. Different users never block each other's
overlaps (only, rarely, a hash collision makes one wait).

**Why not an exclusion constraint:** `EXCLUDE USING gist (user_id WITH =, daterange(...) WITH &&)`
needs the `btree_gist` extension for the uuid equality. Production migrations run as the non-superuser
`lifeos` role on Neon, which cannot `CREATE EXTENSION`, and the runbook requires that migration scripts
contain none ("LifeOS needs no extensions"). The trigger gives the same guarantee with built-in
PostgreSQL only.

Override writes are one `INSERT … SELECT … FROM nutrition_target_plans … FOR SHARE … ON CONFLICT
(user_id, date) DO UPDATE`, conditioned on the plan still covering the date: a concurrent plan delete or
date change either commits first (the insert then finds no covering plan and writes nothing) or waits
for the override and then cascades/cleans it.

## Migration

### Old migration (rejected model)

`20261004134218_AddNutritionTargets` was **removed with EF tooling** (`dotnet ef migrations remove`),
which also reverted `LifeOSDbContextModelSnapshot` to exactly its `main` content. No "fix" migration is
stacked on it; Production never received it.

Local development databases that applied it must be rolled back once, **before** pulling this version:

```powershell
dotnet tool run dotnet-ef database update 20261003143631_AddMealNutritionSnapshots `
  --project src/dotnet/LifeOS.Infrastructure/LifeOS.Infrastructure.csproj `
  --startup-project src/dotnet/LifeOS.Api/LifeOS.Api.csproj
```

(It drops `nutrition_targets` and its rows, which belong to the rejected model.) If the old migration
files are already gone, drop the table and the history row by hand:
`DROP TABLE nutrition_targets; DELETE FROM "__EFMigrationsHistory" WHERE "MigrationId" = '20261004134218_AddNutritionTargets';`
then run `database update` normally. The developer machine used for this change was rolled back this
way (one synthetic row discarded).

### New migration

`20261004145254_AddNutritionTargetPlans` (EF tooling, after `AddMealNutritionSnapshots`). The trigger
and its function are hand-written `migrationBuilder.Sql` in this migration (they are not part of the EF
model); the model snapshot was not hand-edited.

```text
nutrition_target_plans
- id uuid PK · user_id uuid → users ON DELETE RESTRICT
- starts_on date · ends_on date        ck_nutrition_target_plans_period (calendar dates, ends_on >= starts_on)
- default_calories_kcal numeric(6,1)? · default_protein/carbs/fat_grams numeric(5,1)?
                                        ck_nutrition_target_plans_default (null or > 0 and within bounds)
- created_at_utc, updated_at_utc timestamptz
- ix_nutrition_target_plans_user_starts_on (user_id, starts_on)
- trigger trg_nutrition_target_plans_no_overlap → nutrition_target_plans_prevent_overlap()

nutrition_target_plan_day_rules
- PK (plan_id, weekday) · plan_id → nutrition_target_plans ON DELETE CASCADE
- weekday smallint 1..7 (ISO: Monday 1 … Sunday 7)   ck_nutrition_target_plan_day_rules_weekday
- mode varchar(16) Default|Custom|NoTarget             ck_nutrition_target_plan_day_rules_mode
- calories_kcal numeric(6,1)? · protein/carbs/fat_grams numeric(5,1)?
  ck_nutrition_target_plan_day_rules_values: bounds, and Custom ⇔ at least one value

nutrition_target_overrides
- id uuid PK · user_id → users RESTRICT · plan_id → nutrition_target_plans CASCADE
- date date · UNIQUE ux_nutrition_target_overrides_user_date (user_id, date)
- mode varchar(16) Custom|NoTarget                     ck_nutrition_target_overrides_mode
- values as above                                      ck_nutrition_target_overrides_values (Custom ⇔ values)
- created_at_utc, updated_at_utc timestamptz
```

`meal_entries` and `meal_nutrition_snapshots` are unchanged. Down drops the three tables and the
function. The idempotent production script (`migrations script --idempotent --no-transactions`) was
applied to an empty PostgreSQL 17 as a non-superuser owner role, like the production `lifeos` role:
it succeeded, created no extension, every table is owned by that role, and running it again changes
nothing. For the S4 review of this release expect, besides `CREATE TABLE`/`CREATE INDEX`, exactly one
`CREATE FUNCTION nutrition_target_plans_prevent_overlap` and one `CREATE TRIGGER
trg_nutrition_target_plans_no_overlap`.

## Application

| Use case | Behaviour |
| --- | --- |
| `GetNutritionTargetPlansHandler` | the user's plans by start date |
| `GetNutritionTargetPlanHandler` | one plan with its weekly rules; 404 for another user's |
| `SaveNutritionTargetPlanHandler.CreateAsync / UpdateAsync` | validate, reject overlaps (excluding the edited plan), save |
| `DeleteNutritionTargetPlanHandler` | delete plan + rules + overrides |
| `GetResolvedNutritionTargetHandler` | the resolved target for a date, whether a plan covers it, its override |
| `SetNutritionTargetOverrideHandler` / `RemoveNutritionTargetOverrideHandler` | per-date Custom/NoTarget, or back to the rule |
| `GetDailyNutritionSummaryHandler` / `AnalyzeDayHandler` | the summary's `Target` is the date's resolved target |

The summary exposes only resolved values, never the plan, weekly rules or future plans. NUT-002
estimation, Analyze day and lazy close are unchanged; a target never affects what AI is asked.

## API

All routes are authenticated and user-scoped; another user's plan is 404. Contracts, not EF entities.
Plans use explicit dates, so no route takes a time zone.

| Route | Result |
| --- | --- |
| `GET /api/nutrition/target-plans` | 200 `[plan]` by `startsOn` |
| `GET /api/nutrition/target-plans/{id}` | 200 `plan`; 404 |
| `POST /api/nutrition/target-plans` | 201 `plan`; 400; **409 overlap** |
| `PUT /api/nutrition/target-plans/{id}` | 200 `plan`; 400; 404; **409 overlap** |
| `DELETE /api/nutrition/target-plans/{id}` | 204; 404 |
| `GET /api/nutrition/targets/resolved?date=yyyy-MM-dd` | 200 `{date, target?, coveredByPlan, override?}`; 400 |
| `PUT /api/nutrition/target-overrides/{yyyy-MM-dd}` `{mode, target?}` | 200 resolved; 400 (also outside every plan) |
| `DELETE /api/nutrition/target-overrides/{yyyy-MM-dd}` | 200 resolved (idempotent) |

`plan` = `{id, startsOn, endsOn, defaultTarget?, weeklyRules: [{weekday, mode, target?}] × 7}`, with
`weekday` "Monday"…"Sunday" and `mode` "Default" | "Custom" | "NoTarget"; `target` =
`{caloriesKcal?, proteinGrams?, carbsGrams?, fatGrams?}`. Validation failures are field-keyed
ProblemDetails (`startsOn`, `endsOn`, `defaultTarget.caloriesKcal`, `weeklyRules.Monday`,
`weeklyRules.Monday.fatGrams`, `mode`, `target`, `date`, …). The summary routes keep their NUT-002
shape with an optional resolved `target`.

## UI

### Targets page (`/nutrition/targets`)

```text
< Back                                  Nutrition targets
Periods                                     + New period
CURRENT
  7 Oct – 3 Nov                                    [Edit]
  2200 kcal default
  Mon · Wed · Fri custom
  Sun no target
UPCOMING
  4 Nov – 1 Dec                                    [Edit]
  2300 kcal default
PAST                                            Show 2
```

Past periods are collapsed and visually secondary. No calendar, no dashboard.

**Plan editor** (inline on the page): Period (From / To dates), Default target (four optional
fields), Weekly pattern (one compact row per weekday with Default / Custom / No target; the four
fields open under a day only when it is Custom), Save / Cancel, and for an existing period
"Delete period" with confirmation ("Delete 7 Oct – 3 Nov? Its days will have no target. Meals are not
affected."). The overlap check runs as soon as a date changes ("This period overlaps 7 Oct – 3 Nov.")
and Save stays disabled until it is resolved; a 409 from the API (a period saved meanwhile elsewhere)
is shown the same way.

### Nutrition page

Below "Daily nutrition", a **Target** section for the selected day:

- a period covers the day → the resolved target (or "No target for this day") and **Edit for this
  day**: "Use custom target" (four fields) or "No target for this day";
- an override exists → the title reads **Target override**, with **Edit** and **Remove override**
  (back to the weekday rule);
- no period covers the day → "No target period covers this day." and no override action;
- always a **Target periods** link to the Targets page.

Daily totals compare with the resolved target, keeping the NUT-002 completeness line above:

```text
3 meals · 2 analyzed
1480 / 2200 kcal
Protein   104 / 160 g
Carbs     151 / 240 g
Fat        49 / 70 g
```

Untargeted metrics show only the consumed value; without a target the NUT-002 display is unchanged.

### Home

The Nutrition card uses only **today's resolved target** from the summary (`1840 / 2500 kcal`,
`138 / 160 P · …`); without a target it is exactly the NUT-002 card. No periods, weekdays, overrides
or future plans on Home; Analyze today / Analyze remaining / Open nutrition are unchanged.

## Boundaries

- No AI: `src/python/lifeos-ai` untouched; no Groq calls, prompts, recommendations or inference.
  Machine-checked: `Targets_Should_Not_Depend_On_Ai_Estimation`.
- No Gym coupling: Nutrition depends on neither Finance nor Gym (`Nutrition_Should_Not_Depend_On_Finance_Or_Gym`).
- No health profile; no generic Goals module.

## Phone acceptance checklist

Apply the migration first (and the one-time rollback above if your database had the rejected one).

1. Create the period 7 Oct – 3 Nov.
2. The default target works on a Default weekday.
3. Monday custom.
4. Wednesday custom.
5. Friday custom.
6. Sunday custom, or No target.
7. Diary dates resolve the correct weekday values.
8. The first and last days of the period resolve correctly.
9. Create the upcoming period 4 Nov – 1 Dec → accepted.
10. Create 28 Oct – 30 Nov → blocked: "This period overlaps …".
11. Edit the first period so it reaches into the second → blocked.
12. A gap between periods → those dates show "No target period covers this day."
13. A daily custom override.
14. Remove override → back to the weekday rule.
15. A daily No target override.
16. Home reflects today's resolved value.
17. A past diary date reflects its period / rule.
18. Estimate / Re-estimate / Analyze unchanged.
19. Restart the app → periods persist.
20. Finance / Gym smoke test.

## Out of scope / deferred

AI recommendations, Gym-driven targets, health/body profile, weight, hydration, micronutrients,
weekly averages, immutable per-day target history, open-ended periods, automatic gap filling or
conflict resolution, plan templates/copying, trends, coaching, notifications, generic Goals module.
