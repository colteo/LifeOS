## 1. Goal and non-goals

An **optional, private** module in which a user records their menstrual periods and, if they wish,
daily flow, symptoms and notes; sees them on a calendar and in an editable history; and, if they
opt in, sees a deterministic, explicitly uncertain estimate of the next period start and receives a
discreet reminder.

The module is **disabled by default for every user**. While disabled it leaves no trace in the app
except one switch in Settings (and, for new users, one optional onboarding screen).

Non-goals (v1, deliberately excluded):

| Excluded | Why |
|---|---|
| Fertility window, ovulation, "safe days", contraception, pregnancy mode **[Given]** | A calendar estimate is not reliable enough for any of these and must never be presented as if it were. |
| Any AI: diagnosis, interpretation, prediction, summaries, chat over cycle data **[Given]** | Estimates are deterministic arithmetic (AGENTS.md "Deterministic software computes"). No external AI provider receives cycle data. |
| Clinical language ("late", "irregular", "abnormal", conditions, advice) **[Given]** | LifeOS is not a medical device. Wording stays descriptive (§7.4). |
| Third-party medical models or datasets **[Given]** | Out of scope by the issue rules. |
| Basal temperature, test results, sexual activity, medication, mood scales | Data minimisation: not needed for the stated goal. |
| Free-form custom symptoms | A fixed catalogue + the note covers v1 (§5.3). |
| Integration with other modules, Weekly Review, Home card, Journal RAG | Isolation by design (§9). |
| Sharing with a partner/clinician, offline sync, widgets, wearables | Out of scope. |
| Gender, sex or "who menstruates" attributes on the user | Not needed; see §4.1. |
| Application-level field encryption, app lock / PIN | Deferred (§12), with the residual risk stated. |

## 3. Proposed design decisions

All rows are **[Proposal]**; the ones with product or risk impact are repeated in §15 for approval.

| # | Decision | Why |
|---|---|---|
| D-1 | **New module `Cycle`** in every layer (`Domain/Cycle`, `Application/Cycle`, `Contracts/Cycle`, `Infrastructure/.../Cycle`, `Api/Cycle`, `App/.../Cycle`), routes under `/api/cycle`, app routes under `/cycle`. Docs under `docs/tasks/health/`. | Same per-feature layout as Journal, Gym, Nutrition. No "Health" umbrella abstraction until a second health module exists. |
| D-2 | **Module settings = `cycle_tracker_settings`, one optional row per user** (`user_id` PK). **No row ⇒ disabled.** | Same shape as AUTO-002 `weekly_review_settings` and AUTO-003A `notification_preferences`, but default-off. No column on `users`, no generic feature-flag framework. |
| D-3 | **The cycle reminder flag lives in `cycle_tracker_settings`, not in `notification_preferences`.** | Module-owned, like Weekly Review. Every cycle-related fact stays in the module's own tables, so "Delete all cycle data" is one place, and a health flag is not stored in a generic table. Quiet hours still come from the Notifications core. |
| D-4 | **Two record tables: `cycle_periods` and `cycle_day_logs`**, independent. | Periods answer "when", day logs answer "how". Spotting outside a period is allowed; a period without day logs is normal. Editing one never rewrites the other. |
| D-5 | **Symptoms = closed catalogue of stable codes stored as `text[]`** with a check constraint. | One row per day, no join table, readable export; the check is exact. Npgsql maps string arrays natively (no new package). |
| D-6 | **Estimates computed on read by a pure Domain service (`CycleEstimator`)**, never stored. | Always consistent with edited history; nothing derived to delete or leak; trivially unit-testable. |
| D-7 | **Per-user write serialisation by locking the user's `cycle_tracker_settings` row (`SELECT … FOR UPDATE`)** in period writes, then checking overlap in Application. | No-overlap across rows needs an exclusion constraint and the `btree_gist` extension (new infrastructure). The settings row always exists while enabled, so it is a natural per-user lock. DB backstops: unique start per user, at most one open period per user, end ≥ start. |
| D-8 | **Module gate in Application:** record use cases first load the settings; disabled ⇒ `CycleTrackerDisabled` ⇒ HTTP **409**. Settings, export and delete-all work in any state. | One rule, testable without HTTP; the user can always see, export and erase their data. 409 matches existing "state conflict" responses. |
| D-9 | **Onboarding offer is client-side; no `OnboardingStatus` change.** After `CompleteOnboarding` succeeds, the app shows an "Optional modules" screen once (in-memory navigation, no persisted flag); "Not now" is the default action. | A server onboarding state would change the state machine for every user to offer something optional. Nothing is stored when the user declines. Existing users enable from Settings. |
| D-10 | **Reminder = module-owned automation handler** with a neutral FCM payload type and no id (§8). | Reuses ADR-012 (claim = insert, outbox, quiet hours). Google (FCM) sees only the neutral type. |
| D-11 | **`Cache-Control: no-store` on every cycle response; App keeps cycle data in memory only.** | Nothing persists on the device except an export the user explicitly creates. |
| D-12 | **No record values in URLs** (dates, flow, symptoms): day logs are written with a body and addressed by opaque id (§7.1). | Request paths and query strings can appear in platform request logs and proxies, which are outside LifeOS's logging rules. |
| D-13 | **An ADR is proposed with PR 1** ("Sensitive personal modules: opt-in, AI exclusion, neutral notifications, hard deletion"). Not written in this task. | The rules in §9 are cross-cutting and would apply to future health modules. |

## 4. Activation and consent

### 4.1 Voluntary preference vs gender attribute

The owner first proposed enabling the module based on gender declared during onboarding. The issue
asks to evaluate a lower-data alternative.

| | A. Gender declared in onboarding drives the module | **B. Voluntary "Track menstrual cycle" preference (proposed)** |
|---|---|---|
| Data collected | A new identity attribute for **every** user, whether or not they want the module | Nothing, unless the user opts in |
| Accuracy | Gender does not determine who menstruates (e.g. trans and non-binary people, menopause, medical conditions, pregnancy) | Whoever wants the module enables it; whoever does not, never sees it |
| Sensitivity | Gender identity (and inferred health status) becomes stored profile data, with its own deletion/export/legal questions | Only the opt-in itself, held with the module's data and erased with it |
| UX | Forced question during onboarding; wrong defaults are intrusive | One optional screen, default "Not now"; Settings at any time |
| Architecture | Touches `users` and onboarding states | Module-owned row (D-2), no `users` change |

**Recommendation: B.** No gender or sex attribute is added to LifeOS by this feature. Approval
needed (§15, O-1).

### 4.2 Lifecycle

```text
          (no row)                     PUT settings {enabled:true}
   ┌────────────────────┐  ──────────────────────────────────────►  ┌─────────────────────┐
   │ Disabled (default) │                                            │ Enabled             │
   │ module hidden      │  ◄──────────────────────────────────────  │ More → Cycle        │
   └────────────────────┘     PUT settings {enabled:false}           └─────────────────────┘
            ▲                 (records kept, reminder rows deleted)          │
            │                                                                 │
            └──────────── DELETE /api/cycle/data (any state) ◄────────────────┘
                          all cycle rows of the user deleted from the live
                          database, settings row included ⇒ back to "no row"
```

- **Enable** creates or updates the settings row: `enabled = true`, `enabled_at_utc = now`;
  `estimates_enabled` and `reminder_enabled` stay **false** unless the user turns them on.
- **Disable** sets `enabled = false`, keeps periods and day logs, and in the same transaction deletes
  the user's `CycleReminder` deliveries and `CycleUpcomingPeriodReminder` automation executions (§9.6).
  Re-enabling shows the old records again. The disable dialog offers "Disable and keep my records"
  and "Disable and delete all cycle data" side by side.
- **Delete all** (§10.1) removes the settings row too.

### 4.3 Consent screen content

Before the user enables anything, the activation screen states, in plain language:

1. what is stored (dates, optional flow, symptoms, notes) and that it is visible only to their account;
2. that nothing is sent to AI services and that LifeOS makes no medical assessment;
3. that estimates, if enabled, are approximate and **not** for contraception or pregnancy planning;
4. that reminders, if enabled, show only "You have a reminder";
5. that they can export or delete everything at any time, and that deleted records may remain in
   encrypted backups for a limited time (§10.3).

The timestamp of the opt-in is `enabled_at_utc`. Whether this screen is sufficient as **explicit
consent** for art. 9 data is a legal question (§13, L-2), not settled here.

## 5. Domain model (`LifeOS.Domain.Cycle`)

Framework-free, no EF attributes, ids `Guid.CreateVersion7()`, timestamps supplied by Application
(`TimeProvider`), validation failures as `ArgumentException` like the other modules.

### 5.1 `CycleTrackerSettings`

| Field | Meaning |
|---|---|
| `UserId` | Owner and key. |
| `Enabled` | Module on/off. |
| `EstimatesEnabled` | Show the next-start estimate. Default false. |
| `ReminderEnabled` | Upcoming-period reminder. Default false. **Invariant:** `ReminderEnabled ⇒ EstimatesEnabled`. |
| `EnabledAtUtc` | Last time the module was enabled (opt-in timestamp). |
| `UpdatedAtUtc` | Last change. |

`Default(userId)` is the disabled, never-saved state (like `NotificationPreferences.Default`).
`Update(enabled, estimates, reminder, now)` enforces the invariant; enabling stamps `EnabledAtUtc`.

### 5.2 `CyclePeriod`

| Field | Meaning |
|---|---|
| `Id`, `UserId` | Identity, owner (never from a request). |
| `StartDate` | `DateOnly`, required. |
| `EndDate` | `DateOnly?`; `null` = period in progress. |
| `Note` | Optional, trimmed, ≤ 500 chars, blank ⇒ `null`, never truncated. |
| `CreatedAtUtc`, `UpdatedAtUtc` | Application clock. |

Rules (Domain, given `today` = the user's local date, supplied by Application):

- Dates are **local calendar dates**: changing time zone never moves a logged day.
- `StartDate ≥ 2000-01-01` and `StartDate ≤ today + 1` (one day of tolerance for a device/server
  zone mismatch). No future planning.
- `EndDate`, when present: `StartDate ≤ EndDate ≤ today + 1` and inclusive length ≤ 20 days.
  Longer ⇒ 400 with a neutral message (probably a forgotten earlier end).
- **Open period:** creating or editing a period with no end requires `StartDate ≥ today − 19`. An
  open period that later becomes older than 20 days stays valid in storage and is shown as "needs an
  end date"; estimates still use its start.
- `Update(start, end, note, today, now)` is a full replacement; an invalid update changes nothing.
- `End(endDate, today, now)` is the "Period ended" shortcut.

Per-user rules (Application, under the D-7 lock, DB backstops where possible):

- periods of one user **never overlap** (inclusive ranges; an open period extends to `today` for
  the check);
- at most **one open period** per user, and it must be the **latest** period.

### 5.3 `CycleDayLog`

| Field | Meaning |
|---|---|
| `Id`, `UserId` | Identity, owner. |
| `Date` | `DateOnly`, unique per user, same range rules as `StartDate`. |
| `Flow` | `FlowIntensity?`: `Spotting`, `Light`, `Medium`, `Heavy`; `null` = not recorded. |
| `Symptoms` | Set of `CycleSymptom` (closed catalogue, de-duplicated, stored sorted). |
| `Note` | Optional, ≤ 1 000 chars, same normalisation as above. |
| `CreatedAtUtc`, `UpdatedAtUtc` | Application clock. |

`CycleSymptom` catalogue (stable codes; UI labels are presentation; contents need approval, O-9):
`Cramps`, `Headache`, `Bloating`, `BreastTenderness`, `BackPain`, `Acne`, `Fatigue`, `Nausea`,
`Cravings`, `SleepChanges`, `MoodChanges`. Adding a symptom later = one enum value + one check
constraint change (a migration).

A day log must carry **something** (flow, at least one symptom, or a note); saving an empty log
deletes it. A flow recorded outside any period is allowed (spotting) and **never** creates or ends a
period implicitly.

### 5.4 `CycleEstimator` (pure Domain service)

Input: the user's periods, `today`. Output `CycleEstimate`:

| Result | When | Shown as |
|---|---|---|
| `Unavailable(InsufficientData, validCycles)` | fewer than **3** valid cycle lengths | "Log at least 4 periods to see an estimate" |
| `Available(windowStart, windowEnd, typicalCycleLength, typicalPeriodLength?, cyclesUsed, wide)` | otherwise, and `today ≤ windowEnd` | a dashed window on the calendar + text (§7.4) |
| `WindowPassed(windowStart, windowEnd, cyclesUsed)` | `today > windowEnd` and no newer period | neutral text, no alert, no reminder |

Algorithm (deterministic, explained to the user in "How is this estimated?"; parameters need
approval, O-4):

1. Sort periods by `StartDate`. **Cycle length** `Lᵢ = Start(i+1) − Start(i)` in days.
2. Keep the **most recent 6** lengths whose later start is within the last 12 months; drop lengths
   **< 15 or > 90 days** (most likely a missing or duplicate record). Dropped lengths are still
   shown in History; they are only excluded from the estimate.
3. Fewer than 3 kept ⇒ `Unavailable`.
4. `M = median(L)`, `m = min(L)`, `X = max(L)`, `last = latest StartDate`;
   `windowStart = last + min(m, M − 2)`, `windowEnd = last + max(X, M + 2)`.
   The window is **at least 5 days wide** and widens with the observed spread.
5. `wide = (X − m) > 9`. Shown as "Your logged cycles vary, so this window is less reliable" —
   never with a clinical label.
6. `typicalPeriodLength = median(End − Start + 1)` over the most recent 6 closed periods, or `null`
   with fewer than 3. Text only; no estimated period days are drawn.
7. Only the **next** start is estimated. No multi-month projection.

**Limits stated to the user:** the estimate only reflects what was logged; missing or late entries
distort it; cycles that vary a lot produce wide windows or none; it cannot account for pregnancy,
contraception, illness, menopause or any medical condition, and it is not suitable for any of them.
The estimator never reads day logs, symptoms or notes.

## 6. Persistence concept (no migration in this task)

Explicit EF configurations in Infrastructure, snake_case, `timestamptz` UTC, `date` for calendar
days, enum-like values as strings. All tables are **user-owned leaf data**: `user_id NOT NULL`, FK →
`users(id) ON DELETE CASCADE` (ADR-006).

```text
cycle_tracker_settings
  user_id            uuid        PK, FK -> users(id) ON DELETE CASCADE
  enabled            boolean     NOT NULL
  estimates_enabled  boolean     NOT NULL
  reminder_enabled   boolean     NOT NULL              (added by PR 5)
  enabled_at_utc     timestamptz NULL
  updated_at_utc     timestamptz NOT NULL
  ck_cycle_tracker_settings_reminder   NOT reminder_enabled OR estimates_enabled

cycle_periods
  id              uuid          PK
  user_id         uuid NOT NULL FK -> users(id) ON DELETE CASCADE
  start_date      date NOT NULL
  end_date        date NULL
  note            varchar(500) NULL
  created_at_utc  timestamptz NOT NULL
  updated_at_utc  timestamptz NOT NULL
  ux_cycle_periods_user_start       UNIQUE (user_id, start_date)
  ux_cycle_periods_user_open        UNIQUE (user_id) WHERE end_date IS NULL
  ck_cycle_periods_range            end_date IS NULL OR (end_date >= start_date AND end_date - start_date <= 19)
  ck_cycle_periods_start            start_date >= '2000-01-01'
  ck_cycle_periods_note             note IS NULL OR length(btrim(note)) > 0

cycle_day_logs
  id              uuid          PK
  user_id         uuid NOT NULL FK -> users(id) ON DELETE CASCADE
  log_date        date NOT NULL
  flow            varchar(16) NULL
  symptoms        text[] NOT NULL DEFAULT '{}'
  note            varchar(1000) NULL
  created_at_utc  timestamptz NOT NULL
  updated_at_utc  timestamptz NOT NULL
  ux_cycle_day_logs_user_date       UNIQUE (user_id, log_date)
  ck_cycle_day_logs_flow            flow IS NULL OR flow IN ('Spotting','Light','Medium','Heavy')
  ck_cycle_day_logs_symptoms        symptoms <@ ARRAY['Cramps',…,'MoodChanges']::text[]
  ck_cycle_day_logs_not_empty       flow IS NOT NULL OR cardinality(symptoms) > 0 OR note IS NOT NULL
  ck_cycle_day_logs_note            note IS NULL OR length(btrim(note)) > 0
```

- Start dates are unique per user, so `start_date DESC` is a total order: history paging and the
  estimator's "last 7 starts" are backward range scans of `ux_cycle_periods_user_start`.
- Overlap is enforced in Application under the D-7 lock; DB backstops cover duplicate starts and a
  second open period.
- No column holds an estimate, a cycle day number or anything AI-related.
- **Migrations, proposed only** (each created by its PR, none by this document): `AddCycleTracker`
  (settings + periods, PR 1), `AddCycleDayLogs` (PR 2), `AddCycleReminderSetting` (PR 5). Each `Down`
  drops only what its `Up` created. Each migration PR updates the runbook and the backup row-count
  checks (backup-restore §4.2).

Repository ports (Application), all with an explicit `userId` (ADR-006):

```text
ICycleSettingsRepository   GetAsync(userId) · GetForUpdateAsync(userId) · UpsertAsync(settings)
ICyclePeriodRepository     ListRecentStartsAsync(userId, max) · GetPageAsync(userId, limit, cursor)
                           GetAsync(userId, id) · ListInRangeAsync(userId, from, to)
                           AddAsync · UpdateAsync · DeleteAsync(userId, id)
ICycleDayLogRepository     GetByIdAsync(userId, id) · GetByDateAsync(userId, date)
                           ListInRangeAsync(userId, from, to) · UpsertAsync · DeleteAsync(userId, id)
ICycleDataEraser           DeleteAllAsync(userId)            // one transaction, §10.1
ICycleReminderRepository   (PR 5) candidate users per zone, reminder row cleanup
```

## 7. API and contracts (`LifeOS.Api/Cycle/CycleEndpoints.cs`)

All routes `RequireAuthorization` (listed in `EndpointAuthorizationHttpTests`). The owner is the
token's `UserId`; contracts contain no user id (an extra `userId` is ignored). Another user's record
is indistinguishable from a missing one (404). Every response sets `Cache-Control: no-store`.
Validation failures are `ValidationProblem` (400) keyed by field, with **fixed messages that never
echo submitted values**. Enum-like values are strings.

### 7.1 Endpoints

| Method | Route | Success | Errors |
|---|---|---|---|
| `GET` | `/api/cycle/settings` | 200 `CycleSettingsResponse` (defaults when no row) | — |
| `PUT` | `/api/cycle/settings` | 200 `CycleSettingsResponse` | 400 |
| `GET` | `/api/cycle/overview` | 200 `CycleOverviewResponse` | 409 disabled |
| `GET` | `/api/cycle/calendar?from=&to=` | 200 `CycleCalendarResponse` | 400 range (`from ≤ to`, ≤ 93 days), 409 |
| `GET` | `/api/cycle/periods?limit=&cursor=` | 200 `CyclePeriodPageResponse` | 400 `limit`/`cursor`, 409 |
| `GET` | `/api/cycle/periods/{id}` | 200 `CyclePeriodResponse` | 404, 409 |
| `POST` | `/api/cycle/periods` | 201 `CyclePeriodResponse` + `Location` | 400 fields/overlap/open-period, 409 |
| `PUT` | `/api/cycle/periods/{id}` | 200 `CyclePeriodResponse` | 400, 404, 409 |
| `DELETE` | `/api/cycle/periods/{id}` | 204 | 404, 409 |
| `PUT` | `/api/cycle/days` (date in the body; upsert by date) | 200 `CycleDayLogResponse`, or **204** when the content is empty (log deleted) | 400, 409 |
| `DELETE` | `/api/cycle/days/{id}` | 204 | 404, 409 |
| `GET` | `/api/cycle/export` | 200 `application/json` attachment `lifeos-cycle-export.json` | — (works when disabled) |
| `DELETE` | `/api/cycle/data` | 204 | — (works when disabled; idempotent) |

- Single day logs are read through `overview` (today) and `calendar` (`from = to` allowed); there is
  no `GET` by date, so no record date appears in a path (D-12). The calendar query carries only a
  navigation range, never record values.
- Overlap and "only one open period" are **400** on `startDate`/`endDate` with a neutral message.
- Module disabled is **409** "Cycle tracker is not enabled." (D-8).
- History paging: keyset, `limit` 1–50 (default 20), order `start_date DESC`, opaque cursor,
  malformed cursor ⇒ 400 (JRN-001 convention).
- "Today" for date rules = `users.time_zone_id` local date, UTC when the zone is unknown.

### 7.3 Application use cases (`LifeOS.Application.Cycle`)

Plain handlers, no mediator, `TimeProvider` for `now`, user zone for `today`:
`GetCycleSettings`, `UpdateCycleSettings` (incl. reminder-row cleanup on disable), `GetCycleOverview`,
`GetCycleCalendar`, `GetCyclePeriodsPage`, `GetCyclePeriod`, `CreateCyclePeriod`, `UpdateCyclePeriod`,
`DeleteCyclePeriod`, `PutCycleDayLog`, `DeleteCycleDayLog`, `ExportCycleData`, `DeleteAllCycleData`,
and (PR 5) `CycleUpcomingPeriodReminderHandler`. Expected failures are results (`NotFound`, `Disabled`,
`Invalid(field, message)`), mapped to HTTP by the endpoint module.

### 7.4 Wording of estimates (fixed; covered by App tests)

- Available: "Next period estimated between **14 and 20 Nov**. Based on your last **5** cycles."
- Always beneath it: "An estimate from your own history, not medical advice. Do not use it for
  contraception or to plan or avoid pregnancy."
- Wide: "Your logged cycles vary, so this window is less reliable."
- WindowPassed: "No period has been logged since the estimated window (14–20 Nov). Estimates are
  only as complete as your history."
- Unavailable: "Log at least 4 periods to see an estimate."
- Never: "late", "overdue", "irregular", "fertile", "ovulation", "safe", percentages, a single
  predicted day, or advice to see (or not to see) a doctor.

## 8. Reminders (PR 5)

### 8.1 Behaviour

| Item | Value |
|---|---|
| Opt-in | `reminder_enabled`, default **false**, requires estimates (§5.1) |
| Handler | `CycleUpcomingPeriodReminderHandler : IAutomationHandler`, `Application/Cycle/Reminders` |
| `automation_type` | `CycleUpcomingPeriodReminder` |
| Condition | settings `enabled ∧ estimates_enabled ∧ reminder_enabled`; estimate `Available`; local date D = `windowStart − 2` |
| Due | 09:00 local on D via `LocalSchedule.ResolveDaily`; lateness 24 h (AUTO-003A D-8) |
| Occurrence key | `<latest period id>` — at most **one reminder per cycle**; editing dates cannot remind twice |
| Discovery | zone buckets of users with the reminder enabled (ids-only SQL); the estimate is computed **in Application** for those candidates (last 7 starts each); only users whose D is today are returned; bounded by the tick `limit` |
| Execution | re-reads settings and periods; any condition false ⇒ `NotApplicable`; no artifact |
| Notification | `NotificationType.CycleReminder`, a reminder for `NotificationCatalog.IsReminder` ⇒ quiet hours apply (AUTO-003A R-1/D-4); expiry 24 h; no `ResourceType`/`ResourceId` |
| Copy | title `LifeOS`, body `You have a reminder` — no word about cycle, period, health or dates, so the lock-screen preview is identical to a generic reminder |
| FCM data | `type=private_reminder`, **no id** |
| Tap | `/cycle` through `AuthGate`; module disabled (or another account signed in that has it disabled) ⇒ Home. Alternative "always open Home" is O-6. |

The reminder never creates, ends or edits a period.

### 8.2 Production scheduler prerequisite

The engine is cadence-independent: the reminder is sent only if at least one tick lands in
`[09:00 local, +24 h)` of D and around the end of quiet hours (AUTO-003A §10).

- The runbook (Part F) documents a Stage 1 tick `*/10 * * * 0,1` UTC (Sunday/Monday).
- The owner has since shown a cron-job.org configuration **every 10 minutes, every day**.
- **Whether Production actually dispatches daily is not verified by this document.** Before the
  reminder is offered in Production, verify the live dispatch (e.g. `automation_executions` rows for
  existing daily handlers on weekdays, or the Diagnostics page) and align the runbook with the
  actual schedule. Until verified, PR 5 must not be released to Production users.

### 8.3 Interface-level integration with generic Reminders (REM-001)

REM-001 (PR #45, proposal, not merged) designs user-created reminders on the same engine. CYC-001
**does not depend on it** and integrates only at the notification-vocabulary level:

- **Shared:** the automation engine, the delivery outbox, quiet hours (`IsReminder`), expiry rules,
  and the same fixed copy "You have a reminder" (REM-001 D-8), so a cycle reminder is
  indistinguishable from a generic one on the lock screen.
- **Not shared:** the cycle reminder is **not** a REM-001 `Reminder` row and does not appear in the
  generic Reminders list, and its switch is **not** a `notification_preferences` column. Either would
  reveal the module's existence in generic screens and keep a health flag outside the module's
  deletion boundary.
- **Merge sequencing:** both features add values to `NotificationType`, `NotificationCatalog` and
  `NotificationTap`. Whichever lands second rebases onto the first; no shared abstraction is needed.

## 9. Privacy threat model

### 9.1 Data classification and minimisation

Menstrual records, flow and symptoms are **health data** in the sense of GDPR art. 9 (§13). Only the
fields of §5 are stored: no location, device data, derived values, analytics events or third-party
SDKs. Notes are free text the user may fill with anything; they are treated as the most sensitive
field (never logged, never in notifications, never sent to AI).

### 9.2 Threats

| # | Threat (asset → actor) | Mitigation in this design | Residual |
|---|---|---|---|
| T-1 | **Notification preview** on lock screen / shared screen | Generic copy identical to a generic reminder; no id; reminder off by default | Someone sees that "a reminder" exists |
| T-2 | **Push provider** (Google FCM) learns health context | Neutral type `private_reminder`, no id, no text beyond the generic copy | Timing of an opted-in reminder is visible to Google |
| T-3 | **Device in someone else's hands** (unlocked phone) | No Home card, dock or quick-add entry; module only in More while enabled; nothing cached on disk | **Medium**: no app lock or `FLAG_SECURE` in v1 (§12) |
| T-4 | **Recents thumbnail / screenshots** | — | Not blocked in v1 (§12) |
| T-5 | **Account switching on one device** | Device registrations are per (installation, user) and the previous owner's row becomes Inactive (ADR-012 WP3A), so new deliveries go only to the signed-in user's devices; payload has no id or user; the tap re-checks the *current* account's settings; cycle state must live only in page components (no singleton or persistent store) and must be cleared on sign-out | A notification already in the tray stays visible after a switch (generic text only) |
| T-6 | **Another LifeOS user** reads or changes records | `UserId` from the token only, explicit in every handler/repository, 404 for foreign ids, DB `user_id NOT NULL` + FK, isolation tests at three levels | Low |
| T-7 | **Application logs** | No record values in log messages, exceptions or validation messages; `Microsoft.AspNetCore` at Warning; no request-body logging | Low |
| T-8 | **Platform request logs / proxies** (Render) | No record values in paths or queries (D-12); only ids and navigation ranges | Paths reveal that cycle endpoints are used — **VERIFY** what Render retains |
| T-9 | **External AI providers** (Groq, OpenAI, Google) | **Default and only option: no.** No Cycle reference from any AI path; architecture tests; no eval data | Depends on keeping the tests |
| T-10 | **Exports** | Explicit user action, warning, no identity in the file, cache copy deleted after sharing | The shared file is outside LifeOS's control |
| T-11 | **Backups** | Encrypted off-site backups (backup-restore §2); disclosure to the user | Deleted records survive in backups up to their retention (§10.3) |
| T-12 | **Retention** | Records kept until the user deletes them; reminder rows deleted on disable/delete | Automation/delivery rows of an active reminder follow PD-5 (13 months) |
| T-13 | **Database / operator access** (owner, leaked connection string) | Secrets handling per runbook; Neon encryption at rest; TLS | **Medium**: no app-level encryption (§12) |
| T-14 | **Consent / activation** | Opt-in only, default off, explicit screen (§4.3), no gender inference (§4.1) | Legal sufficiency unverified (§13) |
| T-15 | **Misuse of estimates** for contraception or medical decisions | Window not day, minimum data, fixed disclaimer, no fertility features, no clinical words | Cannot be fully prevented |
| T-16 | **Overlap race** bypassing the per-user lock | Lock in the only write path, DB backstops | Low |

### 9.3 AI exclusion (machine-enforced)

No Cycle type is referenced by `ActionAgent`, `WeeklyReviews`, Journal memory, AI service clients or
any Python-facing contract; the Python service has no endpoint or tool that reaches cycle data.
Cycle notes are not journal entries and are never indexed or embedded. No cycle data, synthetic or
not, enters `tools/ai-evals`.

### 9.4 Reminder rows on disable

Disabling the module or the reminder deletes, in the same transaction, the user's `CycleReminder`
deliveries (any status) and `CycleUpcomingPeriodReminder` executions, so `automation_executions` does
not keep a timeline of estimated cycles for a user who opted out. The deletion is by
`(user_id, automation_type)` / `(user_id, notification_type)`: generic operations on the core stores,
so the core still knows no module.

## 10. Deletion, export, backup

### 10.1 What each deletion does

| Action | Effect on the **live database** |
|---|---|
| Delete a day log / a period | Hard delete of that row. Deleting a period does not touch day logs. |
| Disable module | Records kept; reminder executions/deliveries deleted (§9.4). |
| **Delete all cycle data** | One transaction: the user's `cycle_day_logs`, `cycle_periods`, `cycle_tracker_settings`, `CycleReminder` deliveries (any status) and `CycleUpcomingPeriodReminder` executions. Idempotent (204 when nothing exists). Afterwards the API and the App behave exactly as for a user who never enabled the module. |
| User deletion (future) | FK cascade removes every cycle row. |

### 10.2 What "Delete all" does **not** remove

"Delete all" acts on the **live Production database only**. It does not and cannot reach:

| Copy | Where | How long |
|---|---|---|
| Independent backups | encrypted `pg_dump` files (backup-restore §1–2) | until rotated out: 7 daily, 4 weekly, 12 monthly ⇒ **up to about 13 months** |
| Provider history | Neon point-in-time history of the branch | provider-defined window — **VERIFY** the current Neon plan |
| Exported files | wherever the user saved or shared them | outside LifeOS |
| Notifications already shown | the device's notification tray | until dismissed (generic text only) |

The delete confirmation dialog states both parts:

> "This permanently deletes all your cycle records from LifeOS. It cannot be undone.
> Copies in encrypted backups are not changed and are removed as backups expire (up to about 13
> months). Files you exported are not affected."

### 10.3 Backups and restore

- Cycle tables are included in the regular `pg_dump`; no change to the procedure. Migration PRs add
  them to the row-count checks of backup-restore §4.2.
- **Restore resurrection:** a disaster restore (backup-restore §5) brings back records deleted after
  the backup. No deletion log is kept (it would itself be data). The runbook step added with PR 1
  says to repeat the deletions after a restore when they happened after the backup date.
- Excluding cycle **data** from backups (`pg_dump --exclude-table-data='cycle_*'`) would make erasure
  immediate at the cost of recoverability: owner decision O-7.

### 10.4 Export

- `GET /api/cycle/export` returns the JSON of §7.2 (`SchemaVersion = 1`), all records, ordered by date.
- App: Settings → Cycle tracker → "Export my cycle data": the file is written to the app cache
  directory, handed to the system share sheet (`Share.RequestAsync(ShareFileRequest)`, MAUI built-in,
  no package) and **deleted from the cache** when the share sheet returns. The screen warns that the
  file is unencrypted and leaves LifeOS's protection. Import is deferred.
