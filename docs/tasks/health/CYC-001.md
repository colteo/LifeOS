# CYC-001 — Cycle Tracker (design)

Status: DESIGN ONLY — approved for design, not implemented. No code, migration, configuration or
deployment change is part of this document. GitHub issue: [#43](https://github.com/colteo/LifeOS/issues/43).

Builds on [ADR-006](../../adr/0006-external-identity-authentication-and-user-owned-data.md) (identity,
per-user ownership), [ADR-012](../../adr/0012-server-side-automation-and-push-notifications.md) and
[AUTO-003A](../automation/AUTO-003A.md) (automation, push, quiet hours), [JRN-001](../journal/JRN-001.md)

## 1. Goal and non-goals

An **optional, private** module in which a user records their menstrual periods and, if they wish,
daily flow, symptoms and notes; sees them on a calendar and in an editable history; and, if they
opt in, sees a deterministic, explicitly uncertain estimate of the next period start and receives a
discreet reminder.

The module is useful on its own, is **off by default**, and when off leaves no trace in the app
except one switch in Settings.

Non-goals (v1, deliberately excluded):

| Excluded | Why |
|---|---|
| Fertility window, ovulation, "safe days", contraception, pregnancy mode | Explicitly out of scope. A calendar estimate is not reliable enough for any of these and must never be presented as if it were. |
| Any AI: diagnosis, interpretation, prediction, summaries, chat over cycle data | Explicitly out of scope. Estimates are deterministic arithmetic (AGENTS.md "Deterministic software computes"). |
| Clinical language ("late", "irregular", "abnormal", conditions, advice) | LifeOS is not a medical device. Wording stays descriptive (§7.4). |
| Basal temperature, test results, sexual activity, medication, mood scales | Data minimisation: not needed for the stated goal. |
| Free-form custom symptoms | A fixed catalogue + the note covers v1 (§5.3). |
| Integration with other modules, Weekly Review, Home card, Journal RAG | Isolation by design (§9.4). |
| Sharing with a partner/clinician, multi-device offline sync, widgets, wearables | Out of scope. |
| Application-level field encryption, app lock / PIN | Deferred (§12), with the residual risk stated. |

## 2. Product decisions

| # | Decision |
|---|---|
| P-1 | **Opt-in only.** The module is disabled for every user until the user enables it. Offered once at the end of onboarding and always available in Settings. |
| P-2 | **Periods are explicit records** (start date, optional end date). Daily logs never create or end a period implicitly. |
| P-3 | **Dates are local calendar dates** (`DateOnly`), never instants: a period starts on a day, not at a time. Changing time zone never moves a logged day. |
| P-4 | **Everything is editable and deletable**: any period, any day log, at any time. Deletes are hard deletes. |
| P-5 | **Estimates are opt-in, deterministic, a window, never a day**, always shown with the number of cycles they are based on and a fixed disclaimer. Too little data ⇒ no estimate. |
| P-6 | **One reminder type**, off by default, requires estimates, subject to quiet hours, with **generic copy and a generic payload** that reveal nothing about the module. |
| P-7 | **No Home card, no dock entry, no quick-add entry.** The module appears in More only while enabled. |
| P-8 | **Disable keeps data; Delete erases it.** Disabling hides the module and stops reminders. A separate, explicit action deletes all cycle data immediately. Both are offered together when disabling. |
| P-9 | **Export** of all the user's cycle records as JSON, on demand. |
| P-10 | **Cycle data never leaves the .NET API boundary towards AI**: not sent to the Python service, not in Weekly Review, not in the Action Agent, not indexed by Journal memory, not in evaluation datasets. Machine-enforced by architecture tests (§11.4). |

## 3. Design decisions

| # | Decision | Why |
|---|---|---|
| D-1 | **New module `Cycle`** in every layer (`Domain/Cycle`, `Application/Cycle`, `Contracts/Cycle`, `Infrastructure/.../Cycle`, `Api/Cycle`, `App/.../Cycle`), routes under `/api/cycle`, app routes under `/cycle`. Grouped with health topics in docs only (`docs/tasks/health/`). | Same per-feature layout as Journal, Gym, Nutrition. No "Health" umbrella abstraction until a second health module exists. |
| D-2 | **Module settings = `cycle_tracker_settings`, one optional row per user** (`user_id` PK). **No row ⇒ disabled.** | Same shape as AUTO-002 `weekly_review_settings` and AUTO-003A `notification_preferences`, but default-off. No column on `users`, no generic module/feature-flag framework. |
| D-3 | **The cycle reminder flag lives in `cycle_tracker_settings`, not in `notification_preferences`.** | A module-owned setting, like Weekly Review. Keeps every cycle-related fact in the module's own tables so "Delete all cycle data" is one place, and keeps a health flag out of a generic table. Quiet hours (a user-level concern) still come from the Notifications core. |
| D-4 | **Two record tables: `cycle_periods` and `cycle_day_logs`**, independent. | Periods answer "when", day logs answer "how". Spotting outside a period is allowed; a period without day logs is normal. Editing one never rewrites the other. |
| D-5 | **Symptoms are a fixed catalogue of stable codes stored as `text[]`** with a check constraint. | One row per day, no join table, readable export; the catalogue is closed so the check is exact. Npgsql maps `string[]`/primitive collections natively (no new package). |
| D-6 | **Estimates are computed on read by a pure Domain service (`CycleEstimator`)**, never stored. | Always consistent with edited history; nothing derived to delete or to leak; trivially unit-testable. |
| D-7 | **Per-user write serialisation by locking the user's `cycle_tracker_settings` row (`SELECT … FOR UPDATE`)** in period writes, then checking overlap in Application. | No-overlap across rows cannot be a simple unique index; an exclusion constraint would need the `btree_gist` extension (new infrastructure). The settings row always exists while the module is enabled, so it is a natural per-user lock. DB backstops: unique start per user, at most one open period per user, end ≥ start. |
| D-8 | **Module gate in Application:** every record use case first loads the settings; disabled ⇒ `CycleTrackerDisabled` ⇒ HTTP **409**. Settings, export and delete-all work in any state. | One rule, testable without HTTP; the user can always see, export and erase their data. 409 matches the existing "state conflict" convention (Accounts, Categories, Action Agent). |
| D-9 | **Onboarding: client-side optional step, no `OnboardingStatus` change.** After `CompleteOnboarding` succeeds, the app shows an "Optional modules" screen once (in-memory navigation, no persisted flag); "Not now" is the default action. | Adding a server onboarding state would force a state-machine change and a migration for every user to offer something optional. Existing users enable from Settings. Nothing is stored when the user declines. |
| D-10 | **Reminder = automation handler `CycleUpcomingPeriodReminder`** in `Application/Cycle/Reminders`, `NotificationType.CycleReminder`, FCM payload `type=private_reminder` with **no id**. | Reuses ADR-012 exactly (claim = insert, outbox, quiet hours). The payload type is neutral because FCM (Google) sees it. |
| D-11 | **All cycle responses carry `Cache-Control: no-store`.** The app keeps cycle data in memory only (no `Preferences`, no SQLite, no file cache). | Nothing persists on the device except what the user explicitly exports. |
| D-12 | **No new ADR in this document; an ADR is proposed for PR 1** ("Sensitive personal modules: opt-in, AI exclusion, neutral notifications, hard deletion"). | The rules in §9 are cross-cutting and will apply to future health modules; they belong in an ADR, not only in a task file. |

## 4. Activation lifecycle

```text
          (no row)                     PUT settings {enabled:true}
   ┌────────────────────┐  ──────────────────────────────────────►  ┌─────────────────────┐
   │ Disabled (default) │                                            │ Enabled             │
   │ module hidden      │  ◄──────────────────────────────────────  │ More → Cycle        │
   └────────────────────┘     PUT settings {enabled:false}           └─────────────────────┘
            ▲                 (data kept, reminders stopped)                  │
            │                                                                 │
            └──────────── DELETE /api/cycle/data (any state) ◄────────────────┘
                          all rows of the user deleted, settings row included ⇒ back to "no row"
```

- **Enable** creates or updates the settings row: `enabled = true`, `enabled_at_utc = now`
  (first enable or re-enable), defaults `estimates_enabled = false`, `reminder_enabled = false`
  unless the activation screen sets them.
- **Disable** sets `enabled = false`, keeps periods and day logs, and in the same transaction deletes
  the user's pending/sending `CycleReminder` deliveries and their `CycleUpcomingPeriodReminder`
  automation executions (§9.6). Re-enabling shows the old data again.
- **Delete all** (§10.1) removes the settings row too: the user is exactly as if they had never
  enabled the module.
- The activation screen states, before the user enables anything: what is stored, that it is
  private to their account, that nothing is sent to AI, that estimates are not medical advice and
  not for contraception, and how to delete everything. This is the user's explicit consent; the
  timestamp is `enabled_at_utc`.

## 5. Domain model (`LifeOS.Domain.Cycle`)

Framework-free, no EF attributes, ids `Guid.CreateVersion7()`, timestamps supplied by Application
(`TimeProvider`), validation failures as `ArgumentException` like the other modules.

### 5.1 `CycleTrackerSettings`

| Field | Meaning |
|---|---|
| `UserId` | Owner and key. |
| `Enabled` | Module on/off. |
| `EstimatesEnabled` | Show the next-start estimate. |
| `ReminderEnabled` | Upcoming-period reminder. **Invariant:** `ReminderEnabled ⇒ EstimatesEnabled` (the reminder is derived from the estimate). |
| `EnabledAtUtc` | Last time the module was enabled (consent timestamp). |
| `UpdatedAtUtc` | Last change. |

`Default(userId)` is the disabled, never-saved state (like `NotificationPreferences.Default`).
`Update(enabled, estimates, reminder, now)` enforces the invariant; enabling stamps `EnabledAtUtc`.

### 5.2 `CyclePeriod`

| Field | Meaning |
|---|---|
| `Id`, `UserId` | Identity, owner (never from a request). |
| `StartDate` | `DateOnly`, required. |
| `EndDate` | `DateOnly?`; `null` = period in progress. |
| `Note` | Optional, trimmed, ≤ 500 chars, blank ⇒ `null`, never truncated. |
| `CreatedAtUtc`, `UpdatedAtUtc` | Application clock. |

Rules (Domain, given `today` = the user's local date, supplied by Application):

- `StartDate ≥ 2000-01-01` and `StartDate ≤ today + 1` (one day of tolerance for a device/server
  zone mismatch). No future planning.
- `EndDate`, when present: `StartDate ≤ EndDate ≤ today + 1` and inclusive length
  `EndDate − StartDate + 1 ≤ 20` days. Longer ⇒ 400 (the user probably forgot to close an earlier
  period; the message says so neutrally).
- **Open period:** creating or editing a period with no end requires `StartDate ≥ today − 19`. An
  open period that becomes older than 20 days stays valid in storage and is shown as "needs an end
  date"; estimates still use its start.
- `Update(start, end, note, today, now)` is a full replacement; an invalid update changes nothing.
- `End(endDate, today, now)` is the "Period ended" shortcut on an open period.

Per-user rules (Application, under the D-7 lock, DB backstop where possible):

- periods of one user **never overlap** (inclusive ranges; an open period extends to `today` for
  the check);
- at most **one open period** per user;
- an open period must be the **latest** period (no period may start after an open one).

### 5.3 `CycleDayLog`

| Field | Meaning |
|---|---|
| `Id`, `UserId` | Identity, owner. |
| `Date` | `DateOnly`, unique per user, same range rules as `StartDate`. |
| `Flow` | `FlowIntensity?`: `Spotting`, `Light`, `Medium`, `Heavy`; `null` = not recorded. |
| `Symptoms` | Set of `CycleSymptom` (closed catalogue, de-duplicated, stored sorted). |
| `Note` | Optional, ≤ 1 000 chars, same normalisation as above. |
| `CreatedAtUtc`, `UpdatedAtUtc` | Application clock. |

`CycleSymptom` catalogue (stable codes; UI labels are localised presentation):
`Cramps`, `Headache`, `Bloating`, `BreastTenderness`, `BackPain`, `Acne`, `Fatigue`, `Nausea`,
`Cravings`, `SleepChanges`, `MoodChanges`. Adding a symptom later = one enum value + one check
constraint change (a migration).

Rules: a day log must carry **something** (flow, at least one symptom, or a note); saving an empty
log is the same as deleting it (the API's `PUT` with nothing deletes; §8). A flow recorded outside
any period is allowed (spotting) and does **not** create a period (P-2).

### 5.4 `CycleEstimator` (pure Domain service)

Input: the user's periods (start dates, end dates), `today`. Output: `CycleEstimate`, one of:

| Result | When | Shown as |
|---|---|---|
| `Unavailable(InsufficientData, validCycles)` | fewer than **3** valid cycle lengths | "Log a few more periods to see an estimate" |
| `Available(windowStart, windowEnd, typicalCycleLength, typicalPeriodLength?, cyclesUsed, variability)` | otherwise, and `today ≤ windowEnd` | a dashed window on the calendar + text (§7.4) |
| `WindowPassed(windowStart, windowEnd, cyclesUsed)` | `today > windowEnd` and no newer period | neutral text, no alert, no reminder |

Algorithm (deterministic, documented to the user in the "How is this estimated?" sheet):

1. Sort periods by `StartDate`. **Cycle length** `Lᵢ = Start(i+1) − Start(i)` in days, for each
   consecutive pair.
2. Keep the **most recent 6** lengths whose later start is within the last 12 months; drop lengths
   **< 15 or > 90 days** (most likely a missing or duplicate record). Dropped lengths are still
   shown in History; they are only excluded from the estimate.
3. Fewer than 3 kept ⇒ `Unavailable`.
4. `M = median(L)`, `m = min(L)`, `X = max(L)`, `last = latest StartDate`.
   - `windowStart = last + min(m, M − 2)`
   - `windowEnd = last + max(X, M + 2)`
   - The window is therefore **at least 5 days wide** and widens with the observed spread.
5. `variability = X − m`. When `variability > 9` the estimate carries a `Wide` flag, shown as
   "Your logged cycles vary, so this window is less reliable". Never labelled clinically.
6. `typicalPeriodLength = median(End − Start + 1)` over the most recent 6 closed periods, or `null`
   with fewer than 3. Informational text only; no estimated period days are drawn.
7. Only the **next** start is estimated. No multi-month projection.

The estimator never reads day logs, symptoms or notes.

## 6. Persistence (PostgreSQL, EF Core in Infrastructure only)

Explicit EF configurations, snake_case, `timestamptz` UTC, `date` for calendar days, enum-like values
as strings. All tables are **user-owned leaf data**: `user_id NOT NULL`, FK → `users(id) ON DELETE
CASCADE` (ADR-006; also covers a future account deletion).

```text
cycle_tracker_settings
  user_id            uuid        PK, FK -> users(id) ON DELETE CASCADE
  enabled            boolean     NOT NULL
  estimates_enabled  boolean     NOT NULL
  reminder_enabled   boolean     NOT NULL              (added by PR 5)
  enabled_at_utc     timestamptz NULL
  updated_at_utc     timestamptz NOT NULL
  ck_cycle_tracker_settings_reminder   NOT reminder_enabled OR estimates_enabled

cycle_periods
  id              uuid          PK
  user_id         uuid NOT NULL FK -> users(id) ON DELETE CASCADE
  start_date      date NOT NULL
  end_date        date NULL
  note            varchar(500) NULL
  created_at_utc  timestamptz NOT NULL
  updated_at_utc  timestamptz NOT NULL
  ux_cycle_periods_user_start       UNIQUE (user_id, start_date)
  ux_cycle_periods_user_open        UNIQUE (user_id) WHERE end_date IS NULL
  ck_cycle_periods_range            end_date IS NULL OR (end_date >= start_date AND end_date - start_date <= 19)
  ck_cycle_periods_start            start_date >= '2000-01-01'
  ck_cycle_periods_note             note IS NULL OR length(btrim(note)) > 0

cycle_day_logs
  id              uuid          PK
  user_id         uuid NOT NULL FK -> users(id) ON DELETE CASCADE
  log_date        date NOT NULL
  flow            varchar(16) NULL
  symptoms        text[] NOT NULL DEFAULT '{}'
  note            varchar(1000) NULL
  created_at_utc  timestamptz NOT NULL
  updated_at_utc  timestamptz NOT NULL
  ux_cycle_day_logs_user_date       UNIQUE (user_id, log_date)
  ck_cycle_day_logs_flow            flow IS NULL OR flow IN ('Spotting','Light','Medium','Heavy')
  ck_cycle_day_logs_symptoms        symptoms <@ ARRAY['Cramps',…,'MoodChanges']::text[]
  ck_cycle_day_logs_not_empty       flow IS NOT NULL OR cardinality(symptoms) > 0 OR note IS NOT NULL
  ck_cycle_day_logs_note            note IS NULL OR length(btrim(note)) > 0
```

Notes:

- `ux_cycle_periods_user_start` makes "one period per start date" a DB rule. Because the start
  date is unique per user, `start_date DESC` is a total order: history keyset paging and the
  estimator's "last 7 starts" read are backward range scans of this index with no sort.
- Overlap is enforced in Application under the D-7 lock (no `btree_gist`); the residual risk of a
  bypass is limited to code that skips the use case, which architecture and persistence tests cover.
- No column holds a derived estimate, a cycle day number or anything AI-related.
- Calendar reads use `(user_id, log_date)` and `(user_id, start_date)` range scans.
- **Migrations** (one per PR that changes schema; none is created by this document):
  `AddCycleTracker` (settings + periods, PR 1), `AddCycleDayLogs` (PR 2),
  `AddCycleReminderSetting` (PR 5). Each `Down` drops only what its `Up` created.

Repository ports (Application), all with an explicit `userId` (ADR-006, no ambient user, no global
query filter as the primary mechanism):

```text
ICycleSettingsRepository   GetAsync(userId) · GetForUpdateAsync(userId) · UpsertAsync(settings)
ICyclePeriodRepository     ListRecentStartsAsync(userId, max) · GetPageAsync(userId, limit, cursor)
                           GetAsync(userId, id) · ListInRangeAsync(userId, from, to)
                           AddAsync · UpdateAsync · DeleteAsync(userId, id)
ICycleDayLogRepository     GetAsync(userId, date) · ListInRangeAsync(userId, from, to)
                           UpsertAsync · DeleteAsync(userId, date)
ICycleDataEraser           DeleteAllAsync(userId)            // one transaction, §10.1
ICycleReminderRepository   (PR 5) candidate users per zone, reminder cleanup
```

## 7. API (`LifeOS.Api/Cycle/CycleEndpoints.cs`)

All routes `RequireAuthorization` (listed in `EndpointAuthorizationHttpTests`). The owner is the
token's `UserId`; contracts contain no user id (an extra `userId` is ignored). Another user's record
is indistinguishable from a missing one (404). Every response sets `Cache-Control: no-store`.
Validation failures are `ValidationProblem` (400) keyed by field, **with fixed messages that never
echo submitted values**. Enum-like values are strings.

### 7.1 Endpoints

| Method | Route | Success | Errors |
|---|---|---|---|
| `GET` | `/api/cycle/settings` | 200 `CycleSettingsResponse` (defaults when no row) | — |
| `PUT` | `/api/cycle/settings` | 200 `CycleSettingsResponse` | 400 (reminder without estimates, missing fields) |
| `GET` | `/api/cycle/overview` | 200 `CycleOverviewResponse` | 409 disabled |
| `GET` | `/api/cycle/calendar?from=&to=` | 200 `CycleCalendarResponse` | 400 range (`from ≤ to`, ≤ 93 days), 409 |
| `GET` | `/api/cycle/periods?limit=&cursor=` | 200 `CyclePeriodPageResponse` | 400 `limit`/`cursor`, 409 |
| `GET` | `/api/cycle/periods/{id}` | 200 `CyclePeriodResponse` | 404, 409 |
| `POST` | `/api/cycle/periods` | 201 `CyclePeriodResponse` + `Location` | 400 fields/overlap/open-period, 409 |
| `PUT` | `/api/cycle/periods/{id}` | 200 `CyclePeriodResponse` | 400, 404, 409 |
| `DELETE` | `/api/cycle/periods/{id}` | 204 | 404, 409 |
| `GET` | `/api/cycle/days/{date}` | 200 `CycleDayLogResponse` | 404 (no log), 400 date, 409 |
| `PUT` | `/api/cycle/days/{date}` | 200 `CycleDayLogResponse`, or **204** when the body is empty-of-content (log deleted) | 400, 409 |
| `DELETE` | `/api/cycle/days/{date}` | 204 | 404, 409 |

- Overlap and "only one open period" are **400** with field `startDate`/`endDate` and a neutral
  message ("This overlaps another period"), not 409: they are input errors the user fixes in the form.
- Module disabled is **409** problem "Cycle tracker is not enabled." (D-8).
- `{date}` is ISO `yyyy-MM-dd`; anything else is 400.
- History paging: keyset, `limit` 1–50 (default 20), order `start_date DESC` (unique per user),
  opaque cursor `"<start day number>"`, malformed cursor ⇒ 400 (JRN-001 convention).
- "Today" for date rules = `users.time_zone_id` local date, UTC when the zone is unknown (D-3 of
  AUTO-003A: the zone follows the device).

`CycleLengthDays` on a period is the distance to the next period's start (null for the latest), shown

estimates, no user id, email or display name (the file should not identify the account by itself).

### 7.3 Application use cases (`LifeOS.Application.Cycle`)

Plain handler classes, no mediator, `TimeProvider` for `now`, user zone for `today`:

`GetCycleSettings`, `UpdateCycleSettings` (enable/disable + reminder cleanup on disable),
`GetCycleOverview`, `GetCycleCalendar`, `GetCyclePeriodsPage`, `GetCyclePeriod`, `CreateCyclePeriod`,
`UpdateCyclePeriod`, `DeleteCyclePeriod`, `GetCycleDayLog`, `PutCycleDayLog`, `DeleteCycleDayLog`,
`ExportCycleData`, `DeleteAllCycleData`, and (PR 5) `CycleUpcomingPeriodReminderHandler`.

Expected failures are results (`NotFound`, `Disabled`, `Invalid(field, message)`), mapped to HTTP by
the endpoint module; no business logic in endpoints.

### 7.4 Wording of estimates (fixed, part of the contract tests of the App)

- Available: "Next period estimated between **14 and 20 Nov**. Based on your last **5** cycles."
- Always beneath it: "An estimate from your own history, not medical advice. Do not use it for
  contraception or to plan or avoid pregnancy."
- Wide: "Your logged cycles vary, so this window is less reliable."
- WindowPassed: "No period has been logged since the estimated window (14–20 Nov). Estimates are
  only as complete as your history."
- Unavailable: "Log at least 4 periods to see an estimate."
- Never: "late", "overdue", "irregular", "fertile", "ovulation", "safe", percentages or a single
  predicted day.

## 8. Reminders (PR 5)

| Item | Value |
|---|---|
| Handler | `CycleUpcomingPeriodReminderHandler : IAutomationHandler`, `Application/Cycle/Reminders` |
| `automation_type` | `CycleUpcomingPeriodReminder` |
| Condition | settings `enabled ∧ estimates_enabled ∧ reminder_enabled`; estimate `Available`; local date D = `windowStart − 2` |
| Due | 09:00 local on D via `LocalSchedule.ResolveDaily`; lateness 24 h (AUTO-003A D-8) |
| Occurrence key | `<latest period id>` — at most **one reminder per cycle**. Editing dates cannot remind twice; a newly logged period starts a new cycle with a new key. |
| Discovery | zone buckets of users with the reminder enabled (ids-only SQL), then the estimate is computed **in Application** for those candidates (last 7 starts each) and only users whose D is today are returned. Bounded by the tick `limit`. |
| Execution | re-reads settings and periods; any condition false ⇒ `NotApplicable`. No artifact. |
| Notification | `NotificationType.CycleReminder`, a **reminder** for `NotificationCatalog.IsReminder` ⇒ quiet hours apply (AUTO-003A R-1/D-4), delivery expiry 24 h. `ResourceType`/`ResourceId` = none. |
| Copy | title `LifeOS`, body `You have a reminder` — no word about cycle, period, health or dates (also on the lock screen). |
| FCM data | `type=private_reminder`, **no id**. |
| Tap | `NotificationTap.PathFor("private_reminder")` → `/cycle` through `AuthGate`; module disabled ⇒ Home. |

The reminder never creates, ends or edits a period. The "open period for more than N days" nudge is
deferred (§12).

## 9. Privacy and security design

### 9.1 Data classification

Menstrual data is **health data** (GDPR art. 9 special category). LifeOS today is a personal
application with a Production allowlist (ADR-006 amendment), so the data subject and the operator are
the same person. If LifeOS ever serves other people, a DPIA, a privacy notice and an explicit legal
basis review are **required before** enabling this module for them (§13).

### 9.2 Minimisation

Only: period dates, optional flow, symptoms from a closed list, optional notes, three booleans and
two timestamps. No location, no device data, no derived values stored, no analytics events, no
third-party SDK.

### 9.3 Isolation between users (ADR-006)

- `UserId` only from the access token, passed explicitly to every handler and repository method.
- Every query filters by `user_id`; cross-user ids ⇒ 404 identical to missing.
- DB backstops: `user_id NOT NULL`, FK cascade, per-user unique indexes. There are no references
  between cycle rows (periods and day logs are independent), so no composite FK is needed.
- Tests prove isolation at Application, PostgreSQL and HTTP levels (§11).

### 9.4 AI exclusion (P-10)

- No Cycle type is referenced by `ActionAgent`, `WeeklyReviews`, Journal memory, the AI service
  clients or any Python-facing contract; the Python service has no endpoint or tool that can reach
  cycle data. Enforced by architecture tests.
- Cycle notes are **not** journal entries and are never indexed or embedded.
- No cycle data in `tools/ai-evals` datasets or prompts, synthetic or not.

### 9.5 Logs, errors, telemetry

- No log line contains dates, flow, symptoms or notes; logs may contain the route template, status
  and the opaque user id already logged today. Validation messages are fixed text.
- Unexpected exceptions keep the existing behaviour (no details in responses); handlers do not put
  record values into exception messages.
- OpenAPI remains Development-only. No request-body logging is introduced.

### 9.6 Notifications and push

- Generic copy, neutral FCM type, no id, quiet hours (§8). Google (FCM) sees only that a LifeOS
  reminder exists.
- Disabling the module or the reminder deletes the user's pending `CycleReminder` deliveries and
  their `CycleUpcomingPeriodReminder` executions in the same transaction, so `automation_executions`
  (13-month retention, PD-5) does not keep a timeline of estimated cycles of a user who opted out.
  Deletion is by `(user_id, automation_type)` / `(user_id, notification_type)`: generic operations on
  the core stores, so the core still knows no module.

### 9.7 Device

- Cycle screens are reachable only through More and Settings while enabled; no Home card, no dock,
  no quick-add (P-7). Nothing on Home reveals that the module exists.
- Data is held in memory by the page components; never written to `Preferences`, `SecureStorage`,
  SQLite or files, except the export file the user explicitly creates (§10.2).
- Screenshots / recents thumbnails are not blocked in v1 (deferred: `FLAG_SECURE` on cycle routes).

### 9.8 Transport and storage

TLS end to end (Render), Neon encryption at rest, encrypted off-site backups per
[backup-restore](../../operations/backup-restore.md). No application-level encryption in v1 (deferred,
§12): anyone with database access (the owner/operator, or an attacker with the connection string)
can read cycle rows, as for every other LifeOS module.

## 10. Deletion, export, backup

### 10.1 Deletion

| Action | Effect |
|---|---|
| Delete a day log / a period | Hard delete of that row (P-4). Deleting a period does not touch day logs. |
| Disable module | Data kept; reminder executions/deliveries deleted (§9.6). |
| **Delete all cycle data** | One transaction: `cycle_day_logs`, `cycle_periods`, `cycle_tracker_settings` of the user, plus their `CycleUpcomingPeriodReminder` executions and `CycleReminder` deliveries. Idempotent (204 when nothing exists). Confirmation dialog in the App with the explicit text "This permanently deletes all your cycle records. It cannot be undone." |
| User deletion (future) | FK cascade removes every cycle row. |

### 10.2 Export

- `GET /api/cycle/export` returns the JSON of §7.2 (`SchemaVersion = 1`), all records, ordered by date.
- App: Settings → Cycle tracker → "Export my cycle data": the file is written to the app cache
  directory, handed to the system share sheet (`Share.RequestAsync(ShareFileRequest)`, MAUI built-in,
  no package) and **deleted from the cache** when the share sheet returns. The screen warns that the
  exported file is unencrypted and leaves LifeOS's protection.
- Import is deferred (§12).

### 10.3 Backup and restore

- Cycle tables are included in the regular `pg_dump` (no change to the procedure). PR 1 adds them
  to the row-count checks of backup-restore §4.2 and to the runbook part for the migration.
- **Deletion vs backups (residual risk):** a hard delete removes data from the live database
  immediately but not from backups already taken; under the documented retention (7 daily, 4
  weekly, 12 monthly) a deleted record can survive in an encrypted backup for **up to ~13 months**.
  The activation screen and the delete dialog say so in one sentence.
- **Restore resurrection:** a disaster restore (backup-restore §5) brings back records deleted after
  the backup. No deletion log is kept (it would itself be data); the runbook step added in PR 1 says
  to repeat "Delete all cycle data" (or the specific deletions) after a restore when they happened
  after the backup date.
- Option for the owner, not decided here: exclude cycle table **data** from backups
  (`pg_dump --exclude-table-data='cycle_*'`), trading recoverability for erasure. Deferred (§12).

## 11. Tests

Synthetic data only (AGENTS.md). Inner loop with `--filter FullyQualifiedName~Cycle`.

### 11.1 Unit (`LifeOS.UnitTests.Cycle`)

- **Settings:** default disabled; enable stamps `EnabledAtUtc`; reminder without estimates rejected;
  disable keeps flags consistent.
- **Period:** start/end ranges, 20-day max, open-period age rule, `today + 1` tolerance, note
  trimming/limit without truncation, full-replacement update, invalid update atomic, `End`.
- **Day log:** flow parsing (strings, case rules like Accounts), closed symptom catalogue, duplicates
  removed, sorted, empty ⇒ delete semantics, note limits.
- **Estimator (table-driven):** < 3 cycles; exactly 3; 6 most recent only; 12-month cut-off;
  outliers 14/91 dropped and 15/90 kept; median for even/odd counts; window minimum width 5; wide
  flag at variability 9 vs 10; `WindowPassed`; open period as last start; leap years and month ends;
  never reads day logs.
- **Handlers:** ownership on every use case; disabled ⇒ `Disabled` everywhere except settings/export/
  delete-all; overlap/open-period checks including an open period extending to today; history paging
  walk and stability; calendar range limits; delete-all removes everything and is idempotent;
  disable deletes reminder rows; today from user zone vs UTC fallback (`FixedTimeProvider`).
- **Reminder (PR 5):** discovery picks only D = windowStart − 2 in open zones; key = latest period id;
  NotApplicable on any changed condition; copy and payload contain no module words and no id;
  quiet hours apply.

### 11.2 PostgreSQL (`LifeOS.IntegrationTests`, `CyclePersistenceTests`)

Migration/schema (columns, types, indexes, FK cascade, every check constraint, no pending model
changes); round trips including `text[]` symptoms; unique start and single open period backstops;
D-7 lock serialises two concurrent overlapping creates (one fails); ownership filters; keyset
paging with PostgreSQL ordering; range reads use the indexes; delete-all in one transaction; user
cascade.

### 11.3 HTTP (`CycleHttpTests`)

Authentication on every route; CRUD; 409 when disabled; settings/export/delete-all when disabled;
cross-user 404 identical to missing; ignored `userId`; validation fields; error bodies contain no
submitted values; `Cache-Control: no-store` on every cycle response; export content type, filename
and absence of user id/email; calendar range validation.

### 11.4 Architecture (`CycleModuleArchitectureTests`)

- Cycle namespaces of every layer depend on no other business module and not on `System.Net.Http`.
- **No type in `ActionAgent`, `WeeklyReviews`, Journal memory or any AI client namespace depends on
  a `Cycle` namespace** (P-10).
- The automation/notification core does not depend on `Cycle` (ADR-012 module boundary).

### 11.5 App

Component/service tests following the existing App test conventions: More shows Cycle only when
enabled; onboarding optional-module step defaults to "Not now" and stores nothing; estimate wording
(§7.4) including the disclaimer; tap mapping `private_reminder` → `/cycle` or Home when disabled;
export file deleted after sharing. Physical-phone acceptance checklist in the App PR (enable,
log, edit, calendar, estimate, disable, delete all, notification on the lock screen).

## 12. Deferred improvements

- Application-level encryption of notes (or all cycle columns) with a server-side key.
- App lock (biometric/PIN) and `FLAG_SECURE` on cycle routes.
- "Period still open after N days" nudge; user-chosen reminder time and lead days.
- Import of an export file / from other apps.
- Excluding cycle data from backups (§10.3) and a shorter retention for executions.
- Custom symptoms; localisation of symptom labels beyond the App's current language.
- A Health umbrella in More if a second health module appears.
- Fertility/contraceptive features: **not planned**; would require a dedicated product, legal and
  safety review, not an increment.

## 13. Risks and residual risks

| Risk | Mitigation in this design | Residual |
|---|---|---|
| Another user sees cycle data | Explicit `UserId`, per-query filtering, 404 for foreign ids, DB constraints, 3-level tests | Low |
| Data sent to an AI provider (Groq/OpenAI/Google) | No Cycle reference from any AI path, architecture tests, no eval data | Low; depends on keeping the tests |
| Lock screen / FCM reveals the module | Generic copy, neutral payload type, no id, opt-in reminder | Google sees that a LifeOS reminder exists |
| Someone with the unlocked phone | Not on Home/dock; screens only in More | Medium: no app lock in v1 |
| Leak through logs or error bodies | No values in logs/messages, tests on error bodies | Low |
| Operator/DB-level access (incl. a leaked connection string) | Secrets handling per runbook; Neon at-rest encryption | Medium: no app-level encryption |
| Deleted data still in backups / resurrected by a restore | Disclosed to the user; runbook step after restores | Up to ~13 months in encrypted backups |
| Exported file leaks | Explicit user action, warning, cache file deleted | The shared file is outside LifeOS's control |
| Estimate misused for contraception / medical decisions | Window not day, minimum data, fixed disclaimer, no fertility features, no clinical words | Cannot be fully prevented |
| Legal requests / jurisdictions where cycle data is sensitive | Minimisation, real hard delete, export, opt-in | Backups and the operator's legal context |
| Overlap race bypassing the lock | Lock in the only write path, DB backstops for open/duplicate starts | Low |
| More users in the future without DPIA | Stated precondition (§9.1) | Process risk |
