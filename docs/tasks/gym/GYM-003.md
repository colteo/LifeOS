# GYM-003 — Workout history and previous performance

Status: READY

## Goal

Allow the user to:

1. browse completed workouts;
2. open a completed workout read-only;
3. see useful previous-performance values while executing the same exercise
   again.

History reads from workout execution snapshots only. It is never reconstructed
from current Programs/Templates. ADR-008 remains authoritative.

## No schema change expected

GYM-002 already persists WorkoutSession, the block snapshot, the exercise
snapshot with stable ExerciseId, set targets, actual reps, weight and
timestamps. GYM-003 normally requires no migration. If a migration appears
necessary: stop and explain why before creating one.

## Gym hub

```text
Gym
├── Resume          if InProgress
├── Train
├── History
└── Programs
```

History is a distinct navigation entry. Train remains the primary execution
intent, Programs remains authoring, History is retrospective.

## History list (`/gym/history`)

Completed WorkoutSessions only, newest completed first. Each row communicates
at least: WorkoutName snapshot, ProgramName snapshot, completion date/time in
local device time, duration, completed sets / prescribed sets. Optional if
clean: short secondary metadata such as exercise count. InProgress sessions are
not shown.

### Paging / bounded query

No unlimited history. Bounded query, e.g. page size 20–30, newest first, Load
more. Prefer stable pagination using CompletedAtUtc + Id or another
deterministic cursor if straightforward. Offset paging is acceptable for
personal-app volumes if clearly documented, but avoid accidental unbounded
queries.

## History detail

A read-only route (e.g. `/gym/history/{sessionId}`) showing: snapshotted
ProgramName and WorkoutName, StartedAt, CompletedAt, Duration, completed /
prescribed sets, blocks in original order, Single / Superset grouping, exercise
names, target reps, actual reps, WeightKg if present, incomplete prescribed
sets clearly distinguishable. Completed history is read-only; no edit/delete in
GYM-003.

## Authoring independence

Critical invariant: history survives Program rename, Workout rename, block
edits, set edits, Program deletion and Workout deletion. Only stored session
snapshot content plus stable ExerciseId is used. The current authoring
aggregate is never fetched to render historical prescription.

## Exercise name semantics

The GYM-002 snapshot stores the stable ExerciseId; historical display uses the
current exercise name. No schema change is introduced to snapshot exercise
names in GYM-003. Exercise rename does not exist yet: current semantics are
preserved and the decision is deferred until rename is introduced.

## Previous performance

ActiveWorkout shows, while entering today's set, what the user did last time
for the same exercise, by stable ExerciseId. For each exercise in the current
InProgress session: the most recent COMPLETED session owned by the same user,
completed before the current session's StartedAtUtc, containing the same
ExerciseId. InProgress sessions and the current session are never previous
history.

### Presentation

Concise values near the current exercise, e.g.

```text
Previous workout
Set 1   82.5 kg × 8
Set 2   82.5 kg × 8
Set 3   82.5 kg × 7
```

Actual recorded values only. If the previous session has fewer/more sets than
the current one, show what actually exists; never fabricate alignment. With no
previous completed performance: nothing, or a subtle "No previous workout".
Do not clutter the screen.

### Which previous session

ONE most recent completed session per ExerciseId; never merge values across
sessions. An exercise appearing more than once inside the same previous
workout is handled deterministically and documented; preferred: preserve all
occurrences in execution order. Never silently drop data.

### Query

No N+1 requests from the phone: one purpose-built query for the current
session, conceptually `GET /api/gym/sessions/{sessionId}/previous-performance`,
grouped by ExerciseId with previous SessionId, WorkoutName, CompletedAtUtc and
actual set values. The server derives ExerciseIds from the owned current
session; no UserId and no free list of ExerciseIds from the client.

## History API

Authenticated, owner-scoped reads: list completed sessions; completed session
detail if a dedicated route is useful; previous performance for the current
session. History exposes no mutable operations. Another user's history is
indistinguishable from missing.

## Phone UX (~360dp Android)

- History list: easy to scan, newest first, workout name dominant,
  date/duration secondary.
- Detail: readable set rows, supersets visually grouped, no editing controls.
- Active workout: previous values visible without navigating away; current
  input stays visually dominant; the page must not become too dense.

## Time

Stored in UTC; History displayed in device-local time. Duration from stored
StartedAtUtc / CompletedAtUtc. Previous-session ordering uses authoritative
completed timestamps.

## Tests

- Application/Domain: only Completed sessions in history; newest first;
  deterministic paging/bounds; ownership isolation; history survives
  Program/Workout deletion; detail preserves the snapshot; incomplete sets
  visible; duration correct.
- Previous performance: same ExerciseId finds the previous completed session;
  current session excluded; InProgress candidate excluded; latest Completed
  wins; another user's session excluded; none → empty; different ExerciseId
  does not match; fewer/more sets preserved; bodyweight/null WeightKg
  preserved; multiple exercises without N+1 semantics; deterministic
  duplicate-exercise behavior.
- HTTP: auth required; owner isolation; completed history list; history
  detail; paging/bounds; previous-performance endpoint.
- PostgreSQL: query ordering; ownership; previous-performance lookup; no
  pending model changes.
- App: local date formatting; duration display; previous set formatting; empty
  history; load more where testable.
- Regression: GYM-001 authoring, GYM-002 execution, GYM-002.1 Train/Programs
  separation, Finance, Authentication.

## Non-goals

Charts, volume analytics, PR detection, estimated 1RM, trends, exercise history
charts, workout comparisons beyond previous values, editing or deleting
completed workouts, calendar scheduling, post-workout feedback, AI coaching.

## Implementation decisions

### No migration

Every read uses the existing `workout_session_*` tables. Paging filters by
`user_id` and orders by `completed_at_utc, id`; the existing
`ix_workout_sessions_user_started_at` index narrows to the user, and a
personal history is small enough that the sort needs no dedicated index. A
`(user_id, completed_at_utc, id)` index is a deferred improvement if history
ever grows large; it is not a reason for a migration now.

### History list: keyset paging

`GET /api/gym/history?limit=20&cursor=…` → 200

```text
WorkoutHistoryPageResponse
- Items: WorkoutHistoryItemResponse
    - Id, ProgramName, WorkoutName      (snapshot names)
    - StartedAtUtc, CompletedAtUtc
    - CompletedSetCount, PrescribedSetCount, ExerciseCount
- NextCursor                            null on the last page
```

- Completed sessions only, ordered by `CompletedAtUtc` descending, then `Id`
  descending (a deterministic tie-break).
- Keyset cursor: the page after the last item `(CompletedAtUtc, Id)`, so new
  workouts finished while paging never shift or repeat rows. The cursor is
  opaque text (`<UtcTicks>_<id>`); a malformed one is 400.
- `limit`: default 20, 1–50 (400 otherwise). The repository reads `limit + 1`
  rows to know whether another page exists; nothing is unbounded.
- Application: `GetWorkoutHistoryHandler` (`LifeOS.Application.Gym.History`).
  Port: `IWorkoutSessionRepository.GetCompletedPageAsync`, a no-tracking
  projection of counts (no aggregate is materialized).
- `ExerciseCount` counts exercise prescriptions (a superset counts 2), like
  Train.

### History detail

`GET /api/gym/history/{sessionId}` → 200 / 404, same `WorkoutSessionResponse`
contract as the session endpoint, but only for a **Completed** session: an
InProgress session (it belongs to the active workout) and another user's
session are 404. The history group has no mutating route; the completed
session stays immutable through the GYM-002 rules.

The snapshot alone is rendered: names, blocks, kinds, rest, targets and actual
values come from `workout_session_*`. Exercise names are the current names of
the stable Exercise (see below).

### Exercise names

Unchanged GYM-002 / ADR-008 semantics: history shows the exercise's current
name, looked up by stable `ExerciseId`. Exercises cannot be renamed or
deleted today (RESTRICT), so the shown name is the name at execution time.
When rename is introduced, decide whether to snapshot names then.

### Previous performance

`GET /api/gym/sessions/{sessionId}/previous-performance` → 200 / 404

```text
PreviousPerformanceResponse
- SessionId                         the current session
- Exercises: PreviousExercisePerformanceResponse   (only exercises that have one)
    - ExerciseId
    - SessionId, WorkoutName, CompletedAtUtc       the previous session
    - Sets: PreviousSetResponse (BlockPosition, Position, ActualReps, WeightKg)
```

- The current session is loaded owner-scoped (404 for missing or another
  user's); its distinct ExerciseIds are the only ones queried. The client sends
  nothing else.
- Candidates: the same user's **Completed** sessions with
  `CompletedAtUtc < current.StartedAtUtc`, excluding the current session. The
  current InProgress session is the only InProgress one (GYM-002 invariant)
  and is excluded anyway.
- Per ExerciseId, ONE session wins: latest `CompletedAtUtc`, tie → larger
  `Id`. Values are never merged across sessions.
- Sets: only recorded sets (actual values) of that exercise in the winning
  session, in execution order (block position, then set position). A pending
  (skipped) set is not performance and is omitted; the remaining sets keep
  their real set number, so nothing is re-aligned.
- Duplicate exercise in the previous workout (e.g. Bench Press in block 1 and
  block 4): every occurrence is kept, in execution order; `BlockPosition`
  separates them. The app shows them as separate groups.
- `WeightKg` null (bodyweight) is preserved and shown as "BW".
- Port: `IWorkoutSessionRepository.GetPreviousPerformancesAsync(userId,
  exerciseIds, completedBefore, excludingSessionId)`. EF Core: one query picks
  the winning session per exercise (window/ROW_NUMBER over the user's
  completed sessions), a second loads only those exercises' recorded sets. Two
  queries regardless of the number of exercises.
- Previous performance is read once when the active workout opens (in
  parallel with the session). It does not change while training (the current
  session is InProgress and never a candidate).

### App

- Gym hub: Resume (if any) → Train (emphasised) → History → Programs.
- `/gym/history`: rows with workout name (dominant, wraps), program name, and
  "Today 18:05 · 52 min · 14 / 15 sets"; Load more while `NextCursor` exists;
  an empty state with a link to Train.
- `/gym/history/{id}`: header with program, local start/finish, duration and
  sets; one card per block (Superset labelled with A/B rows A1 B1 …), target
  and actual per set; pending sets shown as "Not done". No controls other than
  Back.
- Active workout: under each exercise name a compact "Previous · 28 Sep" with
  the sets ("Set 1 82.5 kg × 8") in a small wrapping grid, muted, below the
  exercise header and above the inputs. Nothing is shown for an exercise
  without previous performance. A failed previous-performance read is silent
  (training must not be blocked by it).
- Formatting helpers (`HistoryDisplay`) are plain .NET and unit tested: local
  date/time, duration ("52 min", "1 h 05 min"), previous set text.

## Phone acceptance

1. Gym shows Train, History and Programs; Resume above them while training.
2. Finish a workout → History lists it first with local time, duration and
   sets.
3. Open it: blocks in order, supersets grouped, targets, actual values,
   skipped sets marked "Not done", no edit controls.
4. Rename/edit/delete the source program or workout → the history entry and
   detail are unchanged.
5. Start the same workout again → each exercise shows "Previous · date" with
   the values of the last completed workout; a new exercise shows nothing.
6. More than 20 completed workouts → Load more appends the older ones.

## Deferred improvements

- `(user_id, completed_at_utc, id)` index if history becomes large.
- Exercise name snapshot when exercise rename is introduced.
- Previous performance on the history detail page (comparison) — out of scope.
- Component-level (bUnit) tests for Razor pages.
