# GYM-004 — Active program and training cycles

Status: READY

## Problem

After GYM-001 … GYM-003 the user can author programs, start any workout from
Train, execute it and look it up in History. What is missing is the notion of
*following* a program:

- the program has N workouts;
- they must be repeated for X cycles;
- the athlete decides freely when to do each workout and in which order;
- there are no fixed days, weeks or deadlines.

Train listed every workout of every program, with no memory of what was
already done.

## Product decisions

- **Template vs. active program.** A `WorkoutProgram` stays the template
  (authored under Programs). Activating it creates an `ActiveProgram`: a
  reference to the template plus its own progress. The template is never
  changed by training.
- **One active program per user** (v1). Activating another one while a program
  is active is refused (409); the user stops the current one from Train first.
- **Cycles are chosen at activation** (1–99, default 4 in the app).
- **No scheduling.** No weekdays, weekly targets, calendar, minimum/maximum
  frequency, pause or suspension.
- **Stop** ends a program early (status `Stopped`). It is the only way out
  besides completing it, so the user is never locked into a program.
- **Train shows only the active program.** Without one, Train shows an empty
  state that sends the user to Programs. Workouts of other programs are not
  started from Train any more.
- **Workout execution is unchanged.** A workout is started through the GYM-002
  start (`POST /api/gym/sessions`) and runs the normal session flow. History
  (GYM-003) is unchanged: every finished workout is still a history entry.

## Cycle rules

1. Activation opens cycle 1 with every workout of the program to do.
2. A workout counts for the current cycle when its session is **finished**
   (`POST /api/gym/sessions/{id}/finish`) and the session was started from a
   workout of the active program that is not done yet in this cycle.
   Stopping early (pending sets) still counts: finishing is the user's
   statement that the workout is done (GYM-002 semantics).
3. A discarded session never counts.
4. Order within a cycle is free.
5. A workout already done in the current cycle is not offered again; if it is
   trained anyway (e.g. started before activation), it does not count twice.
   A session counts at most once.
6. When every workout of the program is done in the current cycle, the next
   cycle opens immediately (in the same transaction as the finish).
7. After the last workout of the last cycle the program is `Completed` and
   disappears from Train.
8. The workouts of a cycle are the template's **current** workouts:
   - a workout added while the program is active is required from then on
     (also in the current cycle);
   - a deleted workout is no longer required; if it was the only one left to
     do, deleting it opens the next cycle (same transaction as the delete).

## Edge cases

| Case | Behaviour |
| --- | --- |
| Program without workouts, or a workout without exercises | Cannot be activated (400): a cycle could never complete. |
| Workout emptied or added empty while active | Shown in To do as "Not ready"; it blocks the cycle until it gets exercises or is deleted. |
| All workouts deleted while active | Nothing to do, never advances; the user adds workouts or stops the program. |
| Template program deleted | Its active program and progress are deleted with it (cascade). Executed sessions stay in History (ADR-008). |
| Template or workout renamed | Train shows the current names; History keeps snapshot names. |
| Session started before activation, finished after | Counts if it is a workout of the program not done in the current cycle. |
| Workout in progress when the cycle advances | Not possible through Train (one InProgress at a time); a session of an already-done workout simply does not count. |
| Another user's program | 404, indistinguishable from missing. |
| Concurrent activations | Partial unique index; the loser gets 409 with the winner's id. |
| Concurrent finishes / stop | Serialized on the active program row (`FOR UPDATE`). |

## Data model

```text
active_programs
- id, user_id
- workout_program_id      → workout_programs(id, user_id) ON DELETE CASCADE
- total_cycles            1–99
- current_cycle           1..total_cycles
- status                  Active | Completed | Stopped
- activated_at_utc, ended_at_utc
- ux_active_programs_user_active: UNIQUE (user_id) WHERE status = 'Active'

active_program_completions
- id, active_program_id, user_id  → active_programs(id, user_id) ON DELETE CASCADE
- cycle
- workout_template_id     not a foreign key (a deleted workout simply stops counting)
- workout_session_id      → workout_sessions(id, user_id) ON DELETE RESTRICT
- completed_at_utc        the session's finish time
- UNIQUE (active_program_id, cycle, workout_template_id), UNIQUE (workout_session_id)
```

Migration: `20261003082034_AddGymActivePrograms`. No existing table changes.

The aggregate is `ActiveProgram` (`LifeOS.Domain.Gym.Training`) with its
`ActiveProgramCompletion`s. The domain owns every rule above
(`Activate`, `RecordWorkout`, `AdvanceIfCycleDone`, `Stop`).

## Implementation

### Transactions

`ActiveProgramProgress` (Application) runs inside the change of another
aggregate:

- `FinishWorkoutSessionHandler` → after `session.Finish`, `RecordFinishedAsync`
  locks the active program and records the completion;
- `DeleteWorkoutHandler` → after `RemoveWorkout`, `ReconcileAsync` advances
  the cycle when nothing is left to do.

`ActiveProgramRepository.GetActiveForUpdateAsync` joins the request's open
transaction (the one started by the session/program repository), so the
finish (or delete) and the progress are committed together. Lock order is
always "the other aggregate first, then the active program".

### API

| Route | Result |
| --- | --- |
| `GET /api/gym/active-program` | 200 `ActiveProgramResponse`, 204 when none |
| `POST /api/gym/active-program` `{programId, cycles}` | 201, 400 (cycles / incomplete program), 404, 409 (`activeProgramId`) |
| `POST /api/gym/active-program/stop` | 204, 404 when none |

```text
ActiveProgramResponse
- Id, ProgramId, ProgramName (current template name)
- TotalCycles, CurrentCycle, ActivatedAtUtc
- ToDo: TrainingWorkoutResponse[]           current cycle, not done, by position
- Done: CompletedCycleWorkoutResponse[]     Id, Name, Position, SessionId, CompletedAtUtc
                                            current cycle, in the order done
```

`ToDo` reuses the GYM-002.1 `TrainingWorkoutResponse` (counts and `CanStart`)
through a new owner-scoped single-program projection
(`IWorkoutProgramRepository.GetTrainingProgramAsync`). The GYM-002.1
`GET /api/gym/training/programs` endpoint is kept unchanged.

### App

- **Programs → program**: a "Training" section. With no active program: the
  number of cycles and Activate (then Train opens). If the program cannot be
  completed it says why instead. If this program is active: "Active · Cycle 2
  of 5" and Go to Train. If another one is: its name and "Stop it from Train".
- **Train**: Resume card when a workout is in progress (unchanged), the program
  card (name, "Cycle 2 of 5 · 1 of 3 workouts done"), **To do** with Start,
  **Done this cycle** (muted, check icon, local finish time, opens the History
  entry), and Stop program with confirmation. Without an active program: an
  empty state linking to Programs. Train reloads on every visit, so after
  finishing a workout it reflects the new state.
- Gym hub: only the Train subtitle changed ("Your active program's workouts").

## Phone test checklist

1. Programs → program with 3 workouts that all have exercises → Training
   section shows Cycles (4) and Activate.
2. Set 2 cycles → Activate → Train opens: program name, "Cycle 1 of 2 · 0 of 3
   workouts done", 3 workouts in To do.
3. Start Day 2 → finish → Done → Gym → Train: Day 2 is in Done this cycle with
   its time; To do shows Day 1 and Day 3.
4. Tap the Done row → History detail of that workout.
5. Finish Day 3 and Day 1 (any order) → Train shows "Cycle 2 of 2", all 3 to do.
6. Start a workout and Discard it → it stays in To do.
7. Finish all three again → Train shows "No active program" with Go to Programs.
8. History lists all 6 workouts.
9. Activate again → Train → Stop program → confirm → empty state.
10. With an active program, open another program → its Training section names
    the active one; Activate is not offered.
11. A program with an empty workout → Training section says every workout needs
    exercises.
12. While active, delete the only workout left to do in the cycle → Train shows
    the next cycle.
13. While a workout is in progress, Train shows Resume and disabled Starts.
14. ~360dp: long program/workout names wrap; buttons are easy to tap.
