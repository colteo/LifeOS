# GYM-001 — Workout program authoring

Status: READY

## Goal

Implement the first end-to-end LifeOS Gym capability:

create and manage workout programs.

In v1 the LifeOS user manually enters the workout program supplied by their
personal trainer.

There is no trainer account or collaboration model in this slice.

GYM-001 is AUTHORING only.

Workout execution and workout history come later.

## Functional reference

The product owner currently uses a gym application with concepts such as:

- workout days/sessions;
- ordered exercises;
- prescribed sets;
- prescribed repetitions;
- recovery/rest time;
- supersets;
- workout execution;
- historical weights;
- personal records;
- total volume;
- estimated 1RM;
- post-workout feedback.

Only the AUTHORING concepts required to support future versions are part of
GYM-001.

The existing external application's visual design must NOT be copied.

LifeOS must use its own existing design system.

## Program structure

Conceptually:

WorkoutProgram
└── ordered WorkoutTemplates
    └── ordered WorkoutBlocks
        └── one or two exercise prescriptions
            └── ordered set prescriptions

Exact class names may follow existing LifeOS conventions.

## WorkoutProgram

Conceptually:

WorkoutProgram
- Id
- UserId
- Name

Support:

- list;
- create;
- rename;
- delete.

A program belongs to exactly one authenticated LifeOS user.

## WorkoutTemplate

A WorkoutTemplate represents one workout/session within the program.

Examples:

- Back / Triceps / Legs
- Shoulders / Chest / Biceps
- Legs / Back / Triceps

Conceptually:

WorkoutTemplate
- Id
- WorkoutProgramId
- Name
- Position

Support:

- add;
- rename;
- delete;
- reorder.

Do NOT bind templates to weekdays.

Do NOT create calendar/scheduling functionality.

Position/order is the relevant concept in GYM-001.

## Exercise

Exercise is a stable, reusable, user-owned entity.

Conceptually:

Exercise
- Id
- UserId
- Name

Do NOT store exercise names only as strings inside a workout.

Stable identity is required because future LifeOS versions will attach:

- workout history;
- weight history;
- volume;
- personal records;
- estimated 1RM;
- media/descriptions

to the same Exercise.

For GYM-001:

- user may create an Exercise while authoring a program;
- an existing Exercise may be reused;
- duplicate names for the same user are compared case-insensitively;
- different users may have Exercises with the same name.

Do NOT implement a global/shared exercise catalog.

## WorkoutBlock

A WorkoutTemplate contains ordered WorkoutBlocks.

A block is either:

- Single
- Superset

Conceptually:

WorkoutBlock
- Id
- WorkoutTemplateId
- Position
- Kind
- RestSeconds

Do not model a superset as a boolean flag on Exercise.

The block exists because rest/execution semantics belong to the group of
exercise prescriptions.

## Single block

A Single block contains exactly one exercise prescription.

Execution semantics for the future are:

Exercise A
→ Rest
→ Exercise A
→ Rest
→ ...

GYM-001 stores only the prescription.

It does NOT run a timer.

## Superset block

A Superset contains exactly two ordered exercise prescriptions:

Exercise A
Exercise B

The order must be stable.

Future execution semantics are explicitly:

Exercise A
→ Exercise B
→ Rest
→ Exercise A
→ Exercise B
→ Rest
→ ...

RestSeconds therefore means rest AFTER completing both exercises in the
superset round.

There is no prescribed rest between Exercise A and Exercise B in GYM-001.

## WorkoutBlockExercise

Conceptually:

WorkoutBlockExercise
- Id
- WorkoutBlockId
- ExerciseId
- Position
- Notes?

For Single:

exactly one WorkoutBlockExercise.

For Superset:

exactly two WorkoutBlockExercises.

Position preserves A/B order.

## Set prescriptions

Do not model a workout exercise only as:

Sets = 3
Reps = 8

because future programs must support prescriptions such as:

12 / 10 / 8

or:

8-10 / 8-10 / 8-10

Use ordered set prescriptions.

Conceptually:

WorkoutSetPrescription
- Id
- WorkoutBlockExerciseId
- Position
- TargetMinReps
- TargetMaxReps

Validation:

- at least one set;
- TargetMinReps > 0;
- TargetMaxReps >= TargetMinReps;
- positions deterministic.

The UI may provide shortcuts such as:

3 sets × 8 reps

and internally create:

Set 1: 8
Set 2: 8
Set 3: 8

Target weight is NOT part of GYM-001.

## Rest

RestSeconds belongs to WorkoutBlock.

It must be positive when configured.

The product UI should support practical values such as:

60 seconds
90 seconds
120 seconds

Exact UI controls are an implementation decision.

No countdown/timer runs in GYM-001.

## Notes

An exercise prescription may contain optional notes.

No attachments or media in this slice.

## Authoring operations

Programs:

- list;
- create;
- rename;
- delete.

Workout templates:

- create;
- rename;
- delete;
- reorder.

Workout blocks:

- add Single;
- add Superset;
- delete;
- reorder.

Exercises within blocks:

- select/reuse existing Exercise;
- create a new Exercise;
- edit notes;
- configure ordered sets/reps;
- configure block rest.

Superset:

- exactly two exercises;
- preserve A/B order.

## Ownership

All Gym data belongs to the authenticated user.

User A must never read or modify User B's:

- Exercises;
- WorkoutPrograms;
- WorkoutTemplates;
- WorkoutBlocks;
- WorkoutBlockExercises;
- WorkoutSetPrescriptions.

Follow existing LifeOS ownership patterns from Finance.

## Deletion semantics

Deleting a WorkoutProgram may delete its program-specific descendants:

- WorkoutTemplates;
- WorkoutBlocks;
- WorkoutBlockExercises;
- WorkoutSetPrescriptions.

Deleting a program must NOT delete reusable Exercise entities.

Deletion behavior must be explicit and safe.

Do not accidentally cascade into unrelated user data.

## Persistence

A schema migration is expected.

Before creating it:

- inspect current EF/PostgreSQL conventions;
- preserve explicit naming conventions;
- use appropriate unique constraints/indexes;
- enforce ownership where appropriate;
- define FK/delete semantics intentionally;
- do not modify existing Finance tables.

Ordering must persist deterministically.

Gym must not depend on Finance.

Shared abstractions may only be introduced when genuinely generic.

## Stop conditions

STOP and request a decision if:

- Finance Domain must change;
- Authentication must change;
- trainer/multi-user collaboration becomes necessary;
- existing architectural dependency rules must be broken;
- a substantial new dependency is required;
- weekday/calendar scheduling appears necessary;
- persistence must materially depart from the model described here;
- a cross-module abstraction would require substantial changes outside Gym.

Routine implementation decisions do NOT require a stop.
