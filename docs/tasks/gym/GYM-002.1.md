# GYM-002.1 — Separate training from program authoring

Status: READY

## Goal

Separate the user's two distinct Gym intentions:

1. "I want to train."
2. "I want to create or edit my workout programs."

After GYM-002, a workout was started from the same WorkoutDetail screen used
for authoring. Physical-device feedback found this unintuitive, even though
execution itself works well.

GYM-002.1 creates a dedicated training entry point while preserving all
existing GYM-001 and GYM-002 behavior. It moves the entry point; it does not
redesign authoring or execution, and it does not change their Domain models.

## Product model

```text
Gym
├── Resume workout     if an InProgress session exists
├── Train              execution intent
└── Programs           authoring intent
```

Start-workout actions are not mixed into authoring screens after this change.

## Gym hub (`/gym`)

- Train: a primary entry ("Choose a workout and start training").
- Programs: "Create and edit workout programs".
- If an InProgress session exists, the prominent "Workout in progress / name /
  progress / Resume" card stays above the normal choices; Resume remains the
  fastest action while a session exists.
- Visual hierarchy, not prose, communicates that Train is the everyday action
  and Programs is configuration.
- No History yet.

## Train (`/gym/train`)

Select an authored WorkoutTemplate and start executing it. Not an authoring
page: a read-only list of available workouts grouped by their WorkoutProgram.

At minimum the user understands the program name, the workout name and whether
the workout can be started. No rename, reorder, delete, add/edit block or any
other authoring action.

### Start workout

Reuses the existing GYM-002 start (`POST /api/gym/sessions`) and navigates to
`/gym/sessions/{sessionId}`. There is no second execution path; snapshot
semantics are unchanged.

### In-progress workout

At most one InProgress workout per user remains the GYM-002 invariant. On
`/gym/train`, an InProgress workout shows the prominent Resume card; the list
stays visible but its Start actions are disabled with understandable context.
The existing 409 + Resume behavior remains the server/database backstop; the
one-InProgress database invariant is not modified.

### Empty workouts

A workout with no blocks cannot be started (GYM-002). Train shows it as
"No exercises yet · Not ready" without an active Start button. Server-side
validation remains.

### No programs / no workouts

- No programs: "No workouts available. Create a program first." with a link
  to `/gym/programs`.
- Programs without any workout: an equally clear state with the same link.
- Authoring is never opened automatically.

## Remove Start from authoring

The primary "Start workout" action is removed from WorkoutDetail, together
with its in-progress warning. WorkoutDetail becomes purely about editing
blocks, exercises, supersets, sets, rest and order. No authoring capability is
removed or weakened, and no alternative Start action is hidden in another
authoring panel.

## Navigation

```text
More
→ Gym
   → Train
      → Active workout
   → Programs
      → Program
         → Workout authoring
```

Active workout Back still leads to Gym; completed workout Done still returns
to Gym. Gym is not added to the bottom dock. No History navigation.

## Phone-first UX

Android phone around 360dp: workout names wrap cleanly, program grouping is
obvious, Start buttons are easy to tap, Resume is prominent, long names do not
collide with actions, empty/not-ready states are understandable, no authoring
controls appear in Train.

## No Domain / database change

No migration. WorkoutProgram, WorkoutTemplate, WorkoutSession snapshot model,
execution schema, rest, sets, ownership and session lifecycle are unchanged.

## Regressions

All GYM-002 behavior (snapshot, one InProgress, resume after restart, Single
rest, Superset A → B → Rest, uneven supersets, set correction, server
timestamps, Finish, Discard, completed immutability) and all GYM-001 authoring
(programs, workouts, Single/Superset blocks, exercise reuse, set
prescriptions, rest, ordering) are preserved.

## Out of scope

GYM-003 History, scheduling, "today's workout", weekday assignments, calendar,
active-program concept, program activation, recommendations, previous-workout
values, PRs/volume/1RM, undo completed set, exercise rename, notifications,
trainer accounts, AI. No placeholder History UI.

## Implementation decisions

### Read model: a purpose-built training query

The existing APIs offer `GET /api/gym/programs` (summaries without workouts)
and `GET /api/gym/programs/{id}` (one whole program with every block,
exercise and set). Building Train from them needs one request per program
(N+1) and transfers whole authoring aggregates only to count them.

Instead, a small read-only query returns exactly the execution choices:

`GET /api/gym/training/programs` → 200

```text
TrainingProgramResponse
- Id, Name
- Workouts: TrainingWorkoutResponse
    - Id, Name, Position
    - ExerciseCount        exercise prescriptions (a superset counts 2)
    - PrescribedSetCount   set prescriptions
    - CanStart             the workout has at least one block
```

- Application: `GetTrainingProgramsHandler` (`LifeOS.Application.Gym.Training`),
  ordering programs like the Programs list (name ignoring case, then id) and
  workouts by position.
- Port: one projection method on the existing `IWorkoutProgramRepository`
  (`GetTrainingProgramsAsync(userId)`), owner-scoped like every other read.
  The EF Core implementation is a single no-tracking projection of counts; no
  whole aggregate is materialized.
- `CanStart` mirrors the GYM-002 start rule (`WorkoutSession.Start` refuses a
  workout without blocks). The rule itself stays in the Domain; the server
  still validates on start.
- No table, no second workout model, no change to authoring repositories
  beyond the one read method. Programs without workouts are returned (empty
  `Workouts`) so the app can tell "no programs" from "no workouts".

### Start and the in-progress session

Train loads `GET /api/gym/sessions/current` and the training programs in
parallel. With a session in progress it shows the same Resume card as the Gym
hub (shared `WorkoutInProgressCard` component) and disables every Start with
"Finish or discard the workout in progress to start another." A start that
still loses to a session started elsewhere receives the GYM-002 409 and the
page shows the Resume card for it.

### Display

- Programs without workouts are omitted from the Train list (nothing to
  train); when no program has any workout the "no workouts" empty state is
  shown.
- Row: workout name (wraps), "5 exercises · 15 sets", and a Start button; a
  workout that cannot start shows "No exercises yet" and a "Not ready" label
  instead.
- The More entry for Gym now reads "Train and manage workout programs".

## Phone acceptance

1. More → Gym.
2. Gym shows Train (emphasised) and Programs as separate choices.
3. Programs → program → workout: WorkoutDetail has no Start button; all
   editing still works.
4. Train lists workouts grouped under their program names.
5. Start an executable workout from Train → active workout opens.
6. Active workout behaves as in GYM-002.
7. Navigate away / restart the app → Gym prominently offers Resume.
8. Train while the session is active shows Resume and disabled Starts.
9. Finish the workout (Done returns to Gym).
10. Train → start another workout.
11. An empty workout shows "No exercises yet · Not ready" with no Start.
12. With no programs, Train shows the empty state linking to Programs.
