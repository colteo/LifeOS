# GYM-002 — Workout execution

Status: READY

## Goal

Allow the authenticated LifeOS user to start a workout from an authored
WorkoutTemplate, record actual set performance on the phone, use the
prescribed rest period, and finish the workout.

GYM-002 is execution only.

Historical browsing, performance analytics and post-workout feedback belong
to later slices.

## Core user flow

Program
→ WorkoutTemplate
→ Start workout
→ Active workout
→ record sets
→ Finish workout
→ completion summary

The active workout must remain usable at approximately 360dp.

## Execution snapshot

Starting a workout must create an execution snapshot of the current workout
prescription.

A completed or in-progress workout must NOT change if the source program or
template is later edited.

Example:

Template on October 1: Bench Press 3 × 8.
Workout started/completed on October 1.
Template changed on October 10: Bench Press 4 × 10.
The October 1 workout must still retain the original 3 × 8 prescription.

Do not make historical execution depend on mutable template contents.

Conceptually expect `WorkoutSession`, with program/template source references
where useful, and owned snapshot descendants representing:

- block order;
- block kind;
- rest prescription;
- exercise identity/order;
- set order;
- target rep prescription.

Stable ExerciseId should remain available for future exercise history and
performance analytics.

## Workout session

Conceptually:

WorkoutSession
- Id
- UserId
- optional/source WorkoutTemplateId as appropriate
- StartedAtUtc
- CompletedAtUtc?
- Status

Required v1 lifecycle: `InProgress`, `Completed`.

Discarding an InProgress workout is supported.

Do not introduce a large workflow/state machine unless required.

Starting the same template again later creates another independent session.

## Set execution

Each snapshotted prescribed set keeps TARGET information:

- TargetMinReps
- TargetMaxReps

Execution adds ACTUAL information:

- ActualReps
- WeightKg?
- CompletedAtUtc?

Rules:

- ActualReps must be positive when a set is completed.
- WeightKg is optional.
- If provided, WeightKg must be valid; document the bodyweight/unloaded
  decision.
- Use suitable decimal precision and PostgreSQL numeric type for weight.
- No RPE, RIR, tempo or warm-up taxonomy.

The user must be able to correct a set entry while the workout remains
InProgress. After a workout is Completed, execution data is immutable in
GYM-002.

## Single block execution

Exercise A set 1 → complete → rest → Exercise A set 2 → complete → rest → ...

The block-level RestSeconds from GYM-001 is authoritative.

## Superset execution

Exercise A → Exercise B → Rest → Exercise A → Exercise B → Rest.

There is no prescribed rest between A and B. Exercise order is the existing
A/B block order from GYM-001. The active-workout UI must make the grouping
visually clear. Do not flatten a Superset into unrelated exercises.

If the two exercises contain different set counts, handle the case
deterministically and document the behavior.

Do not change GYM-001 authoring constraints merely to simplify execution.

## Rest timer

Implement the prescribed rest timer, derived from `CompletedAtUtc +
RestSeconds` rather than solely an in-memory decrementing counter, so it
remains meaningful if the app is briefly backgrounded.

- Single: completing a set begins rest when another set remains.
- Superset: completing A does NOT begin rest; completing B for that round
  begins rest when further work remains.

Required UI: remaining rest time; ability to skip/end the rest early.
No notification, background service, sound or vibration requirement.

## Active workout UX

The phone is the primary execution interface. Required information:

- workout name;
- elapsed workout time;
- exercises grouped according to Single/Superset blocks;
- target reps;
- previous entered/current actual weight and reps;
- clear completed/pending state;
- rest timer when active.

Input must be fast; avoid a separate page per set. The user must be able to
enter WeightKg and ActualReps, complete a set, correct a completed set while
InProgress, finish the workout and discard it after confirmation.

Use the existing LifeOS visual language. Reference screenshots describe
functional expectations only.

## Persistence / resume

An InProgress session survives page navigation and app reload/restart. Opening
Gym with an InProgress workout offers an obvious way to resume it.

At most one InProgress workout per user, enforced at the database/application
level. Starting another workout while one is InProgress rejects with
information that allows the app to resume it.

## Finish workout

A v1 workout does NOT require every prescribed set to be completed.
When finishing: CompletedAtUtc is captured server-side, status becomes
Completed, no more edits are allowed.

Minimal completion summary: workout name, duration, completed sets /
prescribed sets. No volume, 1RM, PRs, charts, comparisons or questionnaire.

## Discard

Discarding an InProgress workout (after explicit confirmation) removes that
execution and its snapshot. Completed workouts cannot be discarded.

## Ownership

All execution data is owned by the authenticated user. User A must never read,
resume, edit, finish or discard User B's workout. Never accept UserId from the
client.

## Template deletion / editing

Execution history must survive renaming, modification or deletion of the
source program/template. No cascading relationship from authoring entities may
delete execution history. This is a critical invariant.

## Time

The server TimeProvider is authoritative for StartedAtUtc, set CompletedAtUtc
and workout CompletedAtUtc. Store UTC. The client may display elapsed/local
time but never supplies execution timestamps.

## API

Authenticated, user-scoped endpoints: start from template, get current
in-progress workout, get workout details, complete/update a set, finish,
discard.

## Database

A new migration, following the existing EF/PostgreSQL conventions, preserving
ownership, snapshot relationships, deterministic order, execution state,
weight precision and safe delete behavior. Historical migrations are not
modified. FIN-003 may add a migration in parallel; whichever PR merges second
regenerates its unpublished migration against the then-current main.

## Non-goals

History browsing (GYM-003), exercise charts, previous-workout comparison,
volume, PRs, 1RM, post-workout feedback, RPE/RIR, progressive overload,
trainer accounts, sharing, calendar, notifications, media, nutrition, AI.

## Implementation decisions

Durable invariant: see `docs/adr/0008-workout-execution-snapshots.md`.

### Model

`LifeOS.Domain.Gym.Sessions`:

```text
WorkoutSession            (aggregate root; workout_sessions)
└── WorkoutSessionBlock     (workout_session_blocks)     position, kind, rest_seconds
    └── WorkoutSessionExercise (workout_session_exercises) position (A=1/B=2), exercise_id, notes
        └── WorkoutSessionSet    (workout_session_sets)     position, target reps, actual reps, weight, completed_at
```

- `WorkoutSession.Start(program, workout, startedAtUtc)` copies the workout's
  blocks, exercises (by stable `ExerciseId`), notes and set targets. The
  workout and program names are copied too (`workout_name`, `program_name`),
  so a renamed or deleted source still shows the original name.
- Exercise names are NOT copied: like GYM-001, they are current metadata of
  the stable Exercise. Exercises cannot be deleted while referenced (RESTRICT).
- A workout without blocks cannot be started (400): there is nothing to
  record.

### Source references and delete semantics

- `workout_program_id` / `workout_template_id` are nullable foreign keys with
  `ON DELETE SET NULL`. They are provenance only ("started from"). Deleting or
  editing a program or workout never deletes or alters a session; deletion
  merely clears the reference. Nothing in execution reads the template after
  the start.
- Snapshot descendants cascade only from their own session (discard).
- `user_id` on sessions → users is RESTRICT, like the rest of LifeOS data.
- Ownership backstop: as in GYM-001, sessions, blocks and exercises carry
  `user_id`; parent references are composite `(…_id, user_id)` foreign keys,
  including `(exercise_id, user_id)` → `exercises`.

### One InProgress workout per user

Enforced by the partial unique index `ux_workout_sessions_user_in_progress`
(`user_id WHERE status = 'InProgress'`). Starting while one is in progress
returns **409** with the problem extension `sessionId`; the app then offers
"Resume". A concurrent double start is resolved by the index: the loser
receives the same 409.

### Set recording

- One endpoint records or corrects a set: `PUT
  /api/gym/sessions/{id}/sets/{setId}` with `actualReps` and optional
  `weightKg`. It returns the whole session (one request per set, no
  follow-up read).
- `ActualReps`: 1–999 (the authoring maximum).
- `WeightKg`: optional. `null` means no external load recorded (bodyweight or
  unloaded). A provided weight must be > 0 and ≤ 1000 kg with at most two
  decimals (`numeric(6,2)`). `0` is rejected so "no load" has exactly one
  representation.
- The first record sets `CompletedAtUtc` from the server clock. A correction
  changes reps/weight but keeps the original `CompletedAtUtc`, so it neither
  restarts rest nor reorders execution.
- Sets may be recorded in any order; the UI suggests the natural order.

### Execution order and rest

- Natural order: blocks by position; within a block, rounds by set position;
  within a round, A then B.
- Superset with different set counts: round *r* contains the set at position
  *r* of each exercise that has one. Example A = 4 sets, B = 3 sets:
  A1 B1 · A2 B2 · A3 B3 · A4. No set is dropped or merged.
- Rest is computed by the server (Domain `WorkoutSession.CurrentRest`) and
  returned as `rest { startedAtUtc, endsAtUtc, seconds }`:
  the most recently completed set starts rest when its completion closed its
  round (every set at that position in the block is completed), the block has
  `RestSeconds`, and at least one set of the session is still pending.
  - Single: every set closes its own round → rest after each set (including
    before the next block, using the finished block's rest).
  - Superset: completing A while B of the round is pending does not start rest;
    completing B closes the round → rest. A lone A4 closes round 4 → rest.
- Timers are derived from server timestamps. Each session response carries
  `serverTimeUtc`; the app computes its clock offset from it, so elapsed time
  and remaining rest stay correct after backgrounding or a wrong device clock.
- Skip rest is client-only (remembered for the app process); it changes no
  data.

### Finish / discard / immutability

- `POST /api/gym/sessions/{id}/finish`: server `CompletedAtUtc`, status
  Completed. Incomplete sets are allowed.
- `DELETE /api/gym/sessions/{id}`: InProgress only; removes the snapshot.
- Any mutation of a Completed session returns **409**; the Domain also
  refuses it.

### API

| Method | Route | Result |
|---|---|---|
| POST | `/api/gym/sessions` `{programId, workoutId}` | 201 / 400 / 404 / 409 |
| GET | `/api/gym/sessions/current` | 200 / 204 |
| GET | `/api/gym/sessions/{id}` | 200 / 404 |
| PUT | `/api/gym/sessions/{id}/sets/{setId}` | 200 / 400 / 404 / 409 |
| POST | `/api/gym/sessions/{id}/finish` | 200 / 404 / 409 |
| DELETE | `/api/gym/sessions/{id}` | 204 / 404 / 409 |

Another user's session is indistinguishable from a missing one (404).

### App

- Workout detail: **Start workout**. If another workout is in progress, the
  page says so and offers Resume. (Superseded by GYM-002.1: workouts are
  started from Train, `/gym/train`; workout detail is authoring only.)
- Gym hub: a "Workout in progress" card with Resume when one exists.
- Active workout page (`/gym/sessions/{id}`): elapsed time, a rest banner with
  remaining time and Skip, one card per block (supersets labelled A/B with
  rows A1, B1, A2, B2 ...), kg + reps inputs per set, ✓ to complete, Edit to
  correct, Finish, Discard with confirmation. A Completed session shows the
  summary (name, duration, completed/prescribed sets).
- Inputs are prefilled with the last values entered for the same exercise in
  this session (otherwise target minimum reps).
