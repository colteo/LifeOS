# FIN-001 — Monthly budget and safe daily spend

Status: READY

## Goal

Allow the LifeOS user to define a spending budget for a calendar month and
currency, understand how much has already been spent, how much remains, and
how much can safely be spent per remaining calendar day without exceeding the
budget.

The current-month budget must also become visible on Home.

## Context

LifeOS Finance already contains:

- accounts;
- transactions;
- categories;
- portfolio;
- monthly analytics.

A budget is planning data.

It is NOT:

- a transaction;
- an account balance;
- an analytics result;
- a forecast transaction.

Budget configuration must never create or modify transactions.

## Product model

Conceptually:

MonthlyBudget
- Id
- UserId
- Year
- Month
- Currency
- Amount

There may be at most one MonthlyBudget for:

User + Year + Month + Currency.

The exact implementation and naming may follow existing LifeOS conventions.

## Currency rules

Currencies must never be combined.

EUR spending counts only against an EUR budget.

USD spending counts only against a USD budget.

AUD spending counts only against an AUD budget.

No FX conversion belongs to this slice.

The Home budget card should use the user's default currency in v1.

The persistence/API model must still support budgets in other currencies.

## Month semantics

Month boundaries must remain consistent with the month semantics already used
by LifeOS Transactions and Analytics.

Do not introduce an independent or conflicting month/timezone implementation.

The UI initially focuses on the current calendar month.

The data model must support other months without redesign.

No dedicated historical budget screen is required in FIN-001.

## Spending calculation

Spent is:

the sum of actual Expense transactions for the authenticated user,
within the selected month and currency.

Excluded:

- Income;
- Transfer;
- Opening Balance;
- future projections;
- recurring rules;
- any non-transaction planning data.

No transaction may be counted twice.

## Remaining budget

Remaining = MonthlyBudget.Amount - Spent

Remaining may be negative.

Example:

Budget = 1,500 EUR
Spent = 620 EUR

Remaining = 880 EUR

## Safe daily spend

For the CURRENT month:

if Remaining <= 0:

SafeDailySpend = 0

otherwise:

SafeDailySpend =
Remaining /
number of remaining calendar days INCLUDING today

Example:

Remaining = 880 EUR
Remaining days including today = 22

SafeDailySpend = 40 EUR/day

Use precise decimal arithmetic internally.

Round only for presentation according to the existing currency-formatting
conventions.

Do not carry unused budget into another month.

Do not subtract future recurring expenses yet.

That belongs to FIN-004.

## Operations

Support:

- read monthly budget;
- create/set monthly budget;
- update monthly budget;
- remove monthly budget.

Missing budget is a valid state.

Budget amount must be greater than zero.

Ownership must always come from the authenticated user.

## Home UX

Home must contain, in this order:

1. Portfolio
2. Monthly budget
3. Recent transactions

Do not turn Home into an analytics dashboard.

When a current-month budget exists, show a compact card containing:

- month;
- currency;
- spent / budget;
- remaining;
- safe daily spend;
- visual progress indicator.

Example:

October budget

620 EUR of 1,500 EUR spent
880 EUR remaining

40 EUR/day
safe to spend

When over budget:

- Remaining may be negative;
- SafeDailySpend is 0;
- presentation should clearly communicate the exceeded budget without
  introducing a new visual system.

When no current-month budget exists:

show a compact CTA to configure one.

The CTA must not dominate Home.

## Budget management UX

Provide a simple way to:

- set the current month's budget;
- edit it;
- remove it.

Use the existing LifeOS design system.

Do not redesign the global shell.

Do not add budget to the bottom dock.

Use English UI only.

## Ownership and security

User A must never be able to read, create, update or delete User B's budget.

Another user's transactions must never affect the calculation.

Follow the existing Finance ownership patterns.

## Persistence

A database migration is expected.

Before implementation:

- inspect current Finance EF conventions;
- use explicit constraints/indexes consistent with the rest of LifeOS;
- enforce uniqueness for User + Year + Month + Currency;
- preserve existing Finance tables and behavior.

No existing transaction schema should need to change.

## API / application

Follow existing LifeOS endpoint, Contract, handler and result conventions.

Endpoint naming is an implementation decision as long as it remains consistent
with the current Finance API.

Avoid putting calculation logic in the Razor UI.

The budget/spending calculation should be testable independently.

## Tests

Cover at least:

- no budget;
- budget with no spending;
- spending below budget;
- spending exactly equal to budget;
- spending above budget;
- first day of month;
- last day of month;
- correct remaining-day count including today;
- Expense included;
- Income excluded;
- Transfer excluded;
- multiple currencies kept separate;
- other user's transactions invisible;
- other user's budget invisible;
- duplicate budget for same user/month/currency prevented;
- same month/currency allowed for different users.

Add appropriate:

- Application/unit tests;
- HTTP integration tests;
- PostgreSQL persistence tests;
- ownership tests;
- app/helper tests where useful.

## Non-goals

Do NOT implement:

- recurring transactions;
- future transaction projections;
- annual budgets;
- category budgets;
- rollover budgets;
- savings goals;
- FX conversion;
- notifications;
- AI budget advice;
- automatic budget generation.

## Stop conditions

STOP and request a decision if implementation requires:

- changing existing Transaction semantics;
- a new TransactionType;
- changing Analytics semantics;
- modifying Authentication;
- recurring transactions in order to complete the feature;
- Production infrastructure changes;
- cross-module changes outside Finance/App shared UI.

## Validation

Run:

- UnitTests;
- IntegrationTests including PostgreSQL;
- ArchitectureTests;
- Android Debug build;
- migration/model consistency / has-pending-model-changes as appropriate.

Self-review the final diff.

Do not merge to main.

## Definition of done

FIN-001 is done when:

- monthly budgets persist correctly;
- ownership is enforced;
- spending calculation matches real Expense transactions;
- SafeDailySpend is correct;
- Home displays the current-month default-currency budget;
- the budget can be configured/edited/removed;
- automated checks pass;
- phone acceptance steps are documented.
