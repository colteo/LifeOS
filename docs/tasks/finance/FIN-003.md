# FIN-003 — Account Balance Reconciliation

Status: READY

## Goal and scope

Allow a user to reconcile an account's current LifeOS balance to an observed,
signed real-world balance without modifying its opening balance or inventing
Income, Expense or Transfer transactions. Example: 1237.50 EUR calculated,
1250.00 EUR observed, +12.50 EUR adjustment, 1250.00 EUR resulting.

Only Finance and the existing Accounts UI are in scope. No FIN-004, recurring
transactions, projections, bank integration/sync, FX, AI or Gym work. No arbitrary
historical reconciliation, new navigation, or reconciliation edit/delete API.

## Domain and balances

Introduce immutable user-owned AccountBalanceAdjustment with Id, UserId,
AccountId, signed Amount, signed ObservedBalance, EffectiveAtUtc, CreatedAtUtc
and optional Note. Account currency is authoritative; no duplicated currency
or category. Monetary inputs/deltas follow numeric(19,4) Finance conventions.
Notes are trimmed; empty/whitespace becomes null.

Derived balances remain opening balance + transaction effects + adjustment
effects, computed in Domain. Existing transaction semantics remain unchanged:
opening baseline inclusive, query instant exclusive. Adjustment effects use
EffectiveAtUtc <= query instant, so the correction is observable at its effective
instant (like an opening balance). Adjustments before an opening baseline are
excluded, as are other accounts/owners and adjustments after the query instant.
An unavailable opening-baseline balance remains unavailable.

## Command and API

POST /api/accounts/{accountId}/reconciliations, authenticated and user-scoped.
Body: ObservedBalance and optional Note only. No UserId, delta or effective time.
A required UUID Idempotency-Key header identifies one submission; this is
transport retry metadata, not client authority over balance or time.

Application captures UTC server TimeProvider time at microsecond precision,
calculates current balance and delta = observed - calculated, and creates an
immutable adjustment only when delta is nonzero. Return previous calculated
balance, observed balance, adjustment amount, resulting balance, effective
instant, account/currency and optional adjustment id. Zero difference succeeds
without an adjustment. Missing or other-owner accounts return identical 404s;
unavailable balances return 409; invalid monetary/key input returns 400.

## Coherence, concurrency and retries

A focused Application port executes the use case against one database snapshot
and atomically saves its result. Infrastructure uses a SERIALIZABLE transaction
and locks the owned account row, with bounded serialization/deadlock retries.
Domain/Application retain the calculation; Infrastructure owns only locking,
reads, persistence and transaction retries. Concurrent reconciliations are
serialized and recalculate from committed predecessors, including predecessors
at the same effective microsecond. Concurrent movement changes may serialize
before or after a reconciliation; later edits/backdated movements still affect
the derived balance, as before.

Persist an immutable account_reconciliations receipt for every successful request,
including zero difference, alongside any adjustment. A unique account/owner/key
index makes retries durable across restarts and intervening movements. Same key
and normalized payload returns the original result; a changed payload returns
409 and writes nothing. Failures do not consume the key. Receipts are necessary
to prevent a retried zero-difference request from later correcting new spending.
No read/history management endpoint is needed for this UX.

## Persistence and deletion

Generate a NEW migration after AddMonthlyBudgets; never edit historical migrations.
account_balance_adjustments: UUID PK, user_id, account_id, signed numeric(19,4)
amount and observed_balance, effective_at_utc, created_at_utc, optional note;
composite RESTRICT FK to accounts(id,user_id), user FK, account/time index and
nonzero-amount check. Receipts have UUID id, owner/account/key, previous and
observed balances, effective/created times and note, with composite ownership FK
and unique request index. A receipt and its adjustment share an id and are saved
in one transaction; zero receipts have no adjustment. Previous calculated totals
use PostgreSQL numeric without a fixed precision, since derived totals may exceed
a single movement's numeric(19,4) range.

Accounts with adjustments OR reconciliation receipts (including zero receipts)
cannot be deleted: return a clear 409, preserve opening balance and audit records,
and enforce RESTRICT FKs as the final race backstop. Existing no-history deletion
behavior remains intact. No silently cascading audit history.

## Isolation from analytics and planning

Adjustments/receipts never appear in transaction history, monthly Income/Expense/
Transfer analytics, category figures or FIN-001 budget spending. Opening balances
are never changed by reconciliation. No changes to Authentication or Production
infrastructure are required.
