# FIN-004 — Monthly recurring transactions and projections

Status: IMPLEMENTED — automated validation passed; phone acceptance pending

## Authoritative contract

Monthly recurring rules describe expected Income or Expense planning data, never
future Transactions. FIN-004 is manual only; automatic confirmation is FIN-005.
Transfers, other recurrence patterns, notifications, bank sync, FX, category
budgets, cash-flow charts, AI forecasting and background jobs are out of scope.

Rules contain an owned UUID, required trimmed Name, immutable Income/Expense
type, one owned Account and matching Category, positive numeric(19,4) Amount,
DayOfMonth 1–31, immutable StartYear/StartMonth, optional EndYear/EndMonth,
optional normalized Note and UTC
creation/update timestamps. Account currency is authoritative. Creation defaults
to the local current month in the UI. Editing Name, Account, Category, Amount,
DayOfMonth, End month and Note affects unprocessed planning only.

Occurrence identity is RuleId + Year + Month, never scheduled date. Schedule
clamps to the last calendar day (including leap February). Months before the
start are absent. Unprocessed dates after local Today are Projected; all others
are Due, including missed months. Today uses server time with the client's
validated current local UTC offset, as FIN-001 does; UTC date is not assumed.
Queries require a bounded calendar-month range. The Finance Recurring screen
shows unresolved past Due occurrences, current month and next three months,
using bounded pages for older history.

Only Confirmed and Skipped states are persisted, with owned UUID, rule, logical
month, scheduled-date snapshot, status, optional TransactionId and UTC creation
timestamp. Unique Rule + Year + Month and ownership-safe composite FKs are
database backstops. Confirmed requires a Transaction; Skipped forbids one.

Only Due may be confirmed. Review prefills type, account, category, expected
amount, note and scheduled date. Actual amount, note and transaction date/time
can change without editing the rule. Confirmation uses normal Transaction Domain
rules. Owned rule/reference validation, unprocessed-state check, Transaction and
Confirmed state commit together or neither commits. Concurrent requests and
lost-response retries cannot duplicate; confirmed retries reveal the original
Transaction. Skip accepts Due or Projected, creates no Transaction and excludes
that month from expectations. Restore removes only Skipped state and derives the
status again. Confirmed is not restorable.

Deleting a rule removes its states and projections, preserving actual
Transactions. Ordinary Transaction editing remains available and never changes
the rule or future months. Deleting a linked Transaction transactionally removes
its Confirmed state, reopening the logical month when the rule remains and the
month is inside its current start/end range. Account
and Category deletion is blocked by referencing rules, including races protected
by PostgreSQL FKs. UserId is auth-derived; every query/action/reference is owned.

## Authoritative acceptance amendment: optional end month

Rules have optional EndYear/EndMonth. Both null means no configured end; otherwise
both must be present and valid, and the final calendar month must be at/after the
start by Year + Month comparison. Occurrences exist only in the inclusive range
StartMonth <= logical month <= EndMonth. The final month's day still clamps;
later months contain no occurrence and no fake Skipped state. Expected recurring
expenses therefore stop after the end automatically.

Create/edit includes End month (optional) with an explicit **No end** choice.
Editing the end changes planning only: retain existing Confirmed and Skipped
states with their audit links, hiding out-of-range months. Actual Transactions
remain unchanged in ordinary history. Extending the range reveals retained states
and cannot duplicate processed months. Confirmed retries return the original
Transaction even after shortening. Other actions outside the range are rejected.
Deleting a linked Transaction removes its state atomically, but the month only
reopens as planning when inside the rule's current range. This deliberately keeps
unreachable Skipped states rather than introducing optional cleanup behavior.

Transactions has a separate **Recurring planning** section for its selected month,
using the same bounded API projection. It shows only Due/Projected expectations
and a link to Recurring, without mixing them into actual history. Both planning
views stop after the end, including after editing shorter/longer.

Required amendment coverage: indefinite recurrence, single-month range, invalid
partial/before-start end, cross-year December/January, final-month inclusion and
next-month absence, final-month clamping, shortening/extension, confirmed actual
history/linkage survival, budget cutoff, Transactions planning cutoff, App end

## Budget formulas and isolation

Spent remains actual Expense Transactions for owner/month/currency. Remaining
remains Amount - Spent. ExpectedRecurringExpenses sums unprocessed Projected/Due
Expense occurrences for owner/month/account currency, excluding Income,
Confirmed and Skipped. FreeToSpend = Amount - Spent - ExpectedRecurringExpenses.
Current-month SafeDailySpend = max(0, FreeToSpend) / remaining calendar days
including today. Use decimal arithmetic, display-only rounding. Confirming at
the expected amount preserves FreeToSpend; a different amount changes it only
by the difference. Home shows compact budget values, not the recurring list.
Analytics, balances and history read actual Transactions only. Never modify
Analytics or AccountBalanceCalculator to consume planning data.
