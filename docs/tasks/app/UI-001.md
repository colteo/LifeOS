# UI-001 — Mobile layout consolidation and inline management

Status: IMPLEMENTED — automated validation passed; phone acceptance pending

Branch: `improve/home-navigation`, on top of the APP-001 commit, delivered in the
same future PR. No merge, no rebase, the APP-001 commit is not rewritten.

Baseline: APP-001 (Home = Monthly budget + Training, wordmark → Home, dock
`Transactions | + | More`, Home suggests the first incomplete workout), with
FIN-006 and GYM-004.

## The request (as given)

LifeOS already has an acceptable visual identity: **do not redesign it.** Fix:

- excessive vertical whitespace;
- inconsistent title/action placement;
- explanatory text where hierarchy already explains the UI;
- management actions living on separate pages unnecessarily;
- previous workout history occupying too much space during training.

Make the UI denser, clearer and more consistent at ~360dp (usable at 390–420dp).

### System rules

1. **Title + action** — when a page or section has a title and one primary
   contextual action, they share a row: title left, action right
   (`Transactions … < Back`, `Portfolio … Analytics`, `Monthly budget … Edit`,
   `Accounts … + Add account`, `Expense categories … + New category`). Long
   titles shrink/wrap; the action stays usable.
2. **Explanatory copy** — remove persistent helper text the structure already
   explains ("Real transactions only", "Recorded transactions for October…",
   recurring/one-off instructions that only describe visible buttons). Keep copy
   that prevents a real mistake, explains a non-obvious consequence or reports an
   exceptional state; never remove validation, errors or important warnings.
3. **Density** (guidance, not pixel rules) — page padding ~16px; title → next
   control ~8–10px; section gap ~14–18px; card padding ~14–16px; list-row
   vertical padding ~12px; primary CTA ~48px; compact contextual action ≥ 40px;
   dock ~68–70px. Never shrink controls below comfortable phone use.

## Implementation decisions

### Shared UI

- `PageHeader` renders one row: `h1` left, then either `< Back` (when
  `BackHref` is set) or an `Action` render fragment on the right. `BackLabel`
  is removed; the link's accessible name is "Back". Pages without a back link or
  action render the same row with the title only.
- Shared classes in `app.css`: `.lo-page-header` (title row), `.lo-section-header`
  (section title row, now `align-items: center`), `.lo-header-action` (the
  compact right-side action: ≥ 40px, link-styled, used by Back, Analytics,
  Edit, + Add account, + New category, History). Density comes from tuning the
  existing tokens/classes (`.lo-page-header`, `.lo-section`, `.lo-row`,
  `.lo-panel`, `.lo-day-title`) rather than page-specific overrides.
- Settings gear: `AppIcon` "gear" is redrawn as a conventional cog (toothed
  outline + hub), same viewBox and stroke model.

### Portfolio and Accounts

- The management UI of `/finance/accounts` moves into a reusable
  `Components/Finance/AccountsManager.razor`: list with ⋮ inline panels (Edit,
  Add current balance, Reconcile balance, Delete), the inline Add account form,
  and the section header `Accounts … + Add account`. It owns loading accounts and
  balances (same API calls, same version guard, same reconcile server-time
  preference) and the exact same validation and failure behavior.
- It reports the balances it loaded through `BalancesLoaded`, so Portfolio builds
  the dark card from the **same** request (no second balances call). Portfolio's
  card Retry calls the manager's `ReloadAsync`.
- `/finance/accounts` keeps working and renders `PageHeader` + the same manager.
- Privacy (hidden amounts) applies to Portfolio rows as before.

### Categories

Only layout: `+ New category` moves to the section title row
(`Expense categories` / `Income categories`) and the top-level create form opens
inline at the top of the tree card. Create/subcategory/rename/delete logic and
the one-open-at-a-time rule are unchanged.

### Exercise history

- Endpoint: `GET /api/gym/sessions/{sessionId}/exercises/{exerciseId}/history`
  with `limit` (1–20, default 5) and `cursor`. 404 when the session is missing,
  another user's, or does not contain the exercise; 400 for an invalid cursor or
  limit. Same opaque keyset cursor as `/api/gym/history`.
- Application: `GetExerciseHistoryHandler` loads the owner's session (ownership
  and exercise membership are validated from the stored session, never from the
  client), then asks the repository for one page.
- Repository: `GetExerciseHistoryPageAsync` — the user's Completed sessions
  completed before this session started, other than this session, that contain
  the exercise; ordered by `CompletedAtUtc` desc, `Id` desc (keyset); then one
  query for the recorded sets of that exercise in those sessions (every
  occurrence, by block position). Two queries per page, whatever its size.
- No schema change, no migration.
- App: the sheet loads lazily on first open, caches pages per exercise for the
  life of the workout page, and a failure shows inside the sheet with Retry.
