# APP-001 — Minimal Home and navigation

Status: IMPLEMENTED — automated validation passed; phone acceptance pending

> **Navigation and Home updated by [NAV-001](NAV-001.md).** The dock is now
> `Home | Transactions | + | Nutrition | More`, "+" is a global quick add
> (Transaction, Meal), and Home's first section is **Finance** (Open → `/finance`)
> with the monthly budget as a subheading inside its card. The rules below are
> the APP-001 record.

Baseline: `origin/main` at FIN-006 + GYM-004. A previous, rejected APP-001
attempt on another branch is **not** a reference; this document is the contract.

## Goal

Simplify the LifeOS Home and the global navigation. Home does not try to
represent every module.

- Home shows **only two cards**: Monthly budget and Training.
- The bottom dock shows **only** `Transactions | + | More`.
- The LifeOS wordmark in the header is the persistent way back Home.

## Scope

App presentation and composition only. No Domain, Application, API, contract or
persistence change; **no migration**. Existing clients are reused:
`BudgetsApiClient`, `ActiveProgramApiClient`, `WorkoutSessionsApiClient`.
If a new endpoint or migration ever looks necessary: stop and explain first.

## Home

Removed: Portfolio summary card, Recent transactions, any module directory,
any generic "Today" section, any other summary.

Contains exactly:

1. **Monthly budget card** — the existing `MonthlyBudgetCard` behavior and
   calculations (budget, spent, remaining, expected expenses, free to spend,
   safe daily spend) and Set / Edit / Remove. Two navigation actions inside the
   card: **Portfolio** → `/portfolio`, **Analytics** → `/finance/analytics`.
   They stay available while the budget loads or fails. No Portfolio card on
   Home; Portfolio and Analytics are not redesigned.
2. **Training card** — three states (below).

The two cards load and fail independently: a Gym failure never hides the budget
and a Budget failure never hides Training. There is no page-wide loading or
error state.

Home loads only: the current month's budget (owned by the budget card), the
current workout session and the active program (concurrently). It does not load
workout history, all programs, transactions or portfolio balances.

## Training card

### A — workout in progress

When `GET /api/gym/sessions/current` returns a session: its workout name, its
program name, "Cycle X of Y" when the active program is that session's program,
and **Resume** → `gym/sessions/{id}`. No Start is offered while a workout runs.
Resume is shown as soon as the current session is known, even if the active
program could not be read.

### B — active program, no workout in progress

Program name, "Cycle X of Y", the **next workout** and **Start workout**.

Next workout = the first item of `ActiveProgramResponse.ToDo` in program order
(lowest `Position`): the first workout still incomplete in the current cycle.
It is a **suggestion** only: no weekday scheduling, no dates, no deadlines, and
Gym → Train still lets the athlete start any incomplete workout in any order.
GYM-004 rules are unchanged.

Start uses the existing GYM-002 start (`WorkoutSessionsApiClient.StartAsync`)
and on success navigates to the active workout (`gym/sessions/{id}`). When the
API answers with the existing in-progress conflict (409 with the session id),
the card reloads and shows Resume, exactly as Train does. Other failures are
shown in the card. Workout execution logic is not duplicated.

If the suggested workout cannot be started (no exercises any more) the card
says so and links to Train. If the cycle has nothing left to do it links to
Train.

### C — no active program

"No active training program" and one action, **Choose program** →
`/gym/programs`. Templates of inactive programs are never shown on Home.

### Failure

Without knowing whether a workout is in progress, Start is never offered: the
card shows the error and Retry.

## Header

The `LifeOS` wordmark becomes a link to `/` (accessible name "LifeOS home"),
visually unchanged (no button styling, focus-visible ring only). The Settings
gear is unchanged.

## Bottom dock

Exactly, in order: **Transactions** | **+** | **More**.

- Transactions → `/finance/transactions`; active on the Transactions page and
  on a transaction's detail/edit pages, never on `/finance/transactions/new`.
  FIN-006 Actual / Planned behavior is unchanged.
- **+** → `/finance/transactions/new` (current behavior), accessible label
  "New transaction", the raised primary circular action, never an active
  section. No global quick-add, action sheet or other creation flows.
- More → `/more`, the unchanged module directory (Finance, Gym). Active on the
  directory and the Finance module's management screens, as before.
- Home and Portfolio are no longer in the dock.

Visual identity preserved (floating bar, raised center +); the grid goes from
five to three columns. At ~360dp the labels fit and the content's bottom padding
still clears the dock.
