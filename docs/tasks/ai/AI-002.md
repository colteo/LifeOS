# AI-002 — LifeOS Action Agent v1

Status: IMPLEMENTED on branch `feature/action-agent`. Not merged, not deployed.

Builds on [AI-001](AI-001.md) (Weekly Review Intelligence), [ADR-011](../../adr/0011-production-python-ai-service.md)
and the AGENTS.md agent-safety policy ("Unstructured input → AI interpretation → structured proposal →
validation → human confirmation → Domain/Application command"). No new ADR: the decisions below apply
ADR-003/ADR-004/ADR-011 inside one module, and the only Finance write is the existing FIN budget command.

---

## 1. What it is

On a saved Weekly Review, the user can ask for a **Suggested action**. The agent looks at the week's
finance figures and the relevant monthly budget, and either proposes **one** change to an existing
monthly budget or says nothing is worth changing. The card shows exactly what would change (month,
currency, current and proposed amount, a one-sentence reason); **nothing changes unless the user taps
Apply**. "Not now" dismisses it.

This is not a chat, not a general assistant and not a multi-agent system: two read-only tools, one
proposable action, one executor, one approval.

### Why this is an agent, not a fixed workflow

AI-001 is a fixed pipeline: one JSON in, one JSON out, code decides everything. AI-002 hands the model
real decisions inside a bounded loop:

| Decision | Who makes it |
|---|---|
| Which read-only tool to call next, and with which arguments (month, currency) | **model** |
| When it has enough information to stop | **model** |
| Whether any action is warranted at all, and which amount to propose | **model** |
| Executing tools, enforcing bounds, validating arguments and the proposal | LifeOS (deterministic) |
| Whether the action happens | **the user** |
| Performing the action | LifeOS (existing deterministic command) |

The path through the tools is not fixed: e.g. it may read the review then October's EUR budget, or
November's, or another currency's, may correct invalid arguments after an error result, and may finish
early without reading a budget. That observe → decide → act(read) → observe cycle is what makes it an
agent; the approval boundary is what keeps it safe.

## 2. Architecture

```text
App "Suggested action" card ── POST /api/weekly-reviews/{id}/suggested-action
  → RunActionAgentHandler (Application: the bounded loop, the only orchestrator)
      ├─ IActionAgentModel ── ActionAgentModelClient (Infrastructure, HTTPS + service key)
      │                        → POST /v1/action-agent/step (lifeos-ai, stateless; ONE model step)
      │                        → GroqActionAgent → Groq native tool calling (tool_choice=required)
      ├─ ActionAgentTools (Application; read-only: weekly review + GetMonthlyBudgetHandler query)
      └─ IProposedActionRepository → proposed_actions (insert a Pending proposal; nothing else)

App "Apply" ── POST /api/action-proposals/{id}/approve
  → ApproveProposedActionHandler → SetMonthlyBudgetHandler (existing FIN command) in one transaction
```

- The **loop lives in .NET**, because the tools are LifeOS use cases. Python receives the tool
  definitions and the results of calls .NET already executed, and returns one decision. It has no
  database access, no LifeOS identifiers and no write tool (ADR-011 boundary, `test_architecture.py`).
- The tool **definitions** (names, descriptions, JSON Schemas) are defined in .NET
  (`ActionAgentTools.Definitions`, schema version `action-agent-tools-v1`) and sent with every step.
  The **terminal** decision contract (propose / finish) and its strict schema are owned by the AI
  service (`action_agent/schema.py`), like AI-001's output schema; .NET validates it again.
- No LangGraph or other framework: a ~100-line explicit loop is sufficient and easier to bound and test.

## 3. Tools

| Tool | Kind | Arguments | Returns |
|---|---|---|---|
| `get_weekly_review` | read | none (`{}` exactly) | week start/end dates; per currency (≤ 10): expenses, income, net flow, top expense categories (≤ 5, names ≤ 100 chars) |
| `get_budget_status` | read | `year`, `month` (integers), `currency` (3 letters) — exactly these | `budget_set`; when set: amount, spent, remaining, expected recurring/planned expenses, free to spend, remaining days |
| `propose_monthly_budget_adjustment` | terminal | `year`, `month`, `currency`, `proposed_amount` (≤ 2 decimals), `rationale` (1 line ≤ 300) | — (ends the run with a proposal) |
| `finish_without_proposal` | terminal | `reason` (1 line ≤ 300) | — (ends the run, nothing stored) |

Read tools are **read-only by construction**: `ActionAgentTools` depends only on the
`GetMonthlyBudgetHandler` query and the already-loaded, user-scoped review (architecture test). They are
**user-scoped** (the owner comes from the token; the model never supplies or sees an id), **bounded**
(readable months = the review's month(s) plus the current and next local month; sizes capped),
**minimal** (only the finance section of the review; no gym/nutrition, no ids, no zone) and free of
secrets. The local month range uses the review's IANA zone (`LocalSchedule.ToUtc`, AUTO-001 DST rules),
as the budget query requires. There is **no** SQL, HTTP, filesystem, shell, generic API or write tool.

Not added: a tool to list budgets or categories. The budget is per user/month/currency (FIN-005), so the
review's currencies plus `get_budget_status` cover the action; nothing more is needed.

## 4. The bounded loop and its stop conditions

`RunActionAgentHandler.MaxSteps = 5` model steps (the service accepts at most 6). Each step is one
model call returning exactly one decision.

| Condition | Result | Stored |
|---|---|---|
| `propose_…` that passes validation (§6) | `Proposed` (200) | one Pending proposal |
| `finish_without_proposal` with a valid reason | `NoAction` (200, reason shown) | nothing |
| Unknown tool name (incl. invented write tools) | `Failed` `unknown_tool` (502) | nothing |
| Same tool with the same *parsed* arguments again (`eur` = `EUR`) | `Failed` `repeated_tool_call` | nothing |
| Invalid tool arguments | error result `{"error":"invalid_arguments","message":…}` returned to the model; the run continues (counts as a step) | — |
| A read-tool call on step 5 | `Failed` `max_steps` | nothing |
| Malformed decision / unusable model output | `Failed` `invalid_output` | nothing |
| Service unavailable / timeout | `Unavailable` (503) | nothing |

Additionally, on the last allowed step the AI service offers **only** the two terminal tools and adds a
"finish now" turn, so a well-behaved model always ends. Python rejects any decision that is not exactly
one call to an offered tool (`tool_choice: "required"`, `parallel_tool_calls: false`). The run is a
single synchronous request: no background continuation, no recursion, no state left behind.

An open (Pending/Approved) proposal for the review is returned **without** any AI call.

## 5. Human approval boundary

```text
AI reasoning → ProposedAction (Pending) → server-side validation → user sees the card
            → user taps Apply (POST …/approve) → SetMonthlyBudgetHandler (existing command)
```

- The model can only produce data. The analysis endpoint can store, at most, a Pending proposal; the
  run handler has no dependency on any Finance write, repository or unit of work (architecture test).
- Only `ApproveProposedActionHandler` reaches `SetMonthlyBudgetHandler`, and it never calls the model or
  the tools (architecture test). It executes the **stored, validated payload**, not model output.
- No approval = no write (unit, HTTP and PostgreSQL tests compare the budget row before/after).

## 6. Server-side validation of a proposal

Before anything is stored (`RunActionAgentHandler.ProposeAsync` + `ProposedAction.ProposeBudgetAdjustment`):

1. action type allowlist: only `MonthlyBudgetAdjustment` exists (enum + DB check);
2. target month ∈ {current local month, next local month} → else `proposal_month_not_allowed`;
3. the agent **read that exact budget** (month + currency) with `get_budget_status` in this run → else
   `proposal_not_grounded`; and it exists → else `proposal_without_budget` (v1 adjusts, never creates);
4. `CurrentAmount` is **LifeOS's observation**, never the model's;
5. amount: positive, Finance range/precision (`MonthlyBudget` rules), different from the current amount,
   and within a factor of 2 either way (`MaxChangeFactor`, an agent policy, not a Finance rule) →
   else `invalid_proposal`;
6. rationale: one plain line, 1–300 characters.

Python validates the proposal strictly first (types, ranges, 2 decimals, no extra fields); .NET repeats.

## 7. ProposedAction and its state machine

```text
Pending ──approve──▶ Approved ──execute──▶ Executed
   │                     └──────fail─────▶ Failed (budget_changed | budget_rejected)
   └──reject──▶ Rejected
```

- One state machine in the Domain (`ProposedAction.CanTransition`); Rejected, Executed, Failed are final.
- The payload is immutable: the repository port has no payload write (`TryAddAsync` inserts Pending
  only; `TryUpdateStatusAsync` updates status/timestamps/failure code only, conditionally on the
  expected status). Domain properties have no setters (architecture test).
- **Approve** (idempotent): Pending → Approved (decision recorded), then in **one transaction**: the
  budget row is locked (`SELECT … FOR UPDATE`) and must still equal `CurrentAmount`;
  `SetMonthlyBudgetHandler` writes; Approved → Executed claims the execution. A concurrent approval that loses the claim rolls back its write. Replays of an
  Executed/Failed proposal return it unchanged; an Approved one left behind (crash after the decision)
  is executed by the next approval. A changed or deleted budget → nothing written, proposal Failed
  `budget_changed` (the user's own edit is never overwritten). Approving a Rejected proposal → 409.
- **Reject**: Pending → Rejected (idempotent); rejecting an approved/executed/failed proposal → 409.
- **No lost update against manual edits.** `IMonthlyBudgetRepository.GetForUpdateAsync` reads the
  exact `(user, year, month, currency)` row with `FOR UPDATE` inside the approval transaction (it
  refuses to run outside one). Under Read Committed:
  - a manual write committed before the lock → the approval sees it → `budget_changed`, nothing written;
  - a manual write in progress when the approval locks → the approval waits for its commit, then sees
    the committed amount (or no row, if deleted) → `budget_changed`, nothing written;
  - a manual write arriving while the approval holds the lock → it waits for the approval's commit and
    then applies on top (the user's later edit wins; nothing is lost).
  At most one budget row is locked, and the proposal row is only touched by a conditional update after
  it, so there is no lock-ordering cycle. No schema change: the normal Finance write path
  (`SetMonthlyBudgetHandler` → `SetAsync` upsert) is unchanged; only the approval takes the lock.
  PostgreSQL tests force both race interleavings by waiting on `pg_blocking_pids`, and fail with the
  previous unlocked read.

## 8. Persistence (migration `20261007173548_AddProposedActions`)

Additive: one new table, directly after AI-001's `AddWeeklyReviewInsights`. Not applied anywhere remote.

```text
proposed_actions
- id                   uuid           PK (UUID v7)
- user_id              uuid           FK → users(id) ON DELETE CASCADE
- review_id            uuid           FK → weekly_reviews(id) ON DELETE CASCADE (source context)
- action_type          varchar(64)    ck IN ('MonthlyBudgetAdjustment')
- status               varchar(16)    ck IN ('Pending','Approved','Rejected','Executed','Failed')
- payload_version      integer        } ck payload_version >= 1 AND jsonb_typeof(payload) = 'object'
- payload              jsonb          } {year, month, currency, currentAmount, proposedAmount}
- rationale            varchar(300)   ck length(btrim(rationale)) > 0
- provider, model, prompt_version, tool_schema_version   varchar(100)
- tool_calls           text[]         } ck step_count BETWEEN 1 AND 8 AND cardinality(tool_calls) <= 8
- step_count           integer        }
- created_at_utc       timestamptz
- decided_at_utc       timestamptz NULL
- executed_at_utc      timestamptz NULL
- failure_code         varchar(64) NULL

ck_proposed_actions_state   the timestamps/failure code each status carries:
  Pending: decided, executed, failure NULL · Approved/Rejected: decided only
  Executed: decided + executed · Failed: decided + failure_code
ux_proposed_actions_review_open   UNIQUE (review_id) WHERE status IN ('Pending','Approved')
                                  (one open proposal per review; the insert's conflict target)
ix_proposed_actions_review_created (review_id, created_at_utc)   latest proposal of a review
ix_proposed_actions_user           (user_id)                     FK / cascade
```

Down drops the table (nothing else depends on it). `monthly_budgets` is not changed. The payload is a
versioned jsonb document read through a persistence record (as AUTO-002 D-3/D-4, AI-001); an unknown
version throws rather than guessing. Ownership is checked on `user_id` in every query; cross-user reads
and updates match nothing.

## 9. API

| Endpoint | Result |
|---|---|
| `GET /api/weekly-reviews/{id}/suggested-action` | `200 {"status":"None","proposal":null}` or `{"status":"Proposal","proposal":{…}}` (latest, any status). Never calls AI. `404` missing/foreign review |
| `POST /api/weekly-reviews/{id}/suggested-action` | runs the agent (or returns the open proposal): `200 Proposal` / `200 {"status":"NoAction","message":"…"}`; `404`; `503` unavailable; `502` no valid suggestion |
| `GET /api/action-proposals/{id}` | `200` proposal; `404` |
| `POST /api/action-proposals/{id}/approve` | `200` proposal (Executed or Failed); `404`; `409` rejected |
| `POST /api/action-proposals/{id}/reject` | `200` proposal (Rejected); `404`; `409` already approved/executed/failed |

Proposal: `id, reviewId, actionType, status, adjustment{year, month, currency, currentAmount,
proposedAmount}, rationale, createdAtUtc, decidedAtUtc, executedAtUtc, failureCode, provider, model,
promptVersion`. All endpoints require the user access token; ownership only from the token; a foreign
id is a 404 indistinguishable from a missing one, with no AI call and no write. Problem details carry
fixed messages only; no exception or provider text is returned or stored.

## 10. App

Weekly Review detail → after AI Insights → **Suggested action** card (`SuggestedActionSection`,
state in `SuggestedActionPanel`, plain .NET). Same AI styling as Insights (dashed border, "AI" badge,
attribution "Suggested by AI (provider · model · prompt). You decide.").

States: checking → *None* ("Suggest an action") → analysing → *NoAction* (reason, "Check again") or
*Proposal*: heading "Change your October 2026 EUR budget", rows Current / Proposed / Change, the
rationale, **Apply** and **Not now**, and "Nothing changes until you tap Apply." Decided proposals show
the outcome ("Applied. The budget is now …", "Dismissed. Nothing was changed.", "Not applied: the budget
changed after this suggestion."). Errors show the API message and Retry (a failed decision reloads the
stored state; it never re-sends). Only the analysis call uses the long AI timeout. No chat UI.

## 11. Privacy, safety and observability

Sent to the AI service/provider: the review's finance figures (currencies, totals, top category names),
budget figures of the read months, the month framing. Never: user/review/budget ids, time zone, tokens,
gym or nutrition data. Category names are user-typed and treated as untrusted data in the prompt (same
trade-off as AI-001).

Logged (no figures, names, prompts, arguments, results, rationale or model text — tested on both sides):

- .NET API, one line per run: outcome, error code, provider, model, prompt version, tool schema
  version, tool names called, step count, latency, proposal generated yes/no;
- .NET client: HTTP status / decision type and latency per step;
- Python: outcome, tool name (offered identifiers only), step, provider, model, prompt, attempts, latency.

Persisted per proposal: provider, model, prompt version, tool schema version, tool calls, step count —
no chain-of-thought (`include_reasoning: false`), no prompt, no tool results.

## 12. Failure handling

| Situation | Result | Finance | Stored |
|---|---|---|---|
| No `NutritionAi:BaseUrl` / no `GROQ_API_KEY` / timeout / 5xx / 429 after retries | 503 | untouched | nothing |
| Provider 400, no/several tool calls, unoffered tool, malformed or out-of-bounds arguments (Python) | 502 | untouched | nothing |
| Decision violates .NET checks (§4, §6) | 502 | untouched | nothing |
| Approval with changed/deleted budget | 200, Failed `budget_changed` | untouched | status only |
| Concurrent approvals | one executes, others return it | written once | one Executed |
