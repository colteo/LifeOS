## 1. Purpose

Test **one** new retrieval policy, `journal-retrieval-v2`, against the frozen production control on
two datasets, and decide promotion with gates declared before any live result. The goal from
AI-005 §15: fix the retrieval safety failure and the irrelevant context on unanswerable questions
while protecting the current recall.

Order of work (each step committed before the next):

1. author and freeze a fresh holdout, the scorer and the promotion gates (§3, §6);
2. only then investigate the v1 policy and write the hypothesis and rejected alternatives (§4);
3. implement the candidate as a new immutable SQL function (§5);
4. the user runs the live commands (§8); the first live result locks the experiment (§7).

## 4. Candidate hypothesis (written after the holdout freeze, before any implementation)

### 4.1 What the v1 policy does

`search_journal_memory_v1` fuses two candidate lists of 20 with Reciprocal Rank Fusion
(score = Σ 1 / (60 + rank)):

- vector arm: the 20 nearest chunks by cosine distance;
- lexical arm: an OR of **every** lexeme of the question under the `simple` configuration, ranked
  by `ts_rank_cd`.

`simple` has no stop words, so the lexical OR-query of a natural question is dominated by function
words: *what, did, the, my, after, is, for* in English, *di, il, che, ho, sono, quale* in Italian.
Almost every chunk in the question's language matches some of them. The lexical arm therefore
always returns 20 candidates, ranked by how densely they contain common words, and each of them
receives a lexical vote worth up to 1/61. That is the same weight as the best vector-arm result.

### 4.2 Mechanism behind the observed failure classes

- **Common-term overweighting** (AI-005 §10 already recorded it offline: a rare booking code ranked
  lexical 10 behind chunks rich in "which", "is", "for").
- **Cross-language misses.** Evidence written in the other language can never get a lexical vote,
  because its content words differ and its function words are the other language's. A relevant
  chunk at a good vector rank r then competes with up to 20 stop-word-only lexical candidates and
  with chunks that get both votes (same-language chunks that are vaguely near in vector space
  *and* contain function words). A score of 1/(60 + r) loses to any of them, and the evidence can
  fall out of the top 8 although the embedding found it. Both failed development cases are an
  English question over Italian evidence; this class is general and not tied to them.
- **Temporal / thematic distractors** are partly the same effect: same-language neighbours
  collect stop-word lexical votes that the right entry may not.

The irrelevant context for unanswerable questions comes from the vector arm, which always returns
its 20 nearest chunks. §4.1 does not explain it, and v2 does not claim to fix it (§4.5).

### 4.3 Hypothesis H1: informative lexical query

> Building the lexical OR-query only from the question's **informative** lexemes, by dropping the
> lexemes that PostgreSQL's built-in English or Italian snowball dictionaries classify as stop
> words, removes the stop-word votes from fusion. Relevant evidence the vector arm already finds
> (especially across languages) then stays in the top 8, while real lexical signals (names,
> codes, content words) keep their full weight.

Testable predictions: on both datasets hit@8 and recall@8 are not lower than the control's, and
the safety-critical cases all hit. MRR is not materially lower. Unanswerable noise is unchanged
(still up to 8 rows; not worse).

Why this is the smallest coherent change: it touches only the lexical query construction (one
statement). Embedding, chunking, both candidate depths, the RRF formula and k, tie-breaks, user and
identity filters, limit and the absence of a threshold are all unchanged. The frozen scorer's
ranking contract (ranks 1..20 per arm, score = Σ 1/(60 + rank)) still holds. Stop-word lists are
fixed linguistic knowledge shipped with PostgreSQL: no constant is chosen from any dataset, and no
new database object, index or configuration is created. English and Italian are the journal's
documented languages (AI-004).

Verified offline in the pinned image (no data, no provider): `ts_lexize('english_stem', l)` and
`ts_lexize('italian_stem', l)` return `{}` exactly for each language's stop words (*what, did, the,
my, after, which, is, for* / *di, ho, sono, quale, come, non, è*) and a non-empty array for content
words and codes (*doctor, blood, booking, isola, qx7p2l, wx-58k3t*).

### 4.4 Rejected alternatives

| Alternative | Why not now |
|---|---|
| Cosine similarity threshold / relevance floor | Needs a calibrated cutoff. The only scored evidence is the development set, and choosing a number from it is exactly what AI-005 §15 forbids. Cross-language evidence has lower similarity, so a floor would first drop the weak-but-relevant cases this experiment must protect. It also invites "less noise" wins bought with recall (noise guard). |
| Weighted RRF, other k | Changes the documented score formula and the frozen scorer's ranking contract, and needs a tuned weight. |
| Language-specific `english` / `italian` tsvector (stemming) | Needs new expression indexes or reindexing (not allowed) and a language guess per chunk of mixed-language text. |
| AND / phrase semantics for the lexical query | A natural question almost never has all of its lexemes in one chunk: the lexical arm would go nearly empty and lose rare-identifier matches. |
| Deeper candidate lists (e.g. 40 + 40) | Does not change the top-8 competition that causes the misses, and breaks the scorer's depth contract. |
| Dropping lexical-only rows beyond rank N, or a `ts_rank_cd` floor | A tuned constant with no prior; partly overlaps with a threshold. |
| Corpus-frequency (IDF) pruning of query lexemes | Needs a frequency cutoff (tuned) and extra per-query scans; stop-word lists need neither. |
| LLM query rewriting / translation | Adds a provider call and latency; out of scope for a ranking-policy experiment. |

### 4.5 Known limits (deferred, not addressed by v2)

- Unanswerable questions still receive up to 8 rows: v2 has no threshold. A calibrated relevance
  floor would need score-distribution evidence collected without tuning on either frozen set:
  `journal-retrieval-v3` with its own holdout.
- Italian inflection (`isola`/`isole`) is unchanged: `simple` still does not stem.
- Languages other than English and Italian get no stop-word pruning (their lexemes are kept, as
  in v1).

### 4.6 Exact v1 → v2 difference

`search_journal_memory_v2` (migration `20261009124617_AddJournalRetrievalV2Candidate`) is the v1
body with exactly one statement changed, plus its own name in its error messages and comment.
This is tested: putting back the v1 statement and name gives the v1 body byte for byte
(whitespace normalised).

```sql
-- v1
SELECT string_agg(plainto_tsquery('simple'::regconfig, lexeme)::text, ' | ')::tsquery
INTO v_query
FROM unnest(tsvector_to_array(to_tsvector('simple'::regconfig, coalesce(p_query_text, '')))) AS lexeme;

-- v2
SELECT string_agg(plainto_tsquery('simple'::regconfig, lexeme)::text, ' | ')::tsquery
INTO v_query
FROM unnest(tsvector_to_array(to_tsvector('simple'::regconfig, coalesce(p_query_text, '')))) AS lexeme
WHERE cardinality(ts_lexize('english_stem'::regdictionary, lexeme)) IS DISTINCT FROM 0
  AND cardinality(ts_lexize('italian_stem'::regdictionary, lexeme)) IS DISTINCT FROM 0;
```

Unchanged: the signature and result columns, argument checks, `hnsw.iterative_scan =
strict_order`, 20 vector + 20 lexical candidates, `ts_rank_cd` lexical ranking against the same
`simple` GIN index, RRF k = 60, tie-breaks, the user filter on both arms and on the joined entry,
the identity filter, `p_limit` 1..40, and no similarity threshold. A question with no informative
lexeme has an empty lexical arm, so it is ranked by meaning alone.

## 5. Versioning and production safety

- `journal-retrieval-v1` and `search_journal_memory_v1` are never modified (body hash pinned).
- The candidate is a new immutable function `search_journal_memory_v2`, added by a new additive
  migration that touches no table, vector dimension or index; its Down drops only v2.
- Production default stays `journal-retrieval-v1` (`JournalMemoryPolicy`, tested).
- Control and candidate use exactly Google `gemini-embedding-2` / 1536 and `journal-chunking-v1`;
  only the retrieval policy differs (enforced by the promotion gate
  `candidate_differs_only_by_retrieval_policy`).
- The evaluator calls the real SQL function of each policy; the lab never ranks in Python.

## 6. Promotion gates — `journal-retrieval-promotion-v1` (frozen before any live run)

Module `tools/ai-evals/src/lifeos_ai_evals/evaluators/journal_retrieval/promotion.py`
(SHA-256 pinned). `compare <control run> <candidate run>` attaches the report to each pairwise
comparison. Each gate is pass / fail; there is **no overall retrieval score**, only
`all_gates_pass`. AI-005's own gates (`journal-retrieval-acceptance-v1`) are unchanged.

Both datasets:

| Gate | Rule |
|---|---|
| `reference_is_production_control` | run 0 is the control identity (`control-v1.json`) |
| `candidate_differs_only_by_retrieval_policy` | same embedding, chunking, image, Ask limit 8; retrieval `journal-retrieval-v2` = `search_journal_memory_v2` |
| `complete_coverage` | both runs: all cases scored, zero execution errors, no `--case` filter |
| `policy_functions_verified` | each run ranked by its own migration-verified function, one call per case |
| `candidate_zero_*` | cross-user, deleted, wrong-identity, unknown-source results and malformed rankings = 0 |
| `candidate_safety_critical_evidence_in_top_8` | every safety-critical answerable case hits the top 8 |

Development (AI-005 v1 set):

| Gate | Rule |
|---|---|
| `candidate_hit_rate@8_min` / `candidate_recall@8_min` / `candidate_mrr_min` | ≥ 0.90 / ≥ 0.80 / ≥ 0.60 (AI-005's minimums, unchanged) |
| `candidate_fixes_control_safety_critical_misses` | every safety-critical case the control misses is hit by the candidate |
| `no_material_regression_hit_rate@8`, `…_recall@8` | candidate ≥ control − 1 / answerable cases (at most one case's worth) |
| `no_material_regression_mrr` | candidate ≥ control − 0.02 |

Holdout:

| Gate | Rule |
|---|---|
| `hit_rate@8_not_below_control`, `recall@8_not_below_control` | candidate ≥ control, no tolerance |
| `no_material_regression_mrr` | candidate ≥ control − 0.02 |
| `unanswerable_noise_not_worse` | mean irrelevant rows **and** non-empty rate on unanswerable questions ≤ control |
| `no_evidence_lost_to_filtering` | zero answerable cases where the candidate returned fewer rows than the limit and has lower recall@8 than the control |

Noise guard: returning fewer rows is never rewarded by itself. Lower unanswerable noise only
matters when every answerable and safety gate also passes. Precision and result counts are
reported as diagnostics, not gates.

Promotion of the candidate requires `all_gates_pass` on **both** datasets. Promotion here means
"eligible for a later, separate production-activation task"; AI-005.1 never activates it.

## 7. Anti-overfitting rules

- The holdout, labels, scorer and gates above were committed before the candidate was designed.
- The candidate (§4, §5) is committed before any live run.
- **The first live result locks the experiment.** After observing any live result, do not change
  `journal-retrieval-v2`, the holdout, labels, the scorer, the gates or any threshold to improve
  the outcome. A failing candidate is reported as failing and a new idea is deferred to
  `journal-retrieval-v3` with a new holdout.

## 8. Live commands (user-run; not run during implementation)

Run these from `tools/ai-evals` in PowerShell with Docker Desktop running. Keep the key only in this
terminal's environment. Run the steps in order. Stop after any run that reports execution errors
(`ERROR:` lines, exit code 1). Each `evaluate` starts and destroys its own disposable database.
Each development run makes 61 index + 40 query embedding requests, and each holdout run makes
57 + 28. The two `compare` steps make no provider call.

```powershell
cd tools/ai-evals
uv sync --locked
dotnet tool restore

# Offline gate first (no provider calls)
uv run --offline --locked python -m pytest

$env:GEMINI_API_KEY = "<your Gemini API key>"

# 1. Development control (journal-retrieval-v1)
uv run python -m lifeos_ai_evals evaluate journal_retrieval --variant experiments/journal_retrieval/control-v1.json --output results/ai0051-dev-control.json

# 2. Development candidate (journal-retrieval-v2)
uv run python -m lifeos_ai_evals evaluate journal_retrieval --variant experiments/journal_retrieval/candidate-v2.json --output results/ai0051-dev-candidate.json

# 3. Development compare (promotion gates, development set)
uv run --offline --locked python -m lifeos_ai_evals compare results/ai0051-dev-control.json results/ai0051-dev-candidate.json --output results/ai0051-dev-compare.json

# 4. Holdout control
uv run python -m lifeos_ai_evals evaluate journal_retrieval --dataset datasets/journal_retrieval/holdout-v1.json --variant experiments/journal_retrieval/control-v1.json --output results/ai0051-holdout-control.json

# 5. Holdout candidate
uv run python -m lifeos_ai_evals evaluate journal_retrieval --dataset datasets/journal_retrieval/holdout-v1.json --variant experiments/journal_retrieval/candidate-v2.json --output results/ai0051-holdout-candidate.json

# 6. Holdout compare (promotion gates, holdout)
uv run --offline --locked python -m lifeos_ai_evals compare results/ai0051-holdout-control.json results/ai0051-holdout-candidate.json --output results/ai0051-holdout-compare.json

Remove-Item Env:GEMINI_API_KEY
```

Reading the results: in each compare, the `Gate run 1 …` lines are the promotion gates, and
`comparisons[0].acceptance.all_gates_pass` is the decision for that dataset. The candidate is
eligible for promotion only if it is `true` for **both** datasets. The control is re-run here
instead of reusing the AI-005 export, so both sides of each comparison come from the same harness
and provider period. Afterwards, `docker ps -a --filter label=lifeos.purpose=ai005-disposable`
should be empty.
