## 3. Re-queue migration (`20261011132553_RequeueJournalMemoryForOpenAI`)

The migration is **data only**: no table, column, index, vector dimension or function change, and the
EF model is unchanged. It calls no provider.

**Up**, as one statement:

```sql
INSERT INTO journal_memory_index_queue (entry_id, user_id, source_updated_at, requested_at_utc, lease_token, lease_until_utc)
SELECT e.id, e.user_id, e.updated_at_utc, now(), NULL, NULL
FROM journal_entries e
FOR SHARE OF e
ON CONFLICT (entry_id) DO UPDATE SET
    source_updated_at = EXCLUDED.source_updated_at,
    requested_at_utc = EXCLUDED.requested_at_utc,
    lease_token = NULL,
    lease_until_utc = NULL;
```

- Every journal entry ends up with exactly one pending job for its **current** revision. An already
  pending job is updated, never duplicated.
- Any lease is cleared. A sync that claimed the job before the migration fails the existing
  lease-token check when it completes (`Stale`), so it can never overwrite the promoted result.
- `FOR SHARE` takes the journal rows first, the same journal→queue lock order as journal writes and
  index completion. An edit that is in flight is waited for, and its newer revision is the one that
  stays queued. A delete that is in flight is waited for, and the deleted entry is skipped. Without
  the lock, the snapshot's older revision could overwrite the edit's and leave a job no completion
  could satisfy; a mutation test reproduced exactly that.

**Old Gemini chunks are not deleted.**

- Search (v1 and v2) and status filter by provider, model and chunking, so those chunks are invisible
  to the OpenAI identity and are never mixed with OpenAI vectors.
- `IsValidIndex` and `IsValidQueryEmbedding` reject any Gemini answer, so an AI service still on
  Gemini gets 502 and writes nothing.
- When an entry's job completes, the existing sync deletes all of its chunks and inserts the OpenAI
  ones in one transaction.

**Down** (rollback) runs the same statement and queues every entry again, so a rolled-back runtime
rebuilds its own index through the same sync. No vector is reconstructed and no journal row changes.

**Proof:** `JournalMemoryPromotionTests`, on real PostgreSQL, covers:

- a Gemini-indexed entry: one job, chunks kept but invisible, then replaced by 1536-dimension OpenAI
  chunks;
- a pending or edited entry: one job at the current revision, lease cleared;
- a leased in-flight job: released, and its late completion is stale both before and after the
  promoted result exists;
- create, update and delete after the promotion;
- Down, with the journal source byte-identical;
- the edit and delete races, using lock-wait state checks rather than sleeps.

The idempotent Production script was also applied twice to a throwaway pgvector container with
synthetic data. The second run was a no-op.

## 4. Status during the re-index

Nothing is hidden. Until sync finishes, `GET /api/journal/memory/status` reports only the
OpenAI-indexed count, `pendingEntries > 0` and `indexIncomplete = true`. Search and Ask return
`indexIncomplete = true` and use OpenAI chunks only; there is no cross-identity fallback. Entries
that are not re-indexed yet are simply not found, so Ask may answer `insufficient_evidence` for them.

## 5. Re-index execution

There is no background worker. The migration only queues the work. The existing explicit, bounded
`POST /api/journal/memory/sync` (limit 1–10, default 3) is the only indexing path. You repeat
authenticated sync calls with `{"limit": 10}` until `pendingEntries = 0` (runbook §8, steps 9–10).
Each call indexes at most 10 entries, one OpenAI embedding request each. In the worst case each
request takes 3 × 15 s plus 2 × 4 s of waits, about 53 s, so a call stays within a 600 s client
timeout.

Sync results:

- An entry that fails with invalid output keeps its lease for 6 minutes and is retried after that.
- A 503 means OpenAI is unavailable; nothing is lost, so retry later.

An Ask Journal UI that helps drive sync would be a separate App task.

## 6. Timeout

**Requirement:** the effective Production .NET → lifeos-ai timeout for Ask must be at least 120 s.

| Hop | Bound | Source |
| --- | --- | --- |
| API → lifeos-ai, per request (embed query, then answer: two requests, each bounded) | **120 s** in Production; code default 60 s | `NutritionAi__TimeoutSeconds=120` (runbook §2.1, §2.6, D10) |
| lifeos-ai → OpenAI answer | 3 × 30 s + 2 × 4 s = **98 s** worst case | `OpenAIAnswerSettings` (unchanged) |
| lifeos-ai → OpenAI embedding | 3 × 15 s + 2 × 4 s ≈ 53 s | `OpenAIEmbeddingSettings` (unchanged) |
| API inbound (Kestrel) | no request timeout configured | no `RequestTimeouts` middleware |
| lifeos-ai inbound (uvicorn) | no request timeout configured | `Dockerfile` CMD |
| Render proxy | none recorded in the repository | **VERIFY AT EXECUTION** |
| App | no Ask Journal UI exists | — |

**Decision:** no code change. Production already sets 120 s explicitly, so the global code default
(60 s, shared with Nutrition, Weekly Review and the Action Agent) stays as it is.

- `JournalAskTimeoutTests` pins the runbook's Production value at 120 s or more, and above the 98 s
  answer worst case.
- `test_the_worst_case_answer_fits_the_production_ai_service_timeout` pins the 98 s bound.
- The first Ask call (query embedding) absorbs a lifeos-ai cold start, so the answer call meets a
  warm service with its own full 120 s.
- No provider retry behaviour was changed.
- An Ask request end to end can take longer than 120 s (two bounded calls). Clients must allow about
  300 s.

### 7.1 Privacy acceptance (DONE, 2026-10-11)

The owner gave this acceptance explicitly on **2026-10-11**:

> "Accetto la privacy policy del Journal RAG con OpenAI come descritta."
> (*"I accept the Journal RAG privacy policy with OpenAI as described."*)

It covers the Journal RAG feature as implemented:

- When embeddings are generated (indexing), journal titles and content may be sent to OpenAI. At
  query time the user's question is also sent to OpenAI to be embedded.
- For answer generation, the user's question and the retrieved journal passages (at most 8) may be
  sent to OpenAI.
- Every OpenAI Responses request uses `store=false`. No provider-side conversation state and no
  `previous_response_id` are used, and the response id is never read or kept.
- No OpenAI vector store, File Search or web search is used, and neither are any other tools.
- Embedding vectors are stored only in LifeOS PostgreSQL.
- Journal source data stays in LifeOS PostgreSQL, the source of truth.
- LifeOS does not intentionally log journal text, questions, generated answers, vectors, API keys
  or provider reasoning content. Logs carry outcome codes, counts, identity, latency and token
  counts only.
- The user accepts this external processing for the Journal RAG feature.

**Scope of the claim.** `store=false` only asks OpenAI not to store the response for later
retrieval. Any other retention or processing on OpenAI's side follows OpenAI's own API data
policies. The repository holds no evidence of a stronger guarantee, such as zero data retention,
and none is claimed here.

## 8. Deployment order (runbook Part B mechanics)

The repository applies migrations as a reviewed SQL script **before** the API deploy (runbook A4,
B5–B9), and deploys `lifeos-ai` before the API (B4a). Two adjustments to the intended order follow
from that:

- The migration is applied before the API deploy, not together with it.
- `lifeos-ai` must already be on OpenAI when the migration runs. Otherwise the old API plus a Gemini
  `lifeos-ai` could complete a re-queued job with Gemini and remove it from the queue. With
  `lifeos-ai` on OpenAI first, the old API rejects every index answer (502, nothing written) until it
  is replaced.

Between steps 5 and 7 Journal Memory answers 502/503 (safe; the journal itself works). Do not sync in
that window.

0. **Preconditions** (AI-004 §19):
   - check `SELECT "MigrationId" FROM "__EFMigrationsHistory"` for `..._AddJournalMemory`;
   - if it is absent, confirm pgvector ≥ 0.8 on Neon, then run `CREATE EXTENSION IF NOT EXISTS
     vector;` once as the database owner;
   - record the privacy acceptance (§7.1) and the external-provider ADR (ADR-013). **Both are
     DONE.**

   **Production preflight (DONE).** The owner ran this manually against Production Neon and
   supplied the evidence. It was not executed by the implementing agent or from this repository.
   - The connecting Production user was verified as `neondb_owner`.
   - The `vector` extension was available at version 0.8.0 (≥ 0.8, so it supports
     `hnsw.iterative_scan`).
   - The `vector` extension was enabled successfully.
   - At verification time, `AddJournalMemory`, `AddJournalRetrievalV2Candidate` and
     `RequeueJournalMemoryForOpenAI` were **not yet applied**.
   - `journal_memory_index_queue` and `journal_memory_chunks` did not exist yet.

   As a result, step 6's script will create the AI-004 and AI-005.1 objects and enqueue every
   entry (AI-004). The re-queue then upserts those same rows, with no duplicates. The chunk table


    expire and repeat. If the same entries keep failing, stop and investigate. Do not loop forever.

12. Run the smoke search (§9).
13. Run the smoke ask (§9).
14. Verify the citations (§9).
15. Verify that delete and update re-index (§9).
16. Verify that no old-identity rows remain. Read-only SQL, as in A4 "Verify":

## 9. Smoke checklist (post-deploy, few calls, synthetic entries where you create them)

**Status**

- [ ] The `index` identity is `journal-chunking-v1` / `openai` / `text-embedding-3-small` / 1536 /
  `journal-retrieval-v2`.
- [ ] `pendingEntries` reaches 0 and `indexIncomplete` becomes false.

**Index**

- [ ] An entry written before the promotion is found by search after the re-index.
- [ ] A new entry (create, sync) is found.
- [ ] An edited entry (update, sync) is found with its latest text; the old text is not found.
- [ ] A deleted entry is absent from search and from citations.

**Search** (`GET /api/journal/memory/search?q=...`)

- [ ] Results are the signed-in user's entries only.
- [ ] `retrievalVersion` is `journal-retrieval-v2`.
- [ ] No result comes from a Gemini chunk (step 16 SQL shows no Gemini rows).

**Ask** (`POST /api/journal/memory/ask`, client timeout about 300 s)

- [ ] An answerable question returns `answered` with a grounded answer.
- [ ] Every citation's `entryId` is one of your existing entries, and its excerpt matches that entry.
- [ ] An unanswerable question returns `insufficient_evidence` with no citations.
- [ ] The known medical over-refusal limitation (§1) is accepted and is not a failure.
- [ ] Normal use produces no 500.

**Failures**

- [ ] OpenAI unavailable gives the existing 503 "Journal memory is unavailable"; the journal still
  works.
- [ ] Invalid provider output gives the existing 502. Do not provoke it in Production; it is covered
  by tests.

**Privacy** (logs of both services, D16)

- [ ] Logs show only outcome, counts, versions, identity, latency and tokens.
- [ ] Logs never contain journal text, a question, an answer, an excerpt, a vector, a response id, a
  key or a user id.

## 10. Rollback

- **Answer only:** set `LIFEOS_AI_JOURNAL_ANSWER_PROVIDER=groq` on `lifeos-ai` and restart. The
  answer provider is not part of the index identity, so no re-index is needed.
- **Full** (embedding and retrieval back to Gemini and v1):
  1. On `lifeos-ai`, set `LIFEOS_AI_JOURNAL_EMBEDDING_PROVIDER=google` and
     `LIFEOS_AI_JOURNAL_ANSWER_PROVIDER=groq`, set `GEMINI_API_KEY`, and restart. The promoted API
     now rejects every index answer, so nothing is written.
  2. Generate the Down script of this migration only, review it and apply it (A4 mechanics):
     `dotnet tool run dotnet-ef migrations script 20261011132553_RequeueJournalMemoryForOpenAI 20261009124617_AddJournalRetrievalV2Candidate --idempotent --no-transactions ...`.
     It contains only the same re-queue and the removal of its history row. It touches no journal
     row, so it is safe, unlike the damaged-data cases in runbook Part C.
  3. Deploy the previous API commit.
  4. Sync until `pendingEntries = 0` (§8, step 10).
- OpenAI chunks left behind are invisible to the Gemini identity and are replaced entry by entry.
