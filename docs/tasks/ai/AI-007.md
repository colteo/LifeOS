## 1. Goals

1. One persistent chat in the Android app through which the user talks to LifeOS in natural
   language (Italian).
2. v1 capability: record **one expense or one income** from a sentence such as
   "Speso 5€ per colazione con Pamela", completed over one or more messages, shown as an editable
   draft, and saved **only after explicit confirmation**.
3. A conversational core (conversations, messages, turns, operations) that later capabilities
   (Nutrition meals, Hydration, other modules, SQL questions, Journal retrieval, cross-module answers)
   can plug into without rewriting it.

## 2. Problems solved

- Recording a transaction today means opening Finance, choosing type, account, category, date and
  typing the note. A short sentence is faster, especially right after spending.
- Missing details ("Ieri ho speso 10 euro") are asked for instead of rejected, and the operation
  survives app restarts and multi-message exchanges.
- LifeOS gets its first conversational surface while keeping every existing safety boundary: the
  model interprets, .NET validates and writes.

## 4. Functional requirements

### 4.1 Conversation [APPROVED]

- FR-1 One chat interface; new capabilities are added to it, never as separate chats.
- FR-2 Conversations and messages are persisted in LifeOS PostgreSQL and survive app restarts.
- FR-3 An operation may span several messages without losing context.
- FR-4 Several conversations per user; each is visible only to its owner.
- FR-5 The chat shows the current draft and offers confirm, edit and cancel.

### 4.2 Finance v1 [APPROVED]

- FR-6 Expense and income only. A transfer request gets a fixed "non supportato in v1" reply.
- FR-7 Interpreted fields: amount, type, category, account, description/note, date.
- FR-8 People's names stay in the note ("colazione con Pamela").
- FR-9 The account is **always** asked for when not stated explicitly — even when the user has one
  account. Same-name accounts → the user chooses.
- FR-10 The category may be inferred, but it is shown as a proposal and can be changed.
- FR-11 Account and category must belong to the user (enforced by `TransactionInputResolver`).
- FR-12 No transaction without explicit confirmation; one confirmed operation → at most one
  transaction.
- FR-13 Validation and persistence stay in `CreateTransactionHandler`; the model never writes.

### 4.3 Derived from the code [PROPOSAL]

- FR-14 Description and note: the domain has only `Note`. v1 writes one note composed from the
  interpreted description and details (e.g. `colazione con Pamela`). No new column. (Open decision
  D-3.)
- FR-15 Currency: the transaction always takes the account's currency. If the user states a
  different currency ("10 dollari" on a EUR account), the draft is blocked with a clarification —
  no conversion in v1.

## 5. Non-functional requirements

| Id | Requirement |
| --- | --- |
| NFR-1 | User isolation: every query scoped by the token's user id; foreign ids → 404. |
| NFR-2 | Idempotency: a retried message or confirmation never creates a second message, turn or transaction. |
| NFR-3 | Durability: an accepted user message is committed before any AI call; an interrupted turn is recoverable. |
| NFR-4 | Concurrency: one turn at a time per conversation; draft edits use optimistic versioning; the confirmation is atomic with the insert. |
| NFR-5 | Minimisation: the model receives only the current message, a bounded history, the current draft (without LifeOS ids) and the category names it may choose from. |
| NFR-6 | No content in logs: no message text, amounts, notes, names, account or category names; only ids, codes, counts, latency, tokens. |
| NFR-7 | Bounded latency: finite AI timeout, bounded retries (ADR-011 policy), clear "assistant unavailable" when the provider fails; Finance keeps working without the assistant. |
| NFR-8 | Architecture: Domain/Application free of provider, HTTP and EF types; enforced by architecture tests. |
| NFR-9 | No new framework: no agent framework, no LangChain/LangGraph, no provider SDK (ADR-004, ADR-011). |

## 6. Scope

### In v1

- conversations (create, list, open, delete), messages, turns;
- one Finance capability: **create one Expense or Income**;
- clarification of missing fields, editable draft, confirm, cancel, expiry;
- Italian replies;
- Android chat screen (F4).

### Out of v1 (future, §15)

Transfers, edit/delete of existing transactions, multiple transactions per message, Nutrition,

## 7. Architecture

### 7.1 Overview

```text
Android (MAUI Blazor)                                   [presentation only]
  │  HTTPS + LifeOS access token
  ▼
LifeOS.Api  /api/assistant/*                            [transport, auth, mapping]
  ▼
LifeOS.Application/Assistant                            [deterministic orchestrator]
  ├─ conversation & message use cases
  ├─ AssistantTurnHandler       (one user message → one turn)
  ├─ operation state machine    (collect → ready → executed | cancelled | expired)
  ├─ Finance capability         (resolve, validate, render, execute)
  │     └─ CreateTransactionHandler  (existing, unchanged)
  └─ IAssistantInterpreter      (port: text + context → structured interpretation)
  ▼
LifeOS.Infrastructure
  ├─ EF Core stores for assistant_* tables
  └─ AssistantInterpreterClient (HTTPS + service key → lifeos-ai)
  ▼
lifeos-ai  POST /v1/assistant/interpret                 [stateless, no DB]
  └─ provider adapter (OpenAI preferred / Groq alternative — ADR-014)
```

### 7.2 Responsibilities

| Decision | Who decides |
| --- | --- |
| What the user means (intent, amount, type, note, date expression, account mention, category guess) | **model** (structured output only) |
| Whether an account mention matches one, several or no accounts | **.NET** (deterministic, user-scoped) |
| Whether a category guess is a real category of the right type | **.NET** |
| Which fields are missing, what to ask next | **.NET** |
| Reply text shown to the user | **.NET** templates in v1 [PROPOSAL, D-5] |
| Whether the draft is valid and can be saved | **.NET** (`CreateTransactionHandler`) |
| Whether to save | **the user**, by an explicit confirm action |

It is a **workflow**, not an agent: one model call per user message, no tool loop, no autonomous
action. This is deliberately simpler than AI-002 because nothing here needs the model to choose
tools; extending to read-only tools (SQL questions, retrieval) later reuses the AI-002 bounded-loop
pattern behind the same interpreter port.

### 7.3 Modular capabilities without a framework [PROPOSAL]

- The **core** (conversations, messages, turns, operation lifecycle, idempotency, recovery) knows
  nothing about Finance. An operation has a `kind` string (`finance.transaction.create`) and a
  versioned JSON draft.
- A **capability** is a small Application component for one `kind`: it applies an interpretation to
  its draft, resolves references, lists missing fields, renders the Italian reply and executes the
  confirmed draft through the module's existing use case.
- v1 has one capability. The interpreter's output schema has an `intent` enum; unknown or
  unsupported intents get a fixed reply. A capability interface is extracted **when the second
  capability arrives** (AGENTS.md: no speculative abstraction); v1 keeps the Finance code behind a
  `kind` switch so that extraction is mechanical.

### 7.4 Why not extend `ProposedAction`

[FACT] `ProposedAction` requires a `ReviewId`, allows one action type with an immutable payload, and
models a single proposal with no multi-turn editing. Assistant drafts are mutable, versioned,
multi-turn and conversation-bound. Extending it would weaken the Weekly Review invariants. v1
**reuses the pattern** (conditional status transitions, partial unique index for "one open",
execution and status claim in one unit of work, idempotent re-confirm) in a new
`assistant_operations` table, and leaves `ProposedAction` unchanged.

### 7.5 Reuse summary

| Existing component | Reuse |
| --- | --- |
| `CreateTransactionHandler` | The only write path for a confirmed draft, called inside the confirmation unit of work. |
| `TransactionInputResolver` | Indirectly through the handler; its `CategoryCompatibilityError` is also usable to pre-validate a draft's category. |
| `IUnitOfWork.TryInTransactionAsync` | Confirmation: claim the operation + insert the transaction + store its id, all or nothing. |
| Action Agent concurrency | Conditional updates on expected status/version; bounded re-read loop; partial unique index. |
| Reconciliation idempotency | Client-supplied UUID, unique index, replay returns the stored outcome, same key with different input → 409. |
| `openai_http.OpenAITransport` | The Python adapter's HTTP transport (retries, failure classification, no content in logs). |
| ADR-011 service key, base-URL, timeout config | The .NET → `lifeos-ai` client. A separate config section is proposed (`AssistantAi:*`) following `NutritionAi:*`. |
| `AuthenticatedUser` | Owner of every request. |

## 8. Memory model

| Layer | What | Where | v1 |
| --- | --- | --- | --- |
| Conversational memory | What was said: user and assistant messages, in order. | `assistant_conversations`, `assistant_messages` | Yes |
| Operational memory | What is being done: the structured, versioned draft and its status; the **authoritative** state of the operation. | `assistant_operations` | Yes |
| Semantic memory | Long-term facts and retrieval over past content (e.g. Journal, preferences). | future tables / pgvector (AI-004 pattern) | **No** |

The model never holds state: every call is stateless (`store=false` or equivalent, no provider-side
conversation, no previous response id). The model sees a bounded slice of conversational memory and
the current draft; it never sees or changes operational memory directly — .NET applies its output.

### 9.4 Draft payload v1 (`finance.transaction.create`)

```json
{
  "type": "expense",
  "amount": "5.00",
  "currency_mention": "EUR",
  "note": "colazione con Pamela",
  "account": { "status": "missing", "mention": null, "candidate_ids": [], "account_id": null },
  "category": { "category_id": "…", "source": "ai" },
  "occurred_on": "2026-10-23",
  "occurred_time": null,
  "time_zone_id": "Europe/Rome",
  "occurred_at_utc": "2026-10-23T10:00:00Z"
}
```

- `account.status`: `missing` | `ambiguous` (several candidates) | `not_found` | `resolved`.
- `category.source`: `ai` | `user` — a user choice is never overwritten by a later model guess.
- Amounts are strings (decimal) in JSON, never floats.
- `occurred_at_utc` is computed by .NET from local date, optional time and the user's time zone.
- Ids live only in the server-side draft and in the client API; they are never sent to the model.

### 9.5 Deletion

- Deleting a conversation hard-deletes its messages and operations (cascade). Transactions already
  created stay in Finance — they are the user's financial records, not chat data.
- Deleting the user cascades everything (existing `users` pattern).
- Retention until manual deletion is a proposal (§18 P-1).

## 10. Operational flows

### 10.1 Turn (one user message) [PROPOSAL]

```text
POST /messages {clientMessageId, text}
 T1 (one DB transaction)
   lock conversation row (owner check)
   if clientMessageId exists → replay (§11)
   if another turn of this conversation is processing with a live lease → 409 turn_in_progress
   insert user message (sequence n, turn_status=processing, lease = now + L)
   commit                                   ← the message is durable from here
 AI call (outside any DB transaction)
   context = message + last K messages + current draft (no ids) + category names
   → IAssistantInterpreter → structured interpretation | unavailable | invalid
 T2 (one DB transaction)
   lock conversation row; check this turn still holds the lease
   capability applies interpretation to the open operation (or opens one) at draft_version v
   resolve account mention / category guess (user-scoped), compute missing_fields, status
   insert assistant message (sequence n+1) rendered from the draft
   user message turn_status=completed
   commit
 → 200 {userMessage, assistantMessage, operation}
```

Failure paths: provider unavailable/invalid → T2 sets `turn_status=failed` with a stable
`failure_code`; **no assistant message is stored** [APPROVED] — the app renders the failure from the
code, with "Riprova". The draft is unchanged. A lease lost to recovery, or ended → T2 discards the
result (no write).

### 10.2 Example A — explicit expense, account missing

1. "Speso 5€ per colazione con Pamela" → model: `create_expense`, amount `5`, currency `EUR`,
   note `colazione con Pamela`, category guess `Ristoranti` (from the supplied names), no account,
   date: today.
2. .NET: category resolved (source `ai`), account `missing` → status `collecting`, reply:
   "Spesa di 5,00 € — Ristoranti — «colazione con Pamela» — oggi. Da quale conto?" plus account
   options (ids only in the API response, not in the model context).
3. User taps "Revolut" (PATCH with `account_id`) **or** writes "Revolut" (new turn → mention →
   resolved). Status `ready`, draft card with Confirm / Edit / Cancel.
4. Confirm (version v) → one transaction.

### 10.3 Example B — multi-message

1. "Ieri ho speso 10 euro" → amount 10, type expense, date yesterday (local); missing account and
   category → "Per cosa e da quale conto?"
2. "Al supermercato, dal conto Revolut" → same open operation: note `supermercato`, category guess,
   account mention `Revolut` → resolved → `ready`.

### 10.4 Ambiguous or unknown account

- Two accounts named "Revolut" → `ambiguous`, reply lists both with their type/currency, the user
  picks one in the UI (by id) — the model is never asked to disambiguate ids.
- No match → `not_found`, reply lists the user's accounts as options.

### 10.5 Edit

- By UI: `PATCH /operations/{id}` with `expectedVersion` and the changed fields (ids allowed —
  this is the client, not the model). Version mismatch → 409 with the current draft.
- By text ("no, 7 euro", "categoria spesa") → a new turn producing a patch.
- Any change after `ready` creates a new `draft_version`; a confirmation of the old version is
  rejected, so the user always confirms what they saw.

### 10.6 Confirmation [PROPOSAL]

```text
POST /operations/{id}/confirm  {expectedVersion}  Idempotency-Key: <uuid>
 read operation (owner-scoped)
   executed with same confirm_request_id → return stored transaction id (replay)
   executed with another key → 200 with the stored transaction id (already saved; never a second one)
   cancelled | expired → 409
   collecting → 422 missing fields
   ready but draft_version ≠ expectedVersion → 409 with current draft
 TryInTransactionAsync:
   conditional update: status ready→executed WHERE id, user, draft_version = v, status = 'ready'
     (0 rows → return false: a concurrent confirm/edit/cancel won)
   CreateTransactionHandler.HandleAsync(userId, command built from the stored draft)
     not Created → return false (keep failure code)
   set transaction_id, confirm_request_id
   insert assistant message "Registrata: …"
   return true
 committed → 200 {operation, transactionId}
 not committed with a validation failure → operation back to collecting with failure_code and
   a fixed message (e.g. "Il conto selezionato non esiste più"), 422
```

There is no separate `approved` state (unlike `ProposedAction`) because the decision and the write
happen in the same database transaction: either both commit or neither does. The command is built
**only from the stored draft**, never from the model output of the confirming request.

**Textual confirmation** ("sì, registra") [PROPOSAL, D-4]: interpreted as intent `confirm_request`;
.NET answers by re-showing the draft card with the Confirm button. Only the explicit confirm action
writes. This prevents a misinterpreted message from creating a transaction.

### 10.7 Cancel and expiry

- `POST /operations/{id}/cancel {expectedVersion}` → `cancelled`; idempotent for an already cancelled
  operation; 409 for an executed one.
- Expiry (§18 P-2) is evaluated lazily when the conversation is read or written: an open operation
  past `expires_at_utc` becomes `expired` and the assistant posts "La bozza è scaduta".

### 10.8 Recovery after restart / interrupted turns [APPROVED]

- A crash between T1 and T2 leaves a user message `processing` with a lease.
- Lazy recovery (§18 P-4): on a read of the messages, a new message or a retry in that conversation,
  a `processing` turn whose lease has ended becomes `failed` / `interrupted` (no assistant message).
  Resending with the **same** `clientMessageId` reprocesses that message (attempt +1) instead of
  creating a new one, automatically up to attempt 3; after that, and at any time, the user's explicit
  "Riprova" starts the next attempt.
- No background worker in v1.

## 11. Idempotency

| Request | Key | Behaviour |
| --- | --- | --- |
| Create conversation | `clientConversationId` (UUID) | unique per user; replay returns the existing conversation |
| Send message | `clientMessageId` (UUID) | unique per conversation. Same key + same text: `completed` → stored result; `processing` with live lease → 202/409 "in elaborazione"; `failed` → reprocess. Same key + different text → 409. |
| Patch draft | `expectedVersion` | optimistic; a stale version → 409 |
| Confirm | `Idempotency-Key` header (UUID) + `expectedVersion` | replay returns the stored transaction; at most one transaction per operation (unique `transaction_id`, conditional status update) |
| Cancel | `expectedVersion` | idempotent on `cancelled` |

## 12. Concurrency, timeouts and retries

- **Per conversation, one turn at a time**: row lock on `assistant_conversations` in T1/T2, plus the
  turn lease. A second message while a turn runs → 409 `turn_in_progress` (the app disables sending).
- **No DB transaction is held during the AI call.**
- **Draft writes** (turn T2, PATCH, cancel, confirm) are conditional on `draft_version` / status.
- **Confirm vs. edit race**: whichever conditional update wins; the other gets 409.
- **Timeouts** [PROPOSAL]: AI call ≤ 60 s total including the Python service's bounded retries
  (ADR-011 policy: retry only timeouts, transport errors, 429, 5xx); turn lease = AI timeout + margin
  (e.g. 90 s); app request timeout > lease. A client timeout is resolved by retrying the same
  `clientMessageId`.
- **No retries of the confirm write** beyond the idempotent replay; the handler's own race handling
  (`ReferenceGoneAsync`) is kept.

## 16. Security and privacy

- Authorization: owner-scoped queries on every table; `user_id` stored on messages and operations
  and checked against the conversation owner.
- No LifeOS id (user, conversation, message, account, category, transaction) is sent to the model;
  categories are sent as names, accounts not at all (the model returns a mention string).
- Names and free text are **not masked** (owner decision; ADR-014). Minimisation still applies.
- Transport: app → API HTTPS; API → `lifeos-ai` HTTPS + service key (ADR-011); `lifeos-ai` →
  provider HTTPS with the API key from environment only.
- Logs: ids, outcome codes, attempts, latency, token counts. Never message text, draft fields,
  amounts, names, notes, account or category names, model output.
- The provider is stateless from LifeOS's point of view (no stored responses requested, no provider
  conversations, no tools, no vector stores). What the provider retains is governed by its terms —
  see ADR-014 open verifications.
- Synthetic data only in tests, fixtures and documentation (AGENTS.md).

#### F1 implementation notes (F1.1 + F1.2-A)

Approved for F1: P-1 (kept until manual deletion; no automatic deletion), P-4 (lazy recovery),
message limits (user ≤ 1000, assistant ≤ 4000 characters, trimmed, never truncated), no assistant
error messages (failed turns carry `failure_code` only).

As implemented (`Domain/Assistant`, `Application/Assistant`, `Infrastructure/Assistant`):

- **Turn fencing**: the attempt number is the fencing token. Completing or failing a turn requires
  the current attempt **and** `now < turn_lease_until_utc` (`TimeProvider`); the lease end is
  exclusive, the same instant from which recovery may interrupt the turn. The database's optimistic
  tokens (`next_sequence`, `turn_status`, `turn_attempts`) and the one-`processing`-turn index decide
  races between processes.
- **Accepting vs processing**: `SendAssistantMessage` and `RetryAssistantTurn` (user-facing) only
  make a turn durable as `processing` (lease 90 s). `CompleteAssistantTurn` and `FailAssistantTurn`
  are processor-only (an architecture test keeps `LifeOS.Api` off them). F1.2-B: users reach Send and
  Retry only through `AssistantTurnProcessor`, which fails each attempt it starts with
  `assistant_unavailable`; `CompleteAssistantTurn` has no caller in F1 (see F1.2-B notes).
- **Retry**: only the conversation's latest user message can be retried (`turn_superseded`
  otherwise), so a reply always follows the message it answers.
- **Outcomes**: Ok (also idempotent replays, `Replayed`), Invalid, NotFound (also another user's
  resource), Conflict (definitive: `client_message_id_reused`, `turn_not_held`, `turn_superseded`),
  InProgress (`turn_in_progress`), Busy (`assistant_busy`: concurrent writes kept winning after 3
  re-reads; temporary).
- **Concurrency**: a lost save stores nothing (one `SaveChanges`) and clears the change tracker; the
  use case reads the authoritative state again and decides again, at most 3 times.
- Create conversation has a single field, so "same key, different payload" does not apply to it.

#### F1.2-B implementation notes (HTTP endpoints)

Implemented, uncommitted. `Api/Assistant/AssistantEndpoints.cs`, `Contracts/Assistant/AssistantContracts.cs`,
`Application/Assistant/AssistantTurnProcessor.cs`; DI in `Program.cs`.

**F1 semantics without AI (decision).** In F1 nothing can answer a message, so the protocol must not
promise an answer. `POST …/messages` and `POST /messages/{id}/retry` go through `AssistantTurnProcessor`:
it accepts the message (T1, durable), then closes the attempt it started **in the same request** by
failing it with `failure_code = assistant_unavailable` (`FailAssistantTurnHandler`). Result: the message is
stored, the turn is `Failed/assistant_unavailable`, no assistant message exists, no turn is `Completed`,
and nothing stays `Processing` — so the next message is accepted at once (no 90 s `turn_in_progress`
block after every message) and no client waits for a reply that would never come. This replaces the F1
goal's "an accepted turn stays `processing` until a processor completes it or its lease ends", which
would have left every message `Processing` for 90 s and then `interrupted`.

**How F3 takes over.** F3 keeps the same seam and contract: in `AssistantTurnProcessor`, the single
`assistant_unavailable` outcome is replaced by the interpreter call (outside any DB transaction) followed
by `CompleteAssistantTurnHandler` or `FailAssistantTurnHandler` for the attempt returned by Send/Retry
(the fencing token) — the synchronous T1 → AI → T2 flow of §10.1. Messages stored in F1 stay
`Failed/assistant_unavailable`; the latest one of a conversation can be retried once F3 is live. No
background worker is needed (P-4).

**Privileged handlers.** `AssistantTurnProcessor` composes `Send`, `Retry` and `Fail` itself from
`IAssistantConversationRepository` + `TimeProvider`; none of the handlers that accept or close a turn is
registered in DI, and `CompleteAssistantTurnHandler` has no caller in F1. Architecture tests:
`LifeOS.Api` cannot reference `Complete*`/`Fail*` (existing) nor `SendAssistantMessageHandler` /
`RetryAssistantTurnHandler` (new: turns only through the processor). Registered (scoped):
`CreateAssistantConversationHandler`, `ListAssistantConversationsHandler`,
`GetAssistantConversationMessagesHandler`, `DeleteAssistantConversationHandler`,
`AssistantTurnProcessor`; the repository is scoped in `AddInfrastructure`.

**Endpoints** (all under `/api/assistant`, group `RequireAuthorization()`, owner only from the token, no
user id accepted in body or query):

| Method | Path | Request | Success |
| --- | --- | --- | --- |
| POST | `/conversations` | `{clientConversationId}` | 201 new (Location `…/conversations/{id}/messages`), 200 replay; `AssistantConversationResponse` |

202 Accepted is **not** used: in F1 no asynchronous processing exists. A `Failed/assistant_unavailable`
turn is a successful request (the message is stored), hence 201/200 with the turn's state rather than the
503 of §13: a 503 would tell the client the request failed although the message is durable.

**Idempotency and concurrency (HTTP view).** Create: unique `(user_id, client_conversation_id)`, a lost
race re-reads (one 201, the others 200). Send: unique `(conversation_id, client_message_id)`; a replay of a
`Failed` turn restarts it automatically while attempts < 3 (and it is the latest), which in F1 fails again
— so a replay after a timeout returns 200 with the same message and `attempt` + 1. Different messages at
once: each is either accepted with its own sequence or 409 `turn_in_progress` (optimistic `next_sequence`
+ one-`Processing` partial index). A stale attempt can never close a turn (attempt fencing + lease check in
`CompleteTurn`/`FailTurn`). Delete racing a send: the send's save fails on the foreign key/concurrency
token and re-reads → 404; nothing partial remains. Under a burst of simultaneous requests on one
conversation a request can lose its optimistic write three times in a row (in F1 every accepted attempt
closes at once, and every replay of a `Failed` turn starts a new attempt) and get 503 `assistant_busy`;
repeating it is safe and returns the stored state (covered by `AssistantHttpTests.ConcurrentSends_*`).

**DELETE stays 404 on a missing conversation** (not idempotent 204): it is the convention of every other
LifeOS delete (Journal, Reminders, …), the handler already distinguishes it, and a client retrying a delete
treats 404 as done.

**`GET /conversations/{id}` deferred.** In F1 the conversation has only id, client id and two timestamps,
all returned by the list and by `GET …/messages` (`conversation`); §13 gives it value as "conversation +
open operation", which exists only from F2. It is added with F2.

**Deviations from §13**: list paging by an opaque `cursor` (`UpdatedAtUtc` ticks + id) instead of
`before=`, for a stable order on equal timestamps; retry at `POST /messages/{id}/retry` (addressed by
message id: `RetryAssistantTurnHandler` now finds the message across the user's conversations via
`IAssistantConversationRepository.FindUserMessageAsync`); send returns 201/200 with the persisted turn
instead of `{userMessage, assistantMessage, operation}` / 503 (no AI, no operation in F1).

- Instants were kept at .NET tick precision in memory but stored by PostgreSQL in microseconds, so a
  `POST` response and a later `GET` of the same conversation/message carried different timestamps.
  `AssistantConversation.ToStoredPrecision` now truncates every instant (created/updated, message
  creation, lease) to whole microseconds, as Journal, Habits and Reminders already do.
- Not a defect of F1.2-A itself, but found while wiring DI: registering the turn handlers in
  `Program.cs` would have made `LifeOS.Api` depend on `FailAssistantTurnHandler` (the existing
  architecture test caught it); solved by the processor composing them (above).

no `Completed` turn exists. Apart from the instant between T1 and the close of a concurrent request, the only
way to see `Processing` is a request that crashed in between: then `409 turn_in_progress` for up to the 90 s
lease, followed by lazy recovery to
`Failed/interrupted`. The client must read the outcome from `userMessage.turn` (201/200 mean "stored", not
"answered"); `reply` is always null in F1. F3 plugs in at `AssistantTurnProcessor` without changing the

**Defect fixed: a retry racing a new message could make a reply land out of order.** The retry
(`RetryAssistantTurnHandler`, and the automatic retry of a replayed send) checks that no later user message
exists, then saves a change to the message only. A concurrent send accepted **and closed** in that window
does not conflict with that save, so an older message could start a new attempt after a later message
existed. In F1 that is harmless (the attempt fails at once), but in F3 `CompleteAssistantTurnHandler` would
have appended the reply after the later message (reproduced on PostgreSQL before the fix:
`Ok` instead of a refusal). Fix: `AssistantConversation.CompleteTurn` requires the user message to be the
conversation's last message (`IsLastMessage`); `CompleteAssistantTurnHandler` answers
`Conflict turn_superseded` and writes nothing; the conversation's `next_sequence` concurrency token keeps
that check true up to the save. Failing such an attempt is still allowed. Tests:
`AssistantConversationTests.ATurnFollowedByALaterMessage_CannotComplete`,
`AssistantHandlerTests.ARetryRacingANewMessage_CannotStoreAReplyOutOfOrder` (deterministic race through
`PausingAssistantRepository`). No HTTP, schema or migration change.

**States and transitions** (`AssistantOperation.CanTransition`, unit-tested over every pair):

```text
Collecting ⇄ AwaitingConfirmation      (a revision: the status follows the draft's completeness)
AwaitingConfirmation → Executed         (confirm)
Collecting | AwaitingConfirmation → Cancelled | Expired
Executed, Cancelled, Expired: terminal — no revision, confirmation, cancellation or expiry afterwards
```

No `Failed` state: a confirmation that `CreateTransactionHandler` refuses (account/category deleted or no
longer compatible) is a **correctable** error — everything rolls back, the operation stays open and unchanged,
the user fixes the draft. Terminal failures do not exist in v1 (the only write is all-or-nothing).

**Atomic confirmation** (`ConfirmFinanceOperationHandler`):

```text
read (owner-scoped) → lazy expiry → Executed? return it (Changed=false, same transaction id)
Cancelled/Expired → 409 · draftVersion ≠ expected → 409 version_conflict · Collecting → 422 draft_incomplete
currency rule → 422 currency_mismatch
TryInTransactionAsync:
  SELECT … FOR UPDATE WHERE id, user, kind, status='AwaitingConfirmation', draft_version=v, expires_at_utc > now
    (no row → false: a concurrent confirm/edit/cancel/expiry/delete won → re-read and decide again)
  CreateTransactionHandler.HandleAsync(user, command built only from the stored draft)
    not Created → false (correctable 422: account_not_found / category_not_found / category_incompatible / transaction_rejected)
  AwaitingConfirmation → Executed with result_transaction_id (conditional UPDATE, under the lock)
commit → 200; lost → bounded re-read (3) → the stored outcome; else 503 assistant_busy
```

The row lock serialises the confirmation with every other writer of the row: a second confirmation, a PATCH,
a cancel or the conversation's DELETE (its cascade) waits, then sees `Executed`. **R-2 verified**: inside the
confirmation's transaction `SaveChanges` runs in an EF Core savepoint, so a reference foreign-key violation
of the insert (account deleted between `CreateTransactionHandler`'s lookup and its insert) does not abort the
transaction; `ReferenceGoneAsync` still reads and reports NotFound, and the whole unit of work rolls back
(`AnAccountDeletedDuringTheConfirmation_RollsBackCleanly`).

**Concurrency and idempotency.**

| Race / retry | Outcome (tested) |
| --- | --- |
| two (or six, or five over HTTP) confirms | one transaction; the others return the same id, `replayed` |
| confirm vs cancel | first wins; the other 409 `operation_executed` / `operation_cancelled` |
| confirm vs PATCH | the PATCH waits on the lock, then 409 `operation_executed`; the confirmed amount is the one recorded |
| two PATCHes of one version | exactly one 200, the others 409 `version_conflict` |
| conversation DELETE during confirm | DELETE waits; the transaction is committed and survives; the operation is deleted with the conversation |
| DELETE before confirm | 404, nothing written |
| confirm retried after a timeout | 200 with the same transaction id, `replayed: true` (any expectedVersion) |
| failure after the insert, inside the unit of work | neither the transaction nor the status change is stored; the next confirm succeeds |
| concurrent creates in one conversation | one 201, the others 409 `operation_already_open` (partial unique index) |

A create replay is not keyed by a client id: the one-open-operation rule already prevents a duplicate, and the
409 carries the open operation's `operationId`. A PATCH replay after a timeout gets 409 `version_conflict` with
`currentVersion` (the client re-reads; its change is there). Cancel is idempotent on `Cancelled`.

**Expiry.** `expires_at_utc = last substantive change + 24 h` (creation counts; a no-op PATCH, a read, a
cancel or a confirm never extend it). Exclusive end: expired from exactly `expires_at_utc`
(`TheExpiryBoundary_IsExact`: confirmable 1 µs before, refused at the instant). Lazy: the first read or write
that sees it marks it `Expired` (conditional UPDATE); an expired draft stays readable, cannot be edited,
confirmed or cancelled (409 `operation_expired`) and frees the conversation for a new operation.

**Architecture (deterministic orchestrator in .NET; the model only interprets).**

```text
POST …/messages → AssistantTurnProcessor
  T1  Send/Retry: message durable, turn Processing (attempt = fencing token, lease 90 s)
  1   IAssistantCapability.PrepareAsync      (reads: open draft snapshot {id, version}, id-free context)
  2   IAssistantInterpreter.InterpretAsync   (outside any DB transaction; deadline = lease − 15 s)
  3   AssistantInterpretationValidator       (protocol rules; invalid → turn Failed)
  T2  IUnitOfWork:
        TryLockTurnAsync   (SELECT … FOR UPDATE on conversation + message: attempt holds, lease live,
                            message is last — BEFORE any operational write, held to the commit)
        FinanceAssistantCapability.ApplyAsync (snapshot still current? resolve, then F2 Create/Update)
        CompleteAssistantTurnHandler (reply)
      all-or-nothing
  failure → FailAssistantTurnHandler (fenced), no assistant message
```

**Interpretation protocol v1** (`AssistantInterpretation`, wire format snake_case, identical in Python):

- `protocol_version` (1), `intent` ∈ `finance_expense`, `finance_income`, `finance_draft_update`,
  `finance_draft_confirm`, `finance_draft_cancel`, `general_question`, `clarification`, `unsupported`;
  `unsupported_reason` (`transfer`, `multiple_transactions`, `other_capability`, `other`) exactly for
  `unsupported`; `ambiguous_fields` (field names); `finance` with `type`, `amount`, `currency`, `account`,
  `category`, `note` (`{state, value, span}`), `date` (`{state, kind, days_ago, weekday, day, month, year,
  span}`) and `time` (`{state, hour, minute, span}`).
- Field `state`: `absent` (nothing said), `stated` (explicit; `span` = verbatim text, must occur in the
  message, case/space-insensitive), `inferred` (model proposal: **only category and note**), `clear`
  (explicit removal: currency, account, category, note, date, time).
- Formats: amount `\d{1,15}(\.\d{1,4})?`; currency `[A-Z]{3}`; type `expense|income` (must not contradict the
  intent). Date kinds: `today`, `yesterday`, `day_before_yesterday`, `days_ago` (1–366), `weekday` (most
  recent strictly before today), `calendar` (day, month, optional year 1900–2999). No confidence score:
  nothing the model says authorises a write.
- Any violation → the whole interpretation is invalid (`assistant_invalid_output`), never repaired. Validated
  in Python and again in .NET (deliberate defence in depth; the .NET client also refuses unknown members and
  enum values).
- Request (minimised, stronger than ADR-014 §4): message, locale `it-IT`, the open draft's kind/type and
  **filled/missing field names** plus the awaited field (no amount, note, account or category name), the
  user's category names (≤ 100 per type; only the draft type's when known). **No history, no account names,
  no ids, no dates** (architecture test: request types contain no `Guid`/instant).

**Security boundaries.** The capability reaches Finance only through `GetActive`/`Create`/`UpdateFinanceDraft`
handlers (architecture test forbids `ConfirmFinanceOperationHandler`, `CancelFinanceOperationHandler`,
`CreateTransactionHandler`, `IFinanceOperationRepository`, `ITransactionRepository`, `IUnitOfWork` in it).
`finance_draft_confirm` replies "La transazione è pronta. Confermala con il pulsante." and never confirms;
`finance_draft_cancel` replies "Per annullare la bozza usa il pulsante Annulla." and never cancels (detected
intent ≠ authorised operation; the F2 endpoints are the only way). Nothing is written to `transactions` before
`POST …/confirm` (tested).

**Resolution.**

- Account: mention only, matched among the user's own accounts (`IAccountRepository.GetAllAsync`, owner-scoped):
  names compared without case/accents/punctuation; exact name (as written, then without Italian lead words
  "dal conto", "la carta", …), otherwise the mention as whole consecutive words of a name. 1 → id; several →
  ambiguous ("Ho trovato più conti «Revolut». Quale intendi?"); none → not found. Never the first, never
  preselected (single account still asked), no aliases (Finance has none), no model id ever accepted.
- Currency: only the stated one; a resolved account in another currency is not applied and asked again
  ("Il conto «Revolut» è in EUR, non in USD. Quale conto vuoi usare?"); a currency stated later clears an
  account that no longer fits. No conversion.
- Category: among the user's categories compatible with the type (`TransactionInputResolver`); a stated name
  → `User` (partial whole-word match allowed); a model proposal → `Suggested`, only when it names exactly one
  compatible category, otherwise ignored; `Suggested` never replaces `User` (F2 builder); a type change clears
  an incompatible category.
- Dates: `FinanceDateExpressionResolver` computes the local date from the expression, the user's IANA zone and
  `TimeProvider`; the time of day follows F2 (today → now, other day → 12:00, explicit time kept, DST via
  `LocalSchedule`); explicit future dates are kept and flagged in the reply; no zone → "Imposta il fuso
  orario…" and no date applied; non-existent dates (31/02) asked again.
- Amount within Finance's limits; inferred note only fills an empty note; ambiguous fields are asked, never
  applied. One unusable field does not block the others.

**Turns, concurrency, retries.**

| Case | Behaviour (tested on PostgreSQL) |
| --- | --- |
| interpreter disabled (default) / unavailable | `Failed/assistant_unavailable`, draft untouched, no reply |
| provider timeout / hang | `Failed/assistant_timeout`; the processor's deadline (lease − 15 s) cancels a hang |
| malformed / protocol violation | `Failed/assistant_invalid_output` |
| provider refusal | `Failed/assistant_refused` |
| PATCH, confirm, cancel or expiry while interpreting | snapshot mismatch → `Failed/draft_changed`, nothing applied over the change; a retry re-interprets the current draft |
| second message while interpreting | `409 turn_in_progress` (F1), only one interpretation applied |
| lease lost while interpreting, later message accepted | late attempt: lock fails, nothing written (Busy), no out-of-order reply |
| later message exists while the attempt still holds (retry race) | `Failed/turn_superseded` (F1 requirement fulfilled) |
| replay of a completed turn (client timeout) | stored reply, no second interpretation, no second change |
| retry of a failed turn | re-interpreted once; a failed attempt never changed anything |
| another user's conversation | 404, nothing interpreted |

Why a pessimistic lock: the optimistic tokens alone would make the commit fail if the turn moved, but only
*after* the draft write in the same transaction; the lock makes the fencing check precede every operational
write and hold until the commit (concurrent sends/retries/recovery/deletes wait), and the draft write is itself
conditional on the snapshot's version. Lock order (conversation, message, then operation) cannot deadlock with
the F2 confirmation (operation only) or with a conversation delete (conversation first).

New turn failure codes: `assistant_timeout`, `assistant_invalid_output`, `assistant_refused`, `draft_changed`,
`turn_superseded` (plus existing `assistant_unavailable`, `interrupted`).

**Orchestration T1/T2 reviewed** (`AssistantTurnProcessor`): T1 stores the message durably and opens the
attempt (fencing token = attempt, lease 90 s) → `PrepareAsync` reads the authoritative open draft (id +
version) and builds the id-free context → the interpreter runs outside any transaction, bounded by
lease − 15 s, never cancelled by the client → the validator rejects the whole interpretation on any rule →

attempt, live lease, still the last message) **before any operational write**, then the capability re-reads
the open draft and refuses a moved snapshot (`draft_changed`), then the F2 handler writes conditionally on
the draft version, then the reply completes the turn; anything else rolls everything back. Every outcome of
the capability (Conflict, Busy, version conflict, NotFound → `draft_changed`; Invalid → `assistant_invalid_output`;
Rejected → a reply, nothing changed) closes the attempt through the fenced `FailAssistantTurnHandler`; a lost
lock with the attempt still holding → `turn_superseded`, otherwise `Busy` (another request owns the turn).
No path leaves a turn Processing beyond its lease; an exception (crash) does, until lazy recovery.

## 23. Acceptance criteria (v1 overall)

1. "Speso 5€ per colazione con Pamela" produces an expense draft of 5,00 in the account currency,
   a proposed category and the note "colazione con Pamela", and asks for the account.
2. With one account only, the account is still asked for.
3. With two same-name accounts, the user must choose one.
4. "Ieri ho speso 10 euro" → "Al supermercato, dal conto Revolut" completes the same operation, dated
   yesterday in the user's time zone.
5. Nothing is written to `transactions` before the explicit confirm action; a retried confirm never
   creates a second transaction.
6. The transaction is created by `CreateTransactionHandler`; account and category belong to the user.
7. The conversation, messages and draft are intact after closing and reopening the app; an
   interrupted turn can be retried without duplicating the message.
8. No LifeOS id appears in any request to the AI service; no message content appears in logs.
9. Another user's conversation, message or operation is indistinguishable from a missing one.
10. A transfer request is refused politely and creates nothing.
