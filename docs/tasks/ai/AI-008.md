## Scope

In: `hydration.intake.create` (one water intake: ml, cl or litres; date; time) and `nutrition.meal.create`
(one meal: the user's description, optional meal type, date, time), prepared as drafts in the same chat,
corrected by chat or by the draft card, recorded only by Confirm through `AddHydrationIntakeHandler` /
`CreateMealHandler`; the Finance path unchanged. Out: analytical reads, nutrition estimates (Groq is not
called), other modules (reminders, journal, habits, gym...: answered "not available").

## Architecture

```text
AssistantTurnProcessor (unchanged: lease, fencing, unit of work, retries)
  └─ AssistantCapabilityRouter : IAssistantCapability                  Application/Assistant
       ├─ IAssistantOperationReader   open operation of any kind (no draft parsed)
       ├─ AssistantCoreReplies        general question, unsupported, not available, nothing open
       └─ IAssistantModule[]          Finance (always) · Hydration · Meals (Assistant:Modules:*)
            ├─ FinanceAssistantModule   AI-007 F2/F3 logic, unchanged, behind the module interface
            ├─ HydrationAssistantModule → HydrationAssistantOperations → AssistantOperationLifecycle<HydrationIntakeDraft>
            └─ MealAssistantModule      → MealAssistantOperations      → AssistantOperationLifecycle<MealDraft>
```

- **Routing (deterministic).** General intents → core replies. `draft_update` / `draft_confirm` /
  `draft_cancel` / `clarification` → the module of the open draft, whatever its kind (core replies without a
  draft). An intent that opens a record → its module; another module's draft open → "Hai già una bozza aperta
  (…)"; module not enabled → "not available". The router re-reads the open draft inside the turn's unit of work
  and applies nothing if it changed (`draft_changed`), as AI-007.
- **One open draft per conversation**, whatever its kind: the existing partial unique index; the kind-agnostic
  reader makes every path see it (Finance's own repository is kind-scoped; its HTTP create now answers 409
  instead of busy when another module's draft is open).
- **Shared lifecycle** (`AssistantOperationLifecycle<TDraft>` + `IAssistantDraftPolicy<TDraft>`): create, read,
  edit, cancel, lazy expiry and confirmation with the AI-007 rules (conditional writes on status and draft
  version, row lock + execution + Executed in one unit of work, idempotent replay). The module policy only says
  what is missing, what blocks a confirmation (a water intake on a future day) and how to execute the stored
  draft through the module's existing use case. Finance keeps its F2 handlers (no regression risk).
- **Persistence.** Same `assistant_operations` table. `result_transaction_id` → `result_id` (the record the
  confirmation created: a transaction, an intake or a meal; still no foreign key), kinds allowlist extended.
  The SQL is shared (`AssistantOperationRepository<TDraft>` + a draft codec per kind); Finance's repository
  delegates to it. Draft documents: `NutritionAssistantDraftJson.cs`.
- **Time.** Diary drafts resolve date and time like Finance (today → now; another day → 12:00; DST rules), to
  the minute, in the user's IANA zone; the UTC offset given to the diary commands is derived from the resolved
  instant (`AssistantDiaryOccurrence.UtcOffsetMinutes`). No zone → the date stays missing and the reply asks to
  set it.
- **Protocol v2** (`docs/contracts/assistant-interpretation/v2`): Finance section unchanged; `hydration` and
  `meal` sections; generic draft intents; `multiple_operations`; `section_mismatch`; prefixed codes for the new
  sections. Python serves v1 and v2 (`schema.py`, `schema_v2.py`), prompt `assistant-interpret-v3` for v2.
  .NET sends v2 only.
- **HTTP.** Same endpoints. `AssistantOperationResponse` keeps `draft` (Finance) and adds `hydration`, `meal`
  and `resultId`; exactly one draft section matches `kind`. `PATCH` adds `amountMl`, `description`, `mealType`;
  a field of another kind is 400. The confirmation returns `resultId` (and `transactionId` for Finance only).
- **App.** One draft card and one pinned bar for every kind (common header, status, missing fields, issues,
  Confirm/Edit/Cancel, final states); Finance fields and editor only on Finance drafts; a small editor for water
  (ml) and meals (description, meal type) with the shared date/time inputs (`AssistantDiaryDraftEditor`).

## Decisions taken in this increment

| Topic | Decision |
| --- | --- |
| Units | `ml`, `cl`, `l` only; the model reports the quantity and unit as stated; .NET converts; a result that is not whole millilitres in 1–4000 is asked again, never rounded. A number without unit, a unit without number, a container → asked. |
| Meal description | Verbatim user words (case included), never inferred; enough to prepare the meal (no extra question); meal type only when stated. |
| Future | Water on a future day blocks the confirmation (`future_date`, as the Hydration screen); a meal at a future time is allowed and flagged ("L'ora è nel futuro"). |
| Manual create | `POST …/operations` stays Finance-only; water and meal drafts are opened by the chat. |
| Gating | `Assistant:Modules:Hydration` / `Assistant:Modules:NutritionMeals`, default on in Development only. |

## Local migration

`20261027090331_GeneralizeAssistantOperations` (rename column `result_transaction_id` → `result_id` and its
index, recreate the result and kind check constraints). The API does **not** apply migrations at start-up, in
Development or elsewhere, and neither does `tools/dev/start-lifeos-dev.ps1`. Apply it to the local database
before starting the AI-008 API:

```powershell
dotnet tool run dotnet-ef database update `
  --project src/dotnet/LifeOS.Infrastructure/LifeOS.Infrastructure.csproj `
  --startup-project src/dotnet/LifeOS.Api/LifeOS.Api.csproj
```

`Down` cannot run while water or meal operations exist (kind constraint). Not applied to any shared or
production database. The rename is not additive: an AI-007 API cannot use the table after it (runbook Part I,
I4 and I8).

## Residual issues and release blockers

- Release blockers (ADR-014 addendum, runbook Part I gates): owner decision and written privacy acceptance for
  water/meal content; `assistant-interpret-v3` evaluated on the frozen Finance set and on a water/meal synthetic
  set (it now serves Finance too); a green full test run including the PostgreSQL integration suite; the
  migration window and rollback decision; deploy `lifeos-ai` before the API (an older service answers v2 with
  422 → `assistant_invalid_output`).
- Evaluation (2026-10-31, runbook Part I G1/G2): `tools/ai-evals` evaluator `assistant_v2` for protocol 2,
  gates `assistant-v2-gates-v1` (the `assistant-finance-gates-v2` thresholds, owner decision 2026-10-31). Live
  runs of `gpt-6-luna` (effort low, prompt `assistant-interpret-v3`), complete and on the frozen datasets, 0
  execution errors, estimated spend 0.174 USD in all:

  | Dataset | Cases | Incorrect | Critical | Gates |
  | --- | --- | --- | --- | --- |
  | G1 Finance `v1` (converted) | 70 | 2 | 0 | all pass |
  | G1 Finance `holdout-v1` (converted, adapter v2-2) | 68 | 3 | 1 | fail: `critical_error_cases`, `no_critical_in_injection`, `no_critical_in_not_invented` |
  | G2 `hydration-meal-v1` | 60 | 0 | 0 | all pass |
  | G2 `hydration-meal-holdout-v1` | 20 | 0 | 0 | all pass |

  The one critical case is `h_injection_numeric_ids` ("conto numero 3" / "categoria numero 12" taken as a stated
  account and category), the same case and failure as prompt v2 on 2026-10-26; the owner accepted it again on
  2026-10-31 (G1 accepted, not fully met). The two other incorrect holdout cases are unusable outputs (minor:
  the turn fails and can be retried).

  The first scoring of the Finance holdout (adapter `assistant-finance-v1-to-v2-1`) also counted
  `h_other_capability_meal` ("Segna che a pranzo ho mangiato un'insalata") as a critical false draft: its frozen
  protocol-1 answer (`unsupported`, meals were another capability) is wrong in protocol 2, where meals are a
  module. With the owner's approval, adapter `assistant-finance-v1-to-v2-2` replaces that one expectation with
  the v2 contract's answer (a `nutrition_meal` draft) and the saved run was re-scored offline
  (`assistant_v2.rescore`, nothing sent): only that case changed. No dataset file and no threshold changed.

- Water and meal drafts cannot be opened by `POST …/operations` (Finance only, by design).
