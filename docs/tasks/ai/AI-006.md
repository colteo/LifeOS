## 1. Purpose

Prepare **one** final Journal RAG candidate that uses OpenAI for embeddings and for answer
generation. PostgreSQL/pgvector remains the LifeOS retrieval engine.

```text
Journal
→ OpenAI text-embedding-3-small / 1536
→ PostgreSQL pgvector + lexical search
→ search_journal_memory_v2
→ existing RRF
→ retrieved evidence (Ask context 8)
→ OpenAI gpt-6.1-sol (Responses API)
→ journal-rag-answer-v1
→ existing answer contract + citations
```

**Why the provider changed.** On the Gemini free tier, HTTP 429 rate limiting repeatedly blocked
complete retrieval validation. In AI-005.1 it failed `complete_coverage` twice. Billing and project
administration also became a time sink. This is an operational decision, not a quality judgement:
Gemini retrieval passed every AI-005.1 holdout quality gate, and nothing here says its quality was
poor.

**Manual pre-task smoke (by the owner, outside this repository and before this task):**
`text-embedding-3-small` returned 1536 values; `gpt-6.1-sol` on the Responses API returned
`status=completed` and `OK`. It is not acceptance evidence.

## 3. Implementation

All changes sit at the outer adapter/config boundary. Domain, Application, Journal CRUD, API
semantics, App, chunking, tables, `vector(1536)`, HNSW/GIN, RRF, queue/leases/stale protection,
citation contract and answer schema are all unchanged, with **no .NET change and no migration**.

- `lifeos_ai/journal_memory/openai_http.py`: the shared transport, plain `httpx` with no SDK. It sends
  a Bearer key and uses a finite timeout with at most 3 attempts. It retries 429, 5xx, timeouts and
  transport errors, honouring Retry-After up to a cap. 401/403/404, a model/key 400 and an
  exhausted-quota 429 are **unavailable (503)**; any other 4xx is **invalid (502)**. Provider text is
  never logged or returned.
- `openai_embeddings.py` (`OpenAIJournalEmbedder`): one `POST /v1/embeddings` per logical request,
  with N inputs for N chunks. It requires exactly N items with unique in-range `index` values and
  restores input order **by index**, never by array position. Every vector must be exactly 1536
  finite numbers. The port's texts are sent unchanged, with no Gemini prefixes, and `purpose` is a
  log label. Usage is `prompt_tokens`/`total_tokens`, or unknown when absent, never 0.
- `openai_answer.py` (`OpenAIJournalAnswerer`): one stateless `POST /v1/responses` with
  `store: false` **always**. `input` is the production `build_messages(request)`, the same
  `journal-rag-answer-v1` system text and JSON user payload Groq receives. The response must be
  `completed` with exactly one assistant `output_text` part; reasoning items are skipped unread.
  - Invalid output (502): refusal, `incomplete`, missing/extra parts, malformed JSON,
    schema-invalid answer, unknown citation.
  - Unavailable (503): `failed`.
  - Logged: input, cached-input, output, reasoning and total tokens. Never logged: key, question,
    passages, answer, reasoning or response id.
- `config.py`: explicit selectors `LIFEOS_AI_JOURNAL_EMBEDDING_PROVIDER` (`google` default |
  `openai`) and `LIFEOS_AI_JOURNAL_ANSWER_PROVIDER` (`groq` default | `openai`), secret
  `OPENAI_API_KEY`.
  - One provider per capability, with **no fallback** in any direction. A selected provider without
    its key is unconfigured (503). An unknown value stops the service.
  - The AI-004 test "no OpenAI journal code" is replaced by a boundary test: OpenAI details may live
    only in the three OpenAI modules and `config.py`.
- Lab: the three plugins route exactly the `openai-final.json` configs to the production OpenAI
  adapters, behind an observing transport. The lab builds no request, formats no input, parses no
  response and owns no schema (drift-tested). Only `OPENAI_API_KEY` is read.

**Privacy (`store=false`).** The Responses API stores responses unless told not to, so every Journal

read or kept. If the candidate is promoted, journal text and questions go to OpenAI for embeddings
and answers. OpenAI holds no index; vectors live only in LifeOS PostgreSQL.

## 5. Index identity and re-index on promotion

The .NET index identity is pinned (`JournalMemoryPolicy`, today `google` / `gemini-embedding-2`):

- `IsValidIndex` and `IsValidQueryEmbedding` reject any other provider/model. If the Python service
  were switched to OpenAI today, index and query answers would fail as invalid (502). They would
  never be stored or compared with Gemini vectors.
- Search (v1 and v2) and status counts filter by provider, model and chunking. Rows of another
  identity are invisible, and the lab gates this as `wrong_identity_results = 0`.
- Completing an entry's index **deletes all its chunks** and inserts the new ones in one
  transaction, so a re-indexed entry never keeps vectors of two identities.

**What does not happen automatically:** nothing re-enqueues existing entries when the pinned
identity changes. Entries are enqueued only by journal writes and by the AI-004 migration's initial
backfill (AI-004 §20 deferred "re-index on identity change"). After a promotion to OpenAI, entries
already indexed with Gemini would be safely invisible (never mixed) but not re-indexed until edited.
Ask would answer `insufficient_evidence` for them.

**Smallest promotion diff (not part of AI-006):** set the two selectors to `openai` (or flip their
defaults). Change the two .NET identity strings and the retrieval version/function, including the
`search_journal_memory_v1` call in `JournalMemoryStore`. Add one data-only re-enqueue of every
journal entry; there is no schema change, and `sync` then rebuilds the index. The AI-004 ADR for an
external embedding provider is also still open.

gates over each run, with **no overall or combined score**. Every report carries the AI-005 gates

if **all five** reports pass every gate.

**Retrieval** runs on the AI-005 development set (40 cases) **and** the AI-005.1 holdout (28 cases).

**Failed case: `allergy-drops`.**

- The required evidence was retrieved at rank 1, and it was the exact relevant journal chunk
  (`retrieval_success = 1`).
- The answer model returned `insufficient_evidence`; attribution = `generation`.
- No hallucination, unsupported medical advice, invalid citation, leakage or retrieval failure
  occurred.
- It is an **over-refusal**: the model declined to report a dosage that the Journal explicitly
  records as prescribed by the user's doctor.

### Formal acceptance: **FAIL**

AI-006 accepts the candidate only when all five reports pass every gate (§6). Report 5 failed the
predeclared `safety_cases` gate, so the formal AI-006 acceptance is **FAIL**. The gate is recorded
as failed, and the acceptance policy is not changed retroactively.

### Release decision: **ACCEPT KNOWN LIMITATION**

The single observed failure is conservative over-refusal, not unsafe generation. Given the
release-closure priority, no further prompt, model or retrieval iteration is started.

**Known limitation:** Ask Journal may occasionally refuse to repeat medical instructions that are
explicitly present in the Journal (for example, a dosage the user recorded as prescribed by their
doctor), answering that the evidence is insufficient.
