## 1. Goal and scope

From the `+` button, the user opens **Quick Capture**, writes one message such as *"Ieri ho speso 12 euro per la
pizza, ho bevuto mezzo litro d'acqua e a cena ho mangiato pasta al pomodoro"* and gets **three independent
drafts** — an expense, a water intake, a meal — each completed, corrected and confirmed on its own. Nothing is
recorded without the explicit confirmation of that draft.

**In scope**: Finance expenses and income, water intakes, meals of the text meal journal (the three AI-008
operations); creation and absolute correction of drafts; several operations per message and several open drafts per
conversation; per-item failures and selective retry; Android entry point and history.

**Out of scope** (answered with fixed replies): analytics and questions about the user's data, general questions,
other modules (reminders, gym, journal, habits…), transfers, relative corrections ("aggiungi 2 euro"), confirming or
cancelling by text, edits of already recorded data, nutrition estimates, voice, attachments, other languages.
Weekly Review, Action Agent and Analyst are not touched.

## 2. Approved inputs (Gate G1)

### 2.1 Architecture [APPROVED G1]

```text
Router LLM → specialist AI interpreters (Finance, Hydration, Nutrition Meals)
  → deterministic .NET orchestration → independent drafts → individual confirmations
```

.NET keeps authority over validation, authorisation, reference resolution, concurrency, idempotency, transactions,
persistence and confirmations. T1/T2, leases, fencing tokens, `DraftVersion`, the use cases and the existing
confirmations are preserved. No LangChain, no LangGraph.

## 4. Future flow [PROPOSAL]

```text
User message
 T1  accept, lease, attempt                                      (unchanged)
 R   router (lifeos-ai /v1/quick-capture/route, no DB transaction)
       failure / "shape" / rule violation ─────────────────────▶ turn Failed, no item, no draft (R12)
       0 segments ─────────────────────────────────────────────▶ fixed reply "nothing to record"
       truncated ──────────────────────────────────────────────▶ fixed reply "too many operations" (§12)
 P   prepare (reads): open drafts snapshot (id + DraftVersion, local only), reference resolution (§11),
     capacity pre-check (§12), item plan:
       create / correct with a resolved target  → needs a specialist
       everything else                          → outcome known now (Answered)
 S   specialists in parallel, bounded concurrency (D9); each returns a result or a failure for its item only
 T2  one unit of work: lock turn + conversation, re-count open drafts, insert items,
     apply each item (create with source_item_id / conditional correct at the snapshot version),
     ONE assistant reply listing every item's outcome, turn Completed
```

Example: the three-module message above → router: 3 `create` segments with context span "Ieri" → 3 specialist calls
in parallel → T2 creates 3 drafts (`Collecting` if a field is missing, e.g. the Finance account; `AwaitingConfirmation`
otherwise) → one reply: *"Ho preparato 3 bozze: spesa 12,00 € (manca il conto), acqua 500 ml, cena «pasta al
pomodoro». Conferma ciascuna dalla sua scheda."* (template, not model text).

## 6. Responsibilities

| Decision | Who |
| --- | --- |
| How many operations the message contains, of which module, which action, which words belong to each | **router** (closed enums, verbatim spans) |
| The field values of one operation (amount, unit, description, date expression, account mention, category guess) | **specialist** of that module (v2 section, spans grounded in the segment or its context spans) |
| Which draft a correction refers to | **.NET** resolver, locally, from descriptive words (§11) |
| Whether a value is valid, what is missing, what to ask | **.NET** (module policies, unchanged) |
| Whether a draft may be opened (limit, module enabled), whether a write is still current (version, lease) | **.NET** |
| Reply text | **.NET** templates (AI-007 D-5) |
| Whether to record | **the user**, on each draft's Confirm |

Neither the router nor a specialist can name an endpoint, SQL, a table, a command or an identifier; their outputs are
data that .NET reads through a fixed mapping. A specialist only ever sees its own segment (it cannot read or change
another operation), and no output confirms or cancels.

## 7. Several operations, independent drafts

- One message → 0…5 segments → 0…5 items (one per segment, in message order) [APPROVED G1 R6, D3].
- Each `create` item that succeeds opens **its own draft**, with its own kind, status, `DraftVersion`, expiry and
  confirmation. Drafts do not know about each other; there is no message-level or batch draft.
- A conversation may have up to 10 open drafts of any kinds [APPROVED G1 R7, D3].
- Two operations of the same module in one message (two expenses) are two segments, two items, two drafts.
- Shared words ("Ieri" for every segment) reach every specialist that needs them as **context spans**; each
  specialist grounds its date in that span (contract rule) and .NET resolves it per draft.
- A missing field leaves the draft `Collecting`; the reply asks for it (R13). With several drafts, the reply asks
  **one** question at a time for **one** draft (the first incomplete in message order) so that `awaiting` stays
  unambiguous; other incomplete drafts are completed from their cards or by naming them [PROPOSAL].

## 8. Individual confirmations

Unchanged per draft: `POST /api/assistant/operations/{id}/confirm` with `expectedVersion` and `Idempotency-Key`. No
"confirm all" endpoint or button exists or will be added [APPROVED G1 R8]. A draft in `AwaitingConfirmation` can be
confirmed while others are `Collecting` (R9): confirmation already locks only its own row. A textual "sì, registra"
becomes `confirm_request`: the reply shows the resolved draft's Confirm control (or asks which draft, if ambiguous)
and records nothing (R16). A textual "annulla" becomes `cancel`: same, with the Cancel control (D1).

## 9. Partial errors

| Failure | Scope | Effect | Stored | Retry |
| --- | --- | --- | --- | --- |
| Router unavailable / timeout / refused / invalid (`"shape"` or rule code) | turn | turn `Failed` (existing codes), no item, no draft (R12) | turn status only | existing turn retry (re-runs everything) |
| Router `truncated` | turn | turn `Completed`, fixed reply, **no item** (§12) | reply | user resends shorter messages |
| Specialist unavailable / timeout / refused | item | item `Failed` (`specialist_unavailable`, `specialist_timeout`, `specialist_refused`), no draft change; **other items unaffected** (R14) | item | item retry ≤ 24 h |
| Specialist `"shape"` or rule violation | item | item `Failed` (`specialist_invalid_output`) | item | item retry ≤ 24 h |
| Specialist outcome `unclear`, `wrong_domain`, `multiple_operations`, `transfer` | item | item `Answered` with that outcome, no draft change | item | no (final) |
| Target draft moved between prepare and T2 | item | item `Failed` (`draft_changed`), no change | item | item retry re-resolves and re-interprets |
| Ambiguous / unknown reference, two corrections to one draft | item | item `Answered` (`ambiguous_reference`, `reference_not_found`, `conflicting_corrections`), nothing modified (R11) | item | no |
| Draft limit reached | item | item `Answered` (`draft_limit_reached`) | item | no; the user frees a slot and resends |
| Module not enabled | item | item `Answered` (`module_not_available`) | item | no |
| Turn lost its lease / a later message exists | turn | existing `turn_superseded`; nothing applied | turn status | existing |
| **Unexpected DB error in T2** | turn | **today**: rollback, exception propagates, turn stays `Processing` until the lease ends, then `Failed`/`interrupted` [FACT]. No item, draft or reply is committed, so no fictitious success. **Proposed**: after the rollback, fail the turn at once in a new unit of work (`storage_unavailable`), falling back to lease recovery if that fails too [PROPOSAL, NOT IMPLEMENTED] | nothing | existing turn retry |

The assistant reply lists every item's outcome in message order, so a partial result is never presented as complete
and an omitted operation is visible to the user.

## 10. Selective retry [PROPOSAL]

- Only `Failed` items, only before `retry_until_utc` (= creation + 24 h, D4), at most a capped number of attempts
  (proposed 5 per item), one item per request: `POST /api/assistant/items/{id}/retry` (D6).
- The router is never called again; the stored segment and context spans are sent to the item's specialist. A
  correction is resolved again against the current drafts first.
- Fencing: claim `Failed → Retrying` with lease and attempt in one unit of work under the conversation lock; apply
  only if the item still holds that attempt and lease; 409 `turn_in_progress` while a turn of the conversation is
  `Processing`.
- No duplicates: unique `source_item_id` + `ON CONFLICT DO NOTHING`; an `Applied` or `Answered` item is never retried.
- No new assistant message (one reply per user message; the turn fence requires the latest message): the item's
  state and the draft card show the outcome. The app shows "Riprova" on failed items while the window is open and
  "non più ritentabile" after.
- A failed **turn** (router failure) keeps the existing message retry: it re-runs the whole pipeline and cannot
  duplicate, because a failed attempt committed nothing.

## 11. Ambiguity and reference resolution [PROPOSAL]

Rules in [ADR-015 §6](../../adr/0015-quick-capture-router-and-specialist-interpreters.md#6-references-g1-d10-r11).
Summary: references are words, never ids or positions; candidates are the snapshot's open drafts of the segment's
module; one match → that draft; several or doubtful → **nothing is modified** and the reply asks to use the card;
no specialist is called for an unresolved correction (saves a call and guarantees no change). Examples:

| Open drafts | Message | Result |
| --- | --- | --- |
| expense "caffè", expense "giornale" | "il caffè era 1,50" | correction of the "caffè" draft |
| expense "caffè", expense "caffè al bar" | "il caffè era 1,50" | **ambiguous**, nothing changed |
| water (awaiting quantity) | "300 ml" | correction of the water draft |
| two water drafts, no question pending | "300 ml" | **ambiguous** (router: `correct` without reference) |
| one expense | "la spesa era 7 euro" | correction of the only expense |
| two expenses | "la seconda era 7 euro" | **ambiguous** (ordinals are not positions) |
| any | "aggiungi 2 euro al caffè" | out of scope (`relative_correction`, D11) |

## 12. Limits and their handling [PROPOSAL; values APPROVED G1 D3]

| Limit | Default / range | Handling | Testable by |
| --- | --- | --- | --- |
| Segments per message | 5 / 1–5 | sent to the router as `max_segments`. More segments than that → router rule `segments_count` → turn `Failed` (invalid output). `truncated: true` → turn `Completed` with the fixed reply "posso preparare al massimo N operazioni per messaggio: dividilo in più messaggi", **no item, no draft** (nothing half-captured) | contract cases; Application test with a fake router |
| Open drafts per conversation | 10 / 1–10 | counted under the conversation lock in T2 and in every path that opens a draft. Creates are applied **in message order while capacity remains**; the rest become `Answered`/`draft_limit_reached`, listed in the reply. A pre-check in P skips specialist calls for creates that certainly exceed capacity | Application test; PostgreSQL concurrency test (two turns, manual create) |
| Context spans | 3 per segment | router rule | contract cases |
| Retry window | 24 h | `retry_until_utc`; lazy `Expired` | Application test with `TimeProvider` |

Both limits are configuration (`Assistant:QuickCapture:MaxSegmentsPerMessage`,
`Assistant:QuickCapture:MaxOpenDraftsPerConversation`, proposed names), validated at start-up against the contract
maxima; a value outside the range is a start-up error.

## 14. Compatibility and rollout [PROPOSAL]

- **Order** (ADR-015 §7): M1 additive migration → C1 code with flag off → M2 drop of the one-open unique index (only
  when no AI-008 build runs) → `lifeos-ai` with the Quick Capture endpoints (before the API calls them, as AI-008)
  → app build → flag on.
- **Rollback**: flag off. A code rollback past C1 after M2 requires that no conversation has more than one open draft
  (check query in ADR-015 §7); otherwise it needs an owner data decision.
- **Flag off with several open drafts** (after a period with the flag on): the v2 path must not guess "the" draft;
  draft intents are answered "use the draft cards" (C1 requirement), and the cards keep working.
- **v1/v2 protocols** stay served; Finance prompt and protocol choices of AI-008 are unaffected by Quick Capture
  (the flag selects the pipeline).
- **Old app builds** keep working on single-draft conversations; on multi-draft ones they may not show every draft
  (the single-draft response members are null when more than one draft is concerned).

## 16. Invariants the implementation must prove

| # | Invariant | Mechanism | Proof (future test) |
| --- | --- | --- | --- |
| INV-1 | A failed item can exist without a draft | item `Failed` with no `operation_id`; no draft written | Application: specialist failure → item stored, no draft; PostgreSQL: row exists without operation |
| INV-2 | An item cannot create two drafts | unique `source_item_id`, `ON CONFLICT DO NOTHING`, item status fence | PostgreSQL: second insert with the same item → 0 rows; concurrent retries → one draft |
| INV-3 | Replay and retry never duplicate records | message replay, unique `(message_id, ordinal)`, INV-2, unchanged confirmation idempotency | Application + PostgreSQL: replay same `clientMessageId`; retry failed turn; retry item twice; double confirm |
| INV-4 | Several drafts can be open together | no one-open unique index; capacity ≤ N under lock | PostgreSQL: N drafts open, N+1 refused; concurrent turns cannot exceed N |
| INV-5 | Confirmations are independent | per-draft confirm; no batch path | Application: confirm A while B `Collecting`; confirm A does not change B's version; Architecture/HTTP: no batch endpoint |
| INV-6 | A specialist error does not cancel other valid results | per-item outcomes as values; one T2 | Application: 3 segments, middle specialist fails → 2 drafts + 1 failed item, one reply listing all three |
| INV-7 | A DB error never produces a fictitious success | all-or-nothing T2; reply in the same transaction | PostgreSQL: fault injected in T2 → no item, no draft, no reply; turn not `Completed` |
| INV-8 | An ambiguous correction modifies no draft | resolver returns ambiguous; no specialist call | Application: resolver table (§11); every draft's version unchanged |
| INV-9 | The router does not control endpoints or SQL | closed enums; fixed mapping in .NET; strict reader | Contract cases (`endpoint` member refused); Architecture: router output types have no free-form dispatch members; Application: injection text → out of scope |
| INV-10 | No internal id reaches a model | request types without `Guid`/instant/position members; strict request schemas | Architecture test (as AI-008, walking the new request types); contract request cases; Python: `extra="forbid"` |
| INV-11 | Nothing is recorded without explicit confirmation | modules write only in confirm | Application: every turn/item path, including `confirm_request`, leaves module tables unchanged |
| INV-12 | Limits hold | §12 | Application + PostgreSQL |

Note on INV-7: the current code already guarantees "no fictitious success" (rollback, no reply), but **not** an
immediate `Failed` turn (§9). The test must assert the guarantee, not the not-yet-implemented immediacy.

## 18. Evaluation [PROPOSAL]

The contract guarantees grounding, not completeness: a router that omits an operation violates nothing (critical
point 4). Before any live run, a **frozen synthetic** router dataset (Italian, ≥ 1–5 operations per message, shared
context, same-module pairs, corrections with and without references, analytics, transfers, relative corrections,
injections, more than 5 operations) with expected segments, and deterministic scorers:

| Metric | Definition |
| --- | --- |
| Segment recall | expected segments matched by a returned segment (same module + action, span overlap) / expected |
| Segment precision | returned segments matched / returned |
| Omission rate | messages with at least one expected segment missing / messages |
| Module accuracy, action accuracy | on matched segments |
| Out-of-scope recall | analytics/general/other requests classified `out_of_scope` (never `create`) |
| Truncation correctness | `truncated` iff more than `max_segments` operations |
| Contract validity | outputs passing the router rules |

Specialists: the AI-008 v2 sections' datasets adapted to segment + context spans, scored per field; Finance must not
regress against the v2 Finance baseline. Gates are frozen **before** the first live run (AI-003/AI-006 discipline);
live runs only on synthetic data and only after the owner's authorisation (ADR-014). `tools/ai-evals` targets
protocol 1 today; extending it is part of a later increment.
